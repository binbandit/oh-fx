# Architecture

oh-fx is a behavior-faithful Rust port of [vercel-labs/fx](https://github.com/vercel-labs/fx). Upstream behavior is the specification: tool schemas, prompts, help text, and terminal output match upstream unless this document records a deliberate difference.

## Goals

- **A complete port.** Every upstream feature is ported. A feature is left out only for a concrete reason recorded under deliberate differences, such as the Slack app, which depends on credentials that belong to Vercel. Being hard to port is not a reason.
- **Upstream's footprint.** oh-fx is as fast, as small, and as frugal as upstream. Its release builds are held to upstream's on binary size, startup time, time to first request, memory use, and rendering cost, and a change that regresses any of them needs a stated reason.

## Principles

- **Port leaf behavior, not upstream coupling.** Escape parsing, markdown, syntax highlighting, glob matching, git-backed file listing, the frame renderer, and MCP transports are ported from upstream, and their upstream tests become ours. Upstream's large shared structs (`DispatchContext`, `AgentRuntimeDeps`) are replaced by narrow traits and constructor injection.
- **Contracts first.** The agent and the TUI depend only on `ofx-contract`, so they can be built and tested with fakes while transports and tools land in parallel.
- **Module names follow upstream files.** A Rust module that ports `src/core/tooling/tool_dispatch.zig` is named `tool_dispatch.rs`, which keeps the parity ledger mechanical.
- **Every boundary is a compile-time fact.** Crates are layered and acyclic. The UI cannot reach sessions or config, and transports cannot reach product state.

## Type ownership

- A type lives in the crate that ports the upstream file defining it. `core/shared/types` and the tool dispatch contract map to `ofx-contract`, so `PermissionMode`, `ReasoningEffort`, `ApprovalPolicy`, tool metadata, and tool result errors live there. `ProviderId` and context limits live in `ofx-config`, session ids in `ofx-session`, and shell command analysis in `ofx-shell`.
- A crate that needs another crate's type depends on its owner and never keeps a copy. `ofx-cli` validates provider ids, session ids, and login providers by calling their owners while parsing, as upstream does.
- Public items need a consumer outside their crate. A crate lands with its first consumer, or directly before it in the same stack of pull requests. A type moves to its owner in the pull request that adds its first outside consumer.

## Key decisions

| Concern | Decision | Reason |
|---|---|---|
| Async | tokio for the agent, transports, MCP, and processes; no runtime on fast paths such as `--version` | Cancellation of in-flight streams and process trees |
| UI thread | A plain OS thread polling the tty, a wake pipe, and a signal pipe | Rendering never competes with tool tasks, and it mirrors upstream's event loop |
| Agent and UI contract | `UiEvent` and `UiCommand` data, which gain serialization with their first wire consumer (ACP or a JSON event stream). Approvals and questions are correlated by `RequestId` through a map of pending oneshots | One event stream drives the TUI, `ask --json`, ACP, and test fixtures |
| HTTP and TLS | reqwest with rustls and the ring provider. On Linux, a verifier of our own reads one CA bundle, or `SSL_CERT_FILE` and `SSL_CERT_DIR`, on the first TLS handshake and adds a connection's `tls.ca_file`; macOS and Windows use rustls-platform-verifier with extra roots from `SSL_CERT_FILE` or `tls.ca_file` | Corporate CAs and proxies work, static musl builds need no cmake, and neither startup nor plain HTTP pays for parsing the system's roots |
| CLI | A static command spec table ported from upstream, scanned the way upstream scans arguments: no flag clustering, and values may start with `-` | One source for `--help`, `/help`, and the slash menus, with upstream's exact acceptance rules |
| Terminal | rustix plus a port of upstream's escape parser | Upstream needs OSC 11, DSR, and DA1 replies that crossterm drops |
| Renderer | A `FrameSink` seam. A simple live-region renderer ships first; upstream's frame engine replaces it | Resize and tmux parity with upstream's resize tests, without blocking the first release |
| Markdown | Port upstream's streaming processor and profile tokenizer | Linear cost per delta, identical output, and no grammar data in the binary |
| Files and grep | `git ls-files`, `git grep -F`, a `memmem` fallback walk, and upstream's glob matcher | Tool descriptions promise literal matching and git semantics |
| MCP | Hand-written transports on `ofx-jsonrpc` and `ofx-http` behind an `McpTransport` trait | Upstream speaks legacy SSE and several protocol versions, and rmcp changed major versions three times in 2026 |
| Errors | `thiserror` in libraries; `anyhow` only in `ofx-app` and the binary. Upstream error names stay visible to the model | Tool results expose error names upstream already uses |
| Panics | `panic = "unwind"`. The agent contains every panic that unwinds out of tool code. One while preparing, describing, inspecting the file mutation of, or executing a call becomes that call's tool error, with all of `execute` running inside the call's tokio task, and one while dropping a call that never ran is discarded. Only the terminal owner restores the terminal, and only on fatal paths: a panic on the UI or main thread, or process exit | A bug in one tool becomes a tool error instead of ending a work session, and a contained panic never disturbs a live UI |
| Lints | Workspace clippy `pedantic`, `unreachable_pub`, `unwrap_used`, no `unsafe`, no comments | Code explains itself, and dead code stays visible to the compiler |

## Naming and paths

- Binary `oh-fx`, with an `ofx` symlink installed next to it.
- Environment variables use the `OH_FX_` prefix in place of upstream's `FX_`.
- Settings live in `$XDG_CONFIG_HOME/oh-fx` (default `~/.config/oh-fx`), sessions and credentials in `$XDG_DATA_HOME/oh-fx`, logs and upgrade state in `$XDG_STATE_HOME/oh-fx`, and caches in `$XDG_CACHE_HOME/oh-fx`, on Linux and macOS alike.
- Project configuration is `.oh-fx.json`, and project skills live in `.oh-fx/skills`.

## Deliberate differences from upstream

- Custom provider connections accept `headers` with `${VAR}` interpolation, `tls.ca_file`, `proxy`, a `models` list, `max_tokens_parameter` (`max_completion_tokens` for reasoning models and Azure OpenAI), plain `http://` base URLs on any host, and host names with `_`, so self-hosted gateways such as Portkey work. Settings files may start with a UTF-8 byte order mark.
- The chat-completions stream parser tolerates gateway dialects that upstream rejects: empty-choices chunks, a stream that ends after its finish chunk without `[DONE]`, repeated finish chunks, mismatched usage totals, provider-native finish reasons, `stop` after tool calls, tool call deltas without an `index` or with empty ids or repeated names, and finish chunks without a `delta`. A repeated name that could also extend to another advertised tool fails as `InvalidToolName`, where upstream appends it. `{"object": "error"}` chunks and a `finish_reason` of `error` fail as provider errors, and a response that is not `text/event-stream` fails with its JSON error or `UnexpectedContentType` instead of a parse error.
- Provider connections never follow redirects. A 3xx answer names the redirect target's host and explains that `base_url` must point at the gateway API, so a sign-in page never receives the request or its headers.
- An HTTP 404 keeps its real status in the error line, and protocol, transport, and stream failures print a second `oh-fx ask:` line with a masked, terminal-safe detail; a 401 adds the gateway's own explanation. Upstream prints only the error name.
- Stream and response body failure details carry structural facts, never the provider's raw bytes: a rejected stream event is named by its position and size (and, for Codex, a validated event type), an incomplete stream by its event and byte counts, a response that is not `text/event-stream` by its media type and size, and an error body whose read fails partway, which fails as `ReadFailed` as upstream does, by its status, read error, and bytes received. Provider error objects are parsed, re-serialized, and masked before they are shown.
- An HTTP error body without an `error` object but with a non-blank top-level `message` or `detail` string, such as chatgpt.com's `{"detail":"The 'gpt-5.4' model is not supported when using Codex with a ChatGPT account."}`, is shown as `API request failed · HTTP 400 · <text>`, masked and made terminal-safe like an error object's message. Upstream shows such bodies raw, as `HTTP 400: {"detail":...}`. Bodies whose `detail` is not a string, such as validation error lists, still print raw after masking.
- An error response whose body read fails partway or times out keeps its `Retry-After` on the `ReadFailed` or `Timeout` error, so the retry waits as long as the gateway asked. Upstream drops the delay with the body and retries on its default backoff.
- Configured secrets are masked in every provider detail, including forms hidden behind JSON string escapes (`\uXXXX` and surrogate pairs too) or percent-encoding, alone, mixed, or layered, such as `%5Cu0070`: the bearer token, proxy credentials, every substituted value of a header whose name looks sensitive, and other substituted values of at least 8 bytes. A secret that itself contains escapes is also matched in each decoded form of at least 8 bytes. Decoding repeats until a round changes nothing, for at most sixteen rounds over at most 64 KiB, enough for any backslash run that fits; text that would still decode after that, or that is longer and contains any escape, is shown as `content withheld (N bytes)` instead. A bearer token longer than 16 KiB or with non-visible characters fails as `InvalidConfiguredProviderCredential` before any request. Whitespace-only header variables count as missing, and nested defaults are rejected.
- A model failure diagnostic, the text in retry notices and in Codex `response.failed` details, masks anything that looks like a credential across its whole text before it is cut to 256 bytes. Upstream cuts first, so a credential that crossed the cut could leave a prefix too short to be recognized and masked.
- Codex details follow the same rules. A rejected Codex stream event is reported as `stream event N (TYPE, B bytes) was rejected`, such as `stream event 35 (response.completed, 15517 bytes) was rejected`, where upstream reports only the error name. TYPE is the `type` the reducer read while parsing an event whose content it then rejected, shown only when it is 1 to 64 bytes of lowercase ASCII letters, digits, `.`, and `_` that secret masking and terminal-safe encoding leave unchanged. An event rejected by the event-count or byte limits is never parsed, so it, an event that is not valid JSON, and any other type are reported as `stream event N (B bytes) was rejected`. Failure codes and messages from `response.failed` and `error` events are masked with every token the request sent as well as the current one, and Codex HTTP error bodies take the same parse-then-redact path as custom connections.
- A Codex `error` event without a top-level `code` or `message` takes both from its nested `error` object, using the object's `type` when it has no `code`, so `{"type":"error","error":{"type":"server_error","code":null,"message":"..."}}` is retried as a server error and shows its message. Upstream reads only the top-level fields and reports such an event as a non-retryable `provider_error: Provider response failed`.
- Model retries stop after 10 attempts instead of continuing indefinitely, never start after text has streamed, and do not retry TLS or proxy tunnel failures.
- On Linux, TLS roots come from one CA bundle that is read when the first TLS handshake needs it, as upstream reads them with `std.crypto.Certificate.Bundle.rescan`, with these differences. `SSL_CERT_FILE` and `SSL_CERT_DIR` replace the bundle with the files and directories they name, as in rustls-native-certs and OpenSSL; upstream ignores both. The search tries Entware's `/opt/etc/ssl/certs/ca-certificates.crt` and OpenHarmony's `/etc/ssl/certs/cacert.pem` after upstream's six bundles, and the certificate directories are the ones rustls-native-certs read before, `/etc/ssl/certs`, `/etc/pki/tls/certs`, and `/etc/security/certificates`, where upstream reads Android's `/system/etc/security/cacerts` in place of the last, so no directory is trusted that oh-fx did not trust before. When a certificate fails verification against the bundle for any reason other than a name mismatch, oh-fx reads the certificate directories once and verifies again against the bundle and the directories together, the roots it trusted before, so a CA added to `/etc/ssl/certs` without regenerating the bundle is trusted, even when it replaces a bundled CA with the same name; upstream reads only the bundle. A connection's `tls.ca_file` adds to these roots. A failed load is kept for the rest of the run, fails each TLS request as `CertificateBundleLoadFailure`, upstream's name, with a second line naming the file, and is not retried. On macOS and Windows, oh-fx keeps rustls-platform-verifier and the system trust store.
- `oh-fx ask` reads the TLS roots on a background thread once its arguments and settings are valid and the connection, custom or Codex, uses `https://`, so the parsing overlaps name resolution, the TCP connection, and the start of the TLS handshake. Upstream reads them when its first request starts and opens a whole connection ahead of time only for the Vercel AI Gateway; oh-fx never connects early, so the HTTP client's proxy, `CONNECT`, and `NO_PROXY` handling always applies.
- `oh-fx ask ""` fails with `InvalidConversationEvent` before any request is sent.
- The turn context reads git facts from the repository that encloses the workspace, where upstream reads only `<workspace>/.git`, and reports a tracked file as dirty only when it is missing or its size differs from the index, never from its modification time alone.
- A streamed write to a closed or failing stdout cancels the request and ends `ask` with the failed write's name, such as `BrokenPipe` or `NoSpaceLeft`.
- Until sessions land, a tool result over 64 KiB is cut at upstream's `--no-save` truncation marker instead of being stored behind a `read_tool_result` handle, and `read_file` reports image files as binary content until tool image attachments land.
- Until upstream's ask presenter is ported, terminal-mode `ask` writes the turn to stdout as plain lines: assistant text as it streams, operational lines such as `Done.`, `[notice]` recovery lines, and tool progress lines. Consecutive lines of each of the last three kinds stay together, and exactly one blank line separates each such run from assistant text and from runs of another kind. Whitespace the model streams is written only once visible text follows it, so blank lines at either edge of a stretch of text merge into that separator, and the output ends with a single newline; whitespace at the very start of the output is kept. Upstream paints the same events on stdout as a styled transcript with a banner, the prompt, indented Markdown, and grouped tool rows. Blocked-action guidance and failure lines stay on stderr and start on a new line. Progress lines and blocked-action labels escape their control characters with terminal-safe encoding. The raw, quiet, and JSON modes print progress, operational lines, and notices on stderr, as upstream does.
- In the ask and auto permission modes, whether set in settings or for one request with `--auto`, a `read_file` call whose path, or a `glob_files` or `grep_files` call whose search root, resolves outside the workspace needs approval. Upstream reads and searches such paths without approval unless a configured `permission` rule asks for it. Until approval prompts, permission rules, and the auto-mode reviewer are ported, nothing can grant that approval, so `ask` handles the call as upstream does when no approval prompt is available: it prints the blocked-action guidance with upstream's ask-mode or auto-mode hint (which still name `--auto` and the interactive shell), records the call as an error, and fails with `NonInteractivePermissionRequired`. Full access, from settings, `--full-access`, or `--yolo`, reads and searches external paths. A call admitted only for the workspace resolves its path again when it runs and fails with `PathOutsideWorkspace` if the path has left the workspace since admission.
- `write_file` and `edit_file` are admitted as upstream admits them when no `permission` rule, session grant, or approval prompt applies: in ask mode every change needs approval, so `ask` prints the blocked-action guidance and fails with `NonInteractivePermissionRequired`; auto mode allows changes inside the workspace and new files anywhere unless their path is sensitive; a write that would leave an existing workspace file unchanged needs no approval; full access allows everything. Configured `permission` rules are not applied yet. In auto mode, a change that upstream hands to its safety reviewer model, an existing file outside the workspace or a sensitive path, is held instead: oh-fx has no reviewer yet, so the model receives upstream's `tool_review_held` result with `review_cause` `reviewer_unconfigured` and the turn continues. Upstream reviews such a change with the provider's reviewer model, which every upstream provider configures, and holds it the same way only when no reviewer is configured.
- A `write_file` or `edit_file` target outside the workspace is not read before the call is admitted, in keeping with the approval external reads need. In ask and auto mode such a call therefore needs approval or is held even when it would change nothing or its `old_string` is missing, where upstream first reports `No changes to …` or the edit failure. With full access the file is read when the call runs, its path must still resolve to the same target, and those outcomes are reported then. Workspace targets are read before admission, as upstream reads every target.
- Auto mode sends a file change to review when its target path contains a `.git` component or `.ssh/authorized_keys`, `.ssh/config`, `.ssh/rc`, `Library/LaunchAgents`, `Library/LaunchDaemons`, `.config/autostart`, `.config/environment.d`, `.config/systemd/user`, `.local/share/systemd/user`, `.config/fish/config.fish`, `.config/fish/conf.d`, `.config/git/config`, `.gitconfig`, a zsh startup file (`.zshrc`, `.zshenv`, `.zprofile`, `.zlogin`, `.zlogout`), a bash startup file (`.bashrc`, `.bash_profile`, `.bash_login`, `.bash_logout`, `.bash_aliases`), `.profile`, or `.pam_environment`. Names are compared after Unicode case mapping, with zero-width and bidi format characters removed, so a spelling that a case-insensitive filesystem opens as a protected name, such as `.GIT`, `.ssh` written with U+017F LATIN SMALL LETTER LONG S, or `authorized_keys` written with U+212A KELVIN SIGN, is also reviewed. Upstream matches a shorter list byte for byte, with `.git/hooks`, `.git/config`, and `.git/config.worktree` in place of any `.git` component, so a new `.GIT/hooks/pre-commit` on a case-insensitive filesystem, a submodule's `.git/modules/<name>/hooks`, or a new `~/.zshenv` skips review there.
- `write_file` and `edit_file` open the target's anchor directory and every parent without following a symlink in any component, as `read_file` does, before checking the identities recorded at admission. Upstream opens the anchor by its absolute path, following symlinks above it. On macOS each of those directories must also be readable. A new file is put in place only if nothing has appeared at its path: through an exclusive rename, or, where the filesystem has none, a hard link that fails when the path exists, and the write fails where neither is available. A file that appears in that moment fails the write with the stale-preview message, where upstream replaces it. If the staged file's name cannot be removed after such a link, the success result names it. Before `write_file` reports `No changes to …`, it checks again that the parent directories, the file, and its content are the ones it read when the call was prepared. It fails with the stale-preview or changed-traversal message if any of them changed, and with `file mutation failed before commit` if the file can no longer be read. Upstream reports the content it read earlier. The diff preview upstream builds for its approval prompt is not built until approval prompts land.
- In auto mode, `shell` runs a command without approval when each of its `&&` stages is one of upstream's known reversible commands, such as `git status`, `git fetch`, `which`, `npm install`, `npm run <script>`, and `zig build`, and observes a session with `interact` without approval, as upstream does. oh-fx admits fewer commands: `git fetch` only with flags that cannot run a program or rewrite local refs and with no `+` refspec or `::` transport, `npm`, `pnpm`, `yarn`, `bun`, and `zig build` only with flags known to be inert before `--`, and no word that contains `^`, `#`, or `!` or starts with `=`, which a user's zsh options can expand into file names. Upstream also admits flags such as `git fetch --upload-pack=<program>` and `npm install --script-shell=<program>`. Only an unquoted, unescaped `&&` separates stages, so a quoted or escaped `&&` stays an argument of the command around it and that command's flags are still checked; upstream splits on it too. A reversible command whose `cwd` resolves outside the workspace needs review here, in keeping with the approval external reads need; upstream runs it. A `cwd` outside the workspace that does not exist goes through the same admission, so its absence is reported only once the call is allowed, and a command admitted only for the workspace resolves its `cwd` again when it runs and fails with `PathOutsideWorkspace` if the directory has left the workspace since admission. Upstream hands every other shell call, including `stop`, to its auto-mode reviewer, and runs a read-only command requested with `profile: clean` directly, without a shell. Until the reviewer and that direct route are ported, those calls are held as file changes are: the model receives upstream's `tool_review_held` result with `review_cause` `reviewer_unconfigured` and the turn continues. As upstream does, every shell call needs approval in ask mode, so `ask` fails with `NonInteractivePermissionRequired`.
- Until sessions land, `ask` offers the `shell` schema that upstream offers when it keeps no session, without `tty`, `shell`, and `chars`, so commands never get a terminal and `interact` only observes. Shell results carry `full_output_handle: null`, and output cut to its head and tail is marked `... bytes omitted ...`, where upstream's marker points at the handle.
- When a shell command ends on its own, oh-fx kills what is left of its process group; upstream kills what is left of its session, so a process that moved to another group of the same session survives here. A stop, a deadline, or the loss of the oh-fx process that owns the command also reaches only the command's process group. Until upstream's process tree tracker is ported, descendants that leave the group, such as a daemon started with `setsid`, keep running after a stop, a deadline, or the loss of the owner, where upstream finds them through the process tree and stops them too. After a command ends on its own, both keep a daemon that started its own session. If the supervisor has still not exited five seconds after its group was killed, oh-fx reports the command as indeterminate with incomplete output at once and reaps the supervisor in the background; upstream reports the same result but first waits for the supervisor to exit.
- Until shell output streaming is ported, the raw, quiet, and JSON modes of `ask` do not echo a shell command's output lines on stderr as it runs, and `ask --json` records a shell call with only its name and status, without upstream's `action`, `error`, and `command_result` fields.
- `read_file` opens the resolved path without following a symlink in any component, not only the last one as upstream does. It walks from `/` with `O_NOFOLLOW | O_DIRECTORY` descriptors, opened with `O_PATH` on Linux so directories that grant only search permission still work; on macOS each directory on the path must also be readable. A parent directory swapped for a symlink after the path was resolved fails as `NotRegularFile` instead of exposing the symlink target's content.
- `read_file` clips a line longer than its 2,000-byte cap after the last whole character that fits. Upstream cuts at the byte cap, which can split a multibyte character and replace the whole result with the binary-output notice.
- `ask --json` lists the tool calls of a parallel group in call order. Upstream lists the calls that ran in the order their threads finish, then the calls that failed before running, such as on invalid arguments or a missing path.
- A panic in tool code fails only its own call with a `tool_execution_failed` result whose message is `Tool execution panicked`, and the rest of the batch still settles. This covers preparing a call, describing it, inspecting its file mutation, and executing it, including the part of `execute` that runs before it returns its future. A panic while dropping a call that never ran, because its description or file mutation panicked, it was held for review, or an approval or a cancellation stopped the batch first, is discarded, and so is a panic while dropping a panic's payload. The agent finds a tool by the spec it read once when it was built, so it never calls a tool's `spec` again while dispatching. Upstream is written in Zig, where a panic ends the process. A tool error there becomes `Tool execution failed` with the error's name.
- Until sessions land and `ask` saves the full-access acknowledgment, the full-access warning prints on every run unless `yolo_acknowledged` is set by hand, and `ask --json` reports recovery as `"durable": false`.
- Secret masking runs upstream's matchers unchanged and a hardened pass, and masks the union of both: credentials in any `scheme://user:password@host` (cut at the last `@`), sensitive keys (api keys, tokens, secrets, passwords, credentials, cookies, auth headers, Portkey virtual keys) in `key=value`, `key: value`, JSON string members, and `--key value` forms, case-insensitive `Bearer`/`Basic`/`Token` values with the full base64 alphabet, and JWTs whose base64url header decodes to a JSON object. Output is byte-identical to upstream when the hardened pass finds nothing.
- Terminal-safe encoding escapes every Unicode default-ignorable code point except the emoji presentation selectors U+FE0E and U+FE0F, so soft hyphens, the Arabic letter mark, Hangul fillers, and tag characters cannot hide text. Upstream escapes only C1 controls, zero-width characters, line separators, bidi embeddings, and the byte order mark.
- ANSI-aware width measurement and wrap cuts treat DCS, SOS, PM, and APC strings (`ESC P`, `ESC X`, `ESC ^`, `ESC _`) as zero width through their string terminator, so a cut never splits one and leaves the terminal inside it. Upstream treats them as two-byte escapes.
- A file tool `path` that contains a NUL byte fails with `Cannot resolve path "a.txt\u0000x": InvalidPath`, which shows each NUL as `\u0000`, and a glob pattern whose static base contains one fails with `Unable to resolve glob search root: <path> (InvalidPath)`. Upstream cuts both at the NUL, so `a.txt\u0000x` reads `a.txt` there.
- Git commands behind `glob_files` and `grep_files` run with `--no-pager -c core.fsmonitor=false -c core.hooksPath=/dev/null`, `GIT_NO_LAZY_FETCH=1`, and an empty `GIT_ALLOW_PROTOCOL`, so a repository's config cannot make a search run its fsmonitor hook, a git hook, a pager, or a lazy fetch from a promisor remote through `remote.<name>.uploadpack` or `core.sshCommand`. Upstream runs them with the repository's config in effect.
- `git grep` runs with `-c color.grep=never -c grep.column=false -c grep.fullName=false`, so settings such as `color.ui=always`, `grep.column`, and `grep.fullName` cannot change the output `grep_files` parses. Upstream drops tracked matches under those settings, and its scoped searches find nothing under `grep.fullName`.
- `grep_files` canonicalizes every candidate file before reading it and skips one that resolves outside both the workspace and the search root, so a tracked file reached through a symlinked directory cannot expose content from elsewhere. Upstream checks containment only when the file itself is a symlink.
- `grep_files` opens each resolved candidate with `read_file`'s opener, which follows no symlink in any component and opens with `O_NONBLOCK`, and reads it only when the opened file is regular, so a directory swapped for a symlink after the candidate was checked cannot expose outside content, and a symlink to a FIFO is skipped instead of blocking the search forever as it does upstream.
- `glob_files` and `grep_files` use git only when `git rev-parse --show-toplevel` names the search root or one of its ancestors, so a repository whose `core.worktree` or `.git` file puts its work tree elsewhere, or whose `core.bare` leaves it without one, cannot make a search list or read files from outside the search root under the search root's names. Those roots use the directory walk and in-process scan, as outside a repository. Upstream searches whatever work tree git reports.
- When `glob_files` and `grep_files` walk the directory tree instead of using git, an entry whose directory listing reports no type, as on filesystems without `d_type`, is checked with `fstatat` and listed or descended like any other file or directory. Upstream skips such entries. Each subdirectory is opened relative to its parent without following symlinks, so a directory swapped for a symlink after it was listed is skipped where upstream follows it.
- A `glob_files` pattern with a directory part matches only at the depth it spells out: `src/*.rs` and `src/main.rs` match files directly in `src`, and `src/**/*.rs` matches at any depth below it. Upstream matches what follows the directory against file names at any depth, so `src/*.rs` also lists `src/nested/other.rs`.
- `grep_files` passes `include` to `git grep` as a pathspec only when it starts with `*` and contains no `/`, `\`, `[`, `{`, or `}`, so git can only widen the match, and otherwise lets git search every tracked file and filters with its own matcher. Upstream passes every other slash-free include as well, so git reads `[ab]` as a character class and matches a pattern that does not start with `*` only at the search root: a tracked `foo[ab].txt` is missed for `*[ab].txt`, and a tracked `src/main.rs` for `main.rs`.
- Git commands behind the file tools clear `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, and `GIT_ALTERNATE_OBJECT_DIRECTORIES`, so git finds the repository from the search root alone. Upstream passes them through from its environment.
- The assistant intro filter matches "oh-fx" instead of "fx".
- There is one release stream, so `oh-fx upgrade` has no `--channel` option.
- The top-level help links to the oh-fx repository instead of fx.sh/docs.
- oh-fx has no `slack` command (`slack install`, `slack status`, and `slack refresh`) and no one-command Slack MCP preset (`mcp add slack`, added upstream in vercel-labs/fx#1101). Both depend on fx's own Slack app, whose public Client ID and fx.sh OAuth bridge belong to Vercel, so they are omitted until oh-fx has a Slack app of its own. `oh-fx slack` fails as any unknown command does, and `oh-fx mcp add slack` keeps the usage error that upstream printed before the preset. Without the `slack` row, the top-level help's command column is one character narrower than upstream's, because `slack <install|status|refresh>` was its widest usage. Once MCP support lands, a user with their own Slack app can still add Slack's MCP server with `oh-fx mcp add --transport http slack https://mcp.slack.com/mcp` and set `oauth.client_id`, `oauth.client_secret_env`, and `oauth.callback_port` for it in the profile MCP configuration, as upstream allows: upstream authorizes any Slack Client ID other than fx's through its ordinary callback at `http://localhost:<callback_port>/callback`, and Slack offers no dynamic client registration, so the Client ID is required. Those fields alone are not enough: [Slack's MCP server documentation](https://docs.slack.dev/ai/slack-mcp-server/) limits it to internal apps and apps published in Slack's directory, and the app must also list that callback as an OAuth redirect URL and request the user scopes the MCP tools need.
- Top-level help narrower than its two-column layout needs (under 53 columns for commands and flags) puts each usage on its own line with the summary indented below, and stacks the resource links when their longest word does not fit beside the labels, so only unbreakable words overflow. Upstream keeps the two-column layout at every width.
- An unknown command is echoed through terminal-safe encoding capped at 160 bytes, so escape sequences, other control characters, and invalid UTF-8 print as escapes such as `\x1b` and `\xff`. Upstream writes the raw bytes to the terminal.
- A closed stdout cannot be detected: the Rust runtime reopens closed standard streams on `/dev/null` before `main` runs, so output is discarded where upstream reports `WriteFailed` or `NotOpenForWriting`. Full disks and closed pipes fail as upstream does.
- Until their features land, commands and flags that oh-fx parses but cannot run fail with `oh-fx: <command> is not available yet` and exit status 1, where upstream runs them. Arguments are validated first, so malformed ones still fail with upstream's usage errors. With `--json`, such a command also prints `{"kind":"<command>","error":"<command> is not available yet","code":"NotAvailableYet"}` on stdout, and `ask --json` prints its JSON result with the error `NotAvailableYet`. This covers the interactive session (`oh-fx` with no arguments, `-c`, `-r`, `--resume`, and `resume`), every command except `ask`, `upgrade`, `help`, `--version`, `login codex`, `logout codex`, `provider codex`, and `models` while Codex is the selected provider (so `login` and `logout` for Vercel and Grok, `provider` for the gateway, Grok, and custom connections, and `models` for the gateway and custom connections are covered), the `--context-limit` and `--add-dir` launch modifiers, since `ask` has no skills, MCP servers, project instructions, or extra workspace roots for them to apply to, and the `--sessions-v2` launch modifier on `ask`. Commands that keep no sessions upstream, such as `upgrade`, `login codex`, `logout codex`, `help`, and `--version`, accept and ignore `--sessions-v2` as upstream does; the commands that use sessions upstream, the interactive session, and `acp` fail as not available yet with or without it.
- `oh-fx ask` honors `--model`, `--effort`, `--fast`, `--no-fast`, `--auto`, `--full-access`, `--yolo`, `--system`, `--timeout`, `--json`, `--quiet`, and `--no-color`. It fails as not available yet on `--image`, `--prompt-permissions`, `--resume`, `--resume-id`, and `--continue-recovery`, because image attachments, approval prompts, and sessions do not exist yet. It also fails as not available yet when `--sessions-v2`, given before or after `ask`, or `OH_FX_SESSIONS_V2` set to `1` or to `true` in any letter case selects the v2 session store, unless `--no-save` is given. Without them, `ask` runs and saves nothing, since upstream's default store is not ported either; the flag and the variable explicitly ask for the v2 store, whose sessions upstream resumes only with the flag, so oh-fx reports that it cannot honor the request instead of quietly saving nothing. Upstream's `--no-save` writes nothing to either store, so with it the request runs. It validates `--provider-order`, `--provider-strict`, and `--no-provider-strict` as upstream does and then ignores them, as upstream does for custom provider connections, which never advertise gateway routing. Custom connections never advertise reasoning or Fast mode either, so `--effort` and `--fast` leave their requests unchanged, as upstream. `--no-additional-dirs` and `--no-save` are accepted, since ask saves no sessions yet, and `--verbose` is accepted and ignored, as upstream does.
- `ask --system` must be valid UTF-8 and otherwise fails with `InvalidAskArgs` before any request. Upstream sends the invalid bytes as a JSON byte array, which OpenAI-compatible gateways reject.
- Releases come from GitHub Releases. Every push to `main` that changes more than documentation publishes `v<version>-dev.<n>`, where `<n>` is the commit count on `main`.
- Upgrade checks run from every command through a detached background process, at most once every five minutes when commands run, instead of upstream's thirty, so each merge reaches users quickly.
- Assistant markdown escapes terminal controls once, as text enters a span: C0 controls other than tab, DEL, C1 controls, line and paragraph separators, and bidi embedding, override and isolate controls appear as `\xNN` or `\u{NNNN}`, and table widths and hanging indents measure that escaped text. Link targets and numeric entities stay literal text unless every code point is one the terminal-safe encoder keeps. Upstream passes these code points to the terminal.
- Pipe tables take their column count from the header row and drop extra cells, as GitHub-flavoured Markdown does, and a table that would render more than 16 cells per source byte stays plain lines. Upstream widens to the longest row and pads every row, so 32 KiB of pipes rendered hundreds of megabytes.
- `MarkdownProcessor::push` takes `&str`, so callers replace invalid UTF-8 before markdown sees it. Upstream processes raw bytes.
- A heading with no text at the end of a stream produces no line. Upstream writes only its style codes.
- A level-six heading whose whole text is `• `, `☐ ` or `[1] ` has no hanging indent. Upstream's wrap parser reads its dim text as a list, task or footnote marker; the line is too short to wrap either way.
- `flush` never changes events an earlier `push` returned, and the footnote separator counts blank lines already emitted, as upstream's assistant stream does. Upstream's processor trims trailing blank lines from a buffer it shares with earlier pushes.
- The syntax highlighter never splits a multi-byte character. Upstream can cut one after a backslash inside a string, which shows replacement characters.
- The ChatGPT login is stored in `$XDG_DATA_HOME/oh-fx/chatgpt-auth.json` instead of `~/.fx/chatgpt-auth.json`, in upstream's file format and with upstream's lock file. The sign-in, token, and Codex endpoints are fixed; tests pass their own endpoints to constructors, and upstream's `FX_E2E_*` endpoint variables do not exist, so no oh-fx variable can point these requests at another host. Standard proxy settings such as `HTTPS_PROXY` and `ALL_PROXY` still route them through the configured proxy.
- The sign-in callback compares `state` in constant time and serves browser connections concurrently, each with its own 30-second socket timeout, so an idle preconnect or a slow request cannot hold back the real callback; upstream serves them one at a time. Its pages and messages say oh-fx, and requests carry an `oh-fx/<version>` user agent.
- The ChatGPT sign-in redirects the browser to `http://127.0.0.1:<port>/auth/callback`, the address its callback listener binds and the one OpenAI's Codex CLI uses, where upstream uses `localhost`, which some browsers resolve to `::1` first. The code exchange sends the same redirect URI. A token response without `expires_in` takes the session's expiry from the access token's `exp` claim, as refreshes already do, where upstream fails the sign-in; an `expires_in` that is present but not a positive integer still fails it.
- oh-fx names itself to OpenAI with `originator=oh-fx` when signing in with ChatGPT and in the `originator` header of every Codex request, matching its `oh-fx/<version>` user agent, where upstream sends `fx` in both.
- The Codex transport honors `Retry-After` on HTTP errors, as custom connections do, where upstream's Codex transport ignores it, and the 10-attempt retry limit applies.
- The Codex transport refreshes a due access token before each request and, after a 401, refreshes once and resends the request. Upstream makes the same decisions in its agent loop. A Codex 401 adds `Run oh-fx login codex to sign in again.` after the authentication failure line.
- `ask` rejects a `--model` that is not valid UTF-8 with `InvalidModel` before it reads or refreshes the Codex login, so such a model never triggers a refresh. Upstream has no such error and loads and refreshes the login at startup, before it looks at the model. Other models the Codex request rejects, such as an empty name, still fail when the request is built, as upstream's do.
- A SIGINT or SIGTERM while `ask` loads or refreshes the ChatGPT login, during preparation or before a Codex request, stops the wait for the credential lock, and no refresh starts once the signal has been noticed. A refresh already sent gets up to 2 seconds to answer, so rotated tokens can still be saved, and `ask` then exits by the first signal it received, even if preparation failed at the same moment. Upstream lets the refresh run to its 15-second timeout and then re-delivers the first signal. A refresh still unanswered after 2 seconds is abandoned, so if the server rotated the refresh token anyway, the next run asks for a new sign-in.
- A Codex reasoning item can arrive more than once in a stream: in `response.output_item.done` and again in the `response.completed` output. The live OpenAI Responses API encrypts `encrypted_content` afresh each time it emits an item, so the copies carry different ciphertexts. oh-fx accepts a later copy when every field other than `encrypted_content` matches the first completed copy, and replays the first copy that carries a non-empty ciphertext; an empty `encrypted_content` counts as none. A copy that differs in any other field fails as `ResponsesReasoningConflict`, whether or not either copy carries a ciphertext. The comparison uses a digest of the first copy's other fields, with object keys in sorted order, so it costs what the later copy costs to read and keeps 32 bytes per item. The first copy is kept because its bytes already count toward the provider-state limit, because replay then does not depend on whether the terminal event repeats the output, and because the ciphertext is opaque to oh-fx, so a later copy cannot be shown to be better. Upstream compares copies byte for byte, so a stream that re-encrypts, as the live Responses API does in every response that carries reasoning, fails there; it also accepts a copy without ciphertext whatever its other fields say. Whether chatgpt.com's Codex endpoint re-encrypts the same way could not be checked from the network these changes were tested on.
- Codex requests omit the `session-id` and `x-client-request-id` headers, as upstream does with `--no-save`, until sessions land. A request with the same messages, tools, reasoning effort, and Fast mode matches upstream's body byte for byte.
- `ask` loads the Codex model catalog only when a reasoning effort other than `auto` or Fast mode is requested, since the effort and Fast mode are the only things oh-fx reads from it during a run. Upstream loads it at the start of every Codex run, because compaction sizes the conversation from the model's context window; oh-fx has no compaction yet, so a run without either setting makes no catalog or Codex release lookup.
- The Codex model catalog does not have to list `gpt-5.6-luna`. Upstream rejects a catalog without its permission reviewer and session title model as malformed, which broke its sign-in for two days when OpenAI retired the previous reviewer model; oh-fx has neither feature yet, so nothing uses that model.
- The Codex client version that model catalog requests send is cached in `$XDG_CACHE_HOME/oh-fx/provider-versions/codex.json` instead of `~/.fx/provider-versions/codex.json`. A cache file that group or others can access is ignored and looked up again, where upstream reads it.
- `oh-fx models` prints each Codex model id through terminal-safe encoding, so control characters or bidi overrides in a catalog response cannot reach the terminal; `--json` keeps the ids as sent. Upstream prints them as received.
- The settings writer follows upstream's settings store in `$XDG_CONFIG_HOME/oh-fx`, with backups in its `backups` folder, but it drops a leading UTF-8 byte order mark instead of refusing the file, and before it writes it checks only the top-level settings oh-fx reads, plus upstream's rule that `models` keys are spelled in lower case. Upstream checks every top-level setting it knows, so a file that oh-fx reads can be one upstream refuses to rewrite. It also refuses to rewrite a file holding a number it would write back with a different decimal value, such as an integer outside the 64-bit range or `9007199254740993.0`, since it rewrites numbers through 64-bit floats; upstream copies every number as written. When the previous file's backup cannot be written, the save fails and the file is left as it was, where upstream logs the failure and replaces the file without a backup. Pruning old backups never removes the one the save just wrote, and once backup sequence numbers run out a save still writes its backup, where upstream skips the backup. Copies of a corrupt file stay best effort, as upstream. Like upstream, the writer refuses a `settings.json` or profile folder that is a symbolic link or has a second hard link, although oh-fx's settings reader follows a symbolic link.

## Parity tracking

[Upstream parity](upstream-parity.md) records the upstream commit oh-fx is synced to, where each upstream pull request since the previous sync point lands in oh-fx, and how to run the next parity pass. `parity/` will separately map every upstream source file to its Rust module, with a per-file status of `todo`, `partial`, `ported`, or `not-applicable`. CI will fail when an upstream file has no entry. Goldens dumped from upstream (tool schemas, help text, prompts) will be compared byte for byte.

## Delivery order

Crates land in the order they are wired into the binary.

1. Tooling, CI, releases, and self-upgrade.
2. A tracer bullet: contracts, provider connections with headers, the chat-completions transport, the agent loop, and `oh-fx ask`.
3. The command spec table replaces the binary's argument parser.
4. File tools, wired into `ask`.
5. The TUI: terminal input, the composer, markdown, and the simple renderer.
6. Permissions with the write tools and approvals, then the shell tool with `ofx-exec`.
7. MCP, skills, subagents, web tools, the Vercel AI Gateway protocol, menus, and the ported renderer.
8. ACP and subscription logins.
