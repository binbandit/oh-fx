# Architecture

oh-fx is a behavior-faithful Rust port of [vercel-labs/fx](https://github.com/vercel-labs/fx). Upstream behavior is the specification: tool schemas, prompts, help text, and terminal output match upstream unless this document records a deliberate difference.

## Goals

- **A complete port.** Every upstream feature is ported. A feature is left out only for a concrete reason recorded under deliberate differences, such as the Slack app, which depends on credentials that belong to Vercel. Being hard to port is not a reason.
- **Upstream's footprint.** oh-fx is as fast, as small, and as frugal as upstream. Its release builds are held to upstream's on binary size, startup time, time to first request, memory use, and rendering cost, and a change that regresses any of them needs a stated reason.

## Principles

- **Port leaf behavior, not upstream coupling.** Escape parsing, markdown, syntax highlighting, glob matching, git-backed file listing, the frame renderer, and MCP transports are ported from upstream, and their upstream tests become ours. Upstream's large shared structs (`DispatchContext`, `AgentRuntimeDeps`) are replaced by narrow traits and constructor injection.
- **Contracts first.** The agent and the TUI depend only on `ofx-contract`, so they can be built and tested with fakes while transports and tools land in parallel.
- **Module names follow upstream files.** A Rust module that ports `src/core/tooling/tool_dispatch.zig` is named `tool_dispatch.rs`, which keeps the parity ledger mechanical.
- **Every boundary is a compile-time fact.** Crates are layered and acyclic. The UI cannot reach sessions or config, and transports cannot reach product state.

## Type ownership

- A type lives in the crate that ports the upstream file defining it. `core/shared/types` and the tool dispatch contract map to `ofx-contract`, so `PermissionMode`, `ReasoningEffort`, `ApprovalPolicy`, tool metadata, and tool result errors live there. `ProviderId` and context limits live in `ofx-config`, session ids in `ofx-session`, and shell command analysis in `ofx-shell`. The targets a tool call acts on (`ApplicableTarget`, `TargetKind`) live in `ofx-contract` with the tool and permission traits that report them; the project context provider, its result, and the delivery state live in `ofx-agent` beside `RuntimeContext`, since only the agent drives them.
- A crate that needs another crate's type depends on its owner and never keeps a copy. `ofx-cli` validates provider ids, session ids, and login providers by calling their owners while parsing, as upstream does.
- Public items need a consumer outside their crate. A crate lands with its first consumer, or directly before it in the same stack of pull requests. A type moves to its owner in the pull request that adds its first outside consumer.

## Key decisions

| Concern | Decision | Reason |
|---|---|---|
| Async | tokio for the agent, transports, MCP, and processes; no runtime on fast paths such as `--version` | Cancellation of in-flight streams and process trees |
| UI thread | A plain OS thread polling the tty, a wake pipe, and a signal pipe | Rendering never competes with tool tasks, and it mirrors upstream's event loop |
| Agent and UI contract | `UiEvent` and `UiCommand` data, which gain serialization with their first wire consumer (ACP or a JSON event stream). Approvals and questions are correlated by `RequestId` through a map of pending oneshots | One event stream drives the TUI, `ask --json`, ACP, and test fixtures |
| HTTP and TLS | reqwest with rustls and the ring provider. On Linux, a verifier of our own reads one CA bundle, or `SSL_CERT_FILE` and `SSL_CERT_DIR`, on the first TLS handshake and adds a connection's `tls.ca_file`; macOS and Windows use rustls-platform-verifier with extra roots from `SSL_CERT_FILE` or `tls.ca_file` | Corporate CAs and proxies work, static musl builds need no cmake, and neither startup nor plain HTTP pays for parsing the system's roots |
| CLI | A static command spec table ported from upstream, scanned the way upstream scans arguments: no flag clustering, and values may start with `-` | One source for `--help`, `/help`, and the slash menus, with upstream's exact acceptance rules |
| Terminal | rustix plus a port of upstream's escape parser | Upstream needs OSC 11, DSR, and DA1 replies that crossterm drops |
| Renderer | A `FrameSink` seam. A simple live-region renderer ships first; upstream's frame engine replaces it | Resize and tmux parity with upstream's resize tests, without blocking the first release |
| Markdown | Port upstream's streaming processor and profile tokenizer | Linear cost per delta, identical output, and no grammar data in the binary |
| Files and grep | `git ls-files`, `git grep -F`, a `memmem` fallback walk, and upstream's glob matcher | Tool descriptions promise literal matching and git semantics |
| MCP | Hand-written transports on `ofx-jsonrpc` and `ofx-http` behind an `McpTransport` trait | Upstream speaks legacy SSE and several protocol versions, and rmcp changed major versions three times in 2026 |
| Errors | `thiserror` in libraries; `anyhow` only in `ofx-app` and the binary. Upstream error names stay visible to the model | Tool results expose error names upstream already uses |
| Panics | `panic = "unwind"`. The agent contains every panic that unwinds out of tool code. One while preparing, describing, inspecting the file mutation of, or executing a call becomes that call's tool error, with all of `execute` running inside the call's tokio task, and one while dropping a call that never ran is discarded. Only the terminal owner restores the terminal, and only on fatal paths: a panic on the UI or main thread, or process exit | A bug in one tool becomes a tool error instead of ending a work session, and a contained panic never disturbs a live UI |
| Lints | Workspace clippy `pedantic`, `unreachable_pub`, `unwrap_used`, no `unsafe`, no comments | Code explains itself, and dead code stays visible to the compiler |

## Naming and paths

- Binary `oh-fx`, with an `ofx` symlink installed next to it.
- Environment variables use the `OH_FX_` prefix in place of upstream's `FX_`.
- Settings live in `$XDG_CONFIG_HOME/oh-fx` (default `~/.config/oh-fx`), sessions and credentials in `$XDG_DATA_HOME/oh-fx`, logs and upgrade state in `$XDG_STATE_HOME/oh-fx`, and caches in `$XDG_CACHE_HOME/oh-fx`, on Linux and macOS alike.
- Project configuration is `.oh-fx.json`, and project skills live in `.oh-fx/skills`.

## Deliberate differences from upstream

- Custom provider connections accept `headers` with `${VAR}` interpolation, `tls.ca_file`, `proxy`, a `models` list, `max_tokens_parameter` (`max_completion_tokens` for reasoning models and Azure OpenAI), plain `http://` base URLs on any host, and host names with `_`, so self-hosted gateways such as Portkey work. Settings files may start with a UTF-8 byte order mark.
- The chat-completions stream parser tolerates gateway dialects that upstream rejects: empty-choices chunks, a stream that ends after its finish chunk without `[DONE]`, repeated finish chunks, mismatched usage totals, provider-native finish reasons, `stop` after tool calls, tool call deltas without an `index` or with empty ids or repeated names, and finish chunks without a `delta`. A repeated name that could also extend to another advertised tool fails as `InvalidToolName`, where upstream appends it. `{"object": "error"}` chunks and a `finish_reason` of `error` fail as provider errors, and a response that is not `text/event-stream` fails with its JSON error or `UnexpectedContentType` instead of a parse error.
- Provider connections never follow redirects. A 3xx answer names the redirect target's host and explains that `base_url` must point at the gateway API, so a sign-in page never receives the request or its headers.
- An HTTP 404 keeps its real status in the error line, and protocol, transport, and stream failures print a second `oh-fx ask:` line with a masked, terminal-safe detail; a 401 adds the gateway's own explanation. Upstream prints only the error name.
- Stream and response body failure details carry structural facts, never the provider's raw bytes: a rejected stream event is named by its position and size (and, for Codex, a validated event type), an incomplete stream by its event and byte counts, a response that is not `text/event-stream` by its media type and size, and an error body whose read fails partway, which fails as `ReadFailed` as upstream does, by its status, read error, and bytes received. Provider error objects are parsed, re-serialized, and masked before they are shown.
- An HTTP error body without an `error` object but with a non-blank top-level `message` or `detail` string, such as chatgpt.com's `{"detail":"The 'gpt-5.4' model is not supported when using Codex with a ChatGPT account."}`, is shown as `API request failed · HTTP 400 · <text>`, masked and made terminal-safe like an error object's message. Upstream shows such bodies raw, as `HTTP 400: {"detail":...}`. Bodies whose `detail` is not a string, such as validation error lists, still print raw after masking.
- An error response whose body read fails partway or times out keeps its `Retry-After` on the `ReadFailed` or `Timeout` error, so the retry waits as long as the gateway asked. Upstream drops the delay with the body and retries on its default backoff.
- Configured secrets are masked in every provider detail, including forms hidden behind JSON string escapes (`\uXXXX` and surrogate pairs too) or percent-encoding, alone, mixed, or layered, such as `%5Cu0070`: the bearer token, proxy credentials, every substituted value of a header whose name looks sensitive, and other substituted values of at least 8 bytes. A secret that itself contains escapes is also matched in each decoded form of at least 8 bytes. Decoding repeats until a round changes nothing, for at most sixteen rounds over at most 64 KiB, enough for any backslash run that fits; text that would still decode after that, or that is longer and contains any escape, is shown as `content withheld (N bytes)` instead. A bearer token longer than 16 KiB or with non-visible characters fails as `InvalidConfiguredProviderCredential` before any request. Whitespace-only header variables count as missing, and nested defaults are rejected.
- A model failure diagnostic, the text in retry notices and in Codex `response.failed` details, masks anything that looks like a credential across its whole text before it is cut to 256 bytes. Upstream cuts first, so a credential that crossed the cut could leave a prefix too short to be recognized and masked.
- Codex details follow the same rules. A rejected Codex stream event is reported as `stream event N (TYPE, B bytes) was rejected`, such as `stream event 35 (response.completed, 15517 bytes) was rejected`, where upstream reports only the error name. TYPE is the `type` the reducer read while parsing an event whose content it then rejected, shown only when it is 1 to 64 bytes of lowercase ASCII letters, digits, `.`, and `_` that secret masking and terminal-safe encoding leave unchanged. An event rejected by the event-count or byte limits is never parsed, so it, an event that is not valid JSON, and any other type are reported as `stream event N (B bytes) was rejected`. Failure codes and messages from `response.failed` and `error` events are masked with every token the request sent as well as the current one, and Codex HTTP error bodies take the same parse-then-redact path as custom connections.
- A Codex `error` event without a top-level `code` or `message` takes both from its nested `error` object, using the object's `type` when it has no `code`, so `{"type":"error","error":{"type":"server_error","code":null,"message":"..."}}` is retried as a server error and shows its message. Upstream reads only the top-level fields and reports such an event as a non-retryable `provider_error: Provider response failed`.
- Model retries stop after 10 attempts instead of continuing indefinitely, never start after text has streamed, and do not retry TLS or proxy tunnel failures.
- On Linux, TLS roots come from one CA bundle that is read when the first TLS handshake needs it, as upstream reads them with `std.crypto.Certificate.Bundle.rescan`, with these differences. `SSL_CERT_FILE` and `SSL_CERT_DIR` replace the bundle with the files and directories they name, as in rustls-native-certs and OpenSSL; upstream ignores both. The search tries Entware's `/opt/etc/ssl/certs/ca-certificates.crt` and OpenHarmony's `/etc/ssl/certs/cacert.pem` after upstream's six bundles, and the certificate directories are the ones rustls-native-certs read before, `/etc/ssl/certs`, `/etc/pki/tls/certs`, and `/etc/security/certificates`, where upstream reads Android's `/system/etc/security/cacerts` in place of the last, so no directory is trusted that oh-fx did not trust before. When a certificate fails verification against the bundle for any reason other than a name mismatch, oh-fx reads the certificate directories once and verifies again against the bundle and the directories together, the roots it trusted before, so a CA added to `/etc/ssl/certs` without regenerating the bundle is trusted, even when it replaces a bundled CA with the same name; upstream reads only the bundle. A connection's `tls.ca_file` adds to these roots. A failed load is kept for the rest of the run, fails each TLS request as `CertificateBundleLoadFailure`, upstream's name, with a second line naming the file, and is not retried. On macOS and Windows, oh-fx keeps rustls-platform-verifier and the system trust store.
- `oh-fx ask` reads the TLS roots on a background thread once its arguments and settings are valid and the connection, custom or Codex, uses `https://`, so the parsing overlaps name resolution, the TCP connection, and the start of the TLS handshake. Upstream reads them when its first request starts and opens a whole connection ahead of time only for the Vercel AI Gateway; oh-fx never connects early, so the HTTP client's proxy, `CONNECT`, and `NO_PROXY` handling always applies.
- `oh-fx ask ""` fails with `InvalidConversationEvent` before any request is sent.
- The turn context reads git facts from the repository that encloses the workspace, where upstream reads only `<workspace>/.git`, and reports a tracked file as dirty only when it is missing or its size differs from the index, never from its modification time alone.
- A streamed write to a closed or failing stdout cancels the request and ends `ask` with the failed write's name, such as `BrokenPipe` or `NoSpaceLeft`.
- Until sessions land, a tool result over 64 KiB is cut at upstream's `--no-save` truncation marker instead of being stored behind a `read_tool_result` handle, and `read_file` reports image files as binary content until tool image attachments land.
- Until upstream's ask presenter is ported, terminal-mode `ask` writes the turn to stdout as plain lines: assistant text as it streams, operational lines such as `Done.`, `[notice]` recovery lines, and tool progress lines. Consecutive lines of each of the last three kinds stay together, and exactly one blank line separates each such run from assistant text and from runs of another kind. Whitespace the model streams is written only once visible text follows it, so blank lines at either edge of a stretch of text merge into that separator, and the output ends with a single newline; whitespace at the very start of the output is kept. Upstream paints the same events on stdout as a styled transcript with a banner, the prompt, indented Markdown, and grouped tool rows. Blocked-action guidance and failure lines stay on stderr and start on a new line. Progress lines and blocked-action labels escape their control characters with terminal-safe encoding. The raw, quiet, and JSON modes print progress, operational lines, and notices on stderr, as upstream does.
- In the ask and auto permission modes, whether set in settings or for one request with `--auto`, a `read_file` call whose path, or a `glob_files` or `grep_files` call whose search root, resolves outside the workspace needs approval. Upstream reads and searches such paths without approval unless a configured `permission` rule asks for it. Until approval prompts, permission rules, and the auto-mode reviewer are ported, nothing can grant that approval, so `ask` handles the call as upstream does when no approval prompt is available: it prints the blocked-action guidance with upstream's ask-mode or auto-mode hint (which still name `--auto` and the interactive shell), records the call as an error, and fails with `NonInteractivePermissionRequired`. Full access, from settings, `--full-access`, or `--yolo`, reads and searches external paths. A call admitted only for the workspace resolves its path again when it runs and fails with `PathOutsideWorkspace` if the path has left the workspace since admission.
- A `read_file`, `glob_files`, or `grep_files` call outside the workspace that the user approves at the prompt, once or for the rest of the session, or that a remembered session grant admits, runs confined to the directory tree the approval covers: the target itself when it is a directory, otherwise its parent. A prompted call's tree is resolved once, before the request reaches the host, and both the approved call and an `Always` grant are bound to that tree, so a symlink swapped while the prompt is open moves neither of them. The call resolves its path again when it runs and fails with `PathOutsideWorkspace` if the path no longer lies inside that tree, the same check a call admitted only for the workspace makes against the workspace root. Upstream runs such a call, whether approved at the prompt or admitted through `sessionGrantAllowed`, with ordinary authority, so the tool reads whatever its path resolves to at that moment, and a symlink swapped after the user answered lets an approval given for one directory read another one without asking. The approval is consent for its tree only, so oh-fx does not follow the path out of it. Full access is unchanged, and `write_file` and `edit_file` need no extra check, because their execution already requires the exact target and identities recorded at admission, as upstream does.
- An `ApprovalRequested` event carries what the host needs to show exactly what it approves, which upstream's permission request does not always name. Its `title` is the call's progress title where upstream shows a permission label. `tool_arguments_preview` is the call's arguments made terminal-safe and cut at 4 KiB, upstream's `max_tool_arguments_preview_bytes`, for every tool, where upstream fills it only for dynamic MCP tools. `scope` is what the gate resolved before asking: the canonical path a `read_file`, `glob_files`, or `grep_files` call reads or searches and the tree the call stays confined to, which upstream does not show, and in `always` the session grant an `Always` answer records. `file` names a file change's target and state until upstream's diff preview is ported. For `shell`, `command` holds the full command text with its resolved `cwd`, its profile, `user` when the call names none, whether it wants a terminal, and the shell a terminal run names, or the full input `interact` would send; upstream puts the command and profile behind a `# shell.run profile=…` header, does not name the working directory, and leaves `interact` input out of its request. Command text, the named shell, input, `scope.target`, `file.target`, and the paths and command in `scope.always` are raw, and a file name can hold terminal escapes, so a host makes all of them terminal-safe before showing them. Upstream's auto-mode `explanation` has no counterpart until the reviewer is ported.
- The gate settles what an `Always` answer grants before the request reaches the host, and `scope.always` carries it, as upstream's file grant offer does; the host shows it on the `Always` choice and offers no `Always` when it is `None`. A change inside the workspace offers `WorkspaceFiles`, upstream's workspace file access: changes, reads, and searches anywhere in the workspace, `.git` included. A change outside it offers `FileChangesUnder` the nearest existing directory above the target, as upstream normalizes its target and parent grants, so a new file at `/new.txt` offers `/` and one at `~/x` offers the home directory. A `read_file`, `glob_files`, or `grep_files` call outside the workspace offers reads, name searches, or content searches under the tree it is confined to, and a `shell` run offers its exact command. `interact` and `stop` offer nothing, and neither does a call whose target no longer resolves when the request is built, which runs confined to the workspace if approved, or a `shell` run whose `cwd` is not an existing directory, which fails when it runs. Upstream fails that run before asking; here it asks first, so the absence of an external directory stays behind approval like the rest of an external path, and a grant that would admit the command in any directory is not offered for a run that cannot start. Upstream shows its second choice on every prompt and, for every call but a file change, records a grant it works out from the call after the answer, so it also remembers `interact`, `stop`, and a call whose target vanished. oh-fx offers `Always` only when it can name the grant before asking: a grant worked out after the answer can differ from the one the user saw, and `interact` and `stop` carry no target a grant could be bound to. The agent records exactly the offer it showed, so a target that becomes a directory or a symlink swapped while the prompt is open cannot change the grant, and an `Always` answer to a request without an offer approves only that call. Upstream fails a file change whose offer it cannot represent safely, such as a tree whose path holds `*` or `?`, which its grant patterns would read as wildcards; grants here are literal paths, and every canonical file target has an existing directory above it, so neither case arises.
- A remembered command admits the same command text with the same profile, terminal mode, and named shell, so `profile: user`, which runs the login and interactive startup files, asks again after `Always` on `profile: clean`, as upstream binds a command grant to its shell environment and terminal mode. A terminal run's `shell` names an executable the call chooses, so its path is part of the request and the grant, and its `clean_start` sets the profile, as upstream's terminal identity binds it. Every other run uses the account's login shell. Upstream binds that path too; oh-fx leaves it out, because it reads the path from the account database for every call and no call argument can change it. As upstream, the grant ignores the working directory: a remembered command runs in any `cwd`, including one outside the workspace, though the request names the `cwd` it was approved in.
- An answer the host delivers is never dropped. If the turn is cancelled as the answer arrives, an `Always` grant is still recorded and the call does not start, and once the agent has withdrawn a cancelled request, resolving it returns `false`. `Agent::clear_history` also forgets every session grant, as upstream clears its permission engine when it resets a session; `PermissionGate::forget_approvals` has no default, so a gate that wraps another must decide what clearing does. `AgentSetup` gives every agent it builds the same `PermissionPolicy`, so session grants, and clearing them, belong to the process rather than to one agent; a process runs one agent today.
- `write_file` and `edit_file` are admitted as upstream admits them when no `permission` rule, session grant, or approval prompt applies: in ask mode every change needs approval, so `ask` prints the blocked-action guidance and fails with `NonInteractivePermissionRequired`; auto mode allows changes inside the workspace and new files anywhere unless their path is sensitive; a write that would leave an existing workspace file unchanged needs no approval; full access allows everything. Configured `permission` rules are not applied yet. In auto mode, a change that upstream hands to its safety reviewer model, an existing file outside the workspace or a sensitive path, is held instead: oh-fx has no reviewer yet, so the model receives upstream's `tool_review_held` result with `review_cause` `reviewer_unconfigured` and the turn continues. Upstream reviews such a change with the provider's reviewer model, which every upstream provider configures, and holds it the same way only when no reviewer is configured.
- A `write_file` or `edit_file` target outside the workspace is not read before the call is admitted, in keeping with the approval external reads need. In ask and auto mode such a call therefore needs approval or is held even when it would change nothing or its `old_string` is missing, where upstream first reports `No changes to …` or the edit failure. With full access every target is read when the call runs, as upstream does: its path must still resolve to the same target, and those outcomes are reported then. In ask and auto mode workspace targets are read before admission, as upstream reads them.
- Auto mode sends a file change to review when its target path contains a `.git` component or `.ssh/authorized_keys`, `.ssh/config`, `.ssh/rc`, `Library/LaunchAgents`, `Library/LaunchDaemons`, `.config/autostart`, `.config/environment.d`, `.config/systemd/user`, `.local/share/systemd/user`, `.config/fish/config.fish`, `.config/fish/conf.d`, `.config/git/config`, `.gitconfig`, a zsh startup file (`.zshrc`, `.zshenv`, `.zprofile`, `.zlogin`, `.zlogout`), a bash startup file (`.bashrc`, `.bash_profile`, `.bash_login`, `.bash_logout`, `.bash_aliases`), `.profile`, or `.pam_environment`. Names are compared after Unicode case mapping, with zero-width and bidi format characters removed, so a spelling that a case-insensitive filesystem opens as a protected name, such as `.GIT`, `.ssh` written with U+017F LATIN SMALL LETTER LONG S, or `authorized_keys` written with U+212A KELVIN SIGN, is also reviewed. Upstream matches a shorter list byte for byte, with `.git/hooks`, `.git/config`, and `.git/config.worktree` in place of any `.git` component, so a new `.GIT/hooks/pre-commit` on a case-insensitive filesystem, a submodule's `.git/modules/<name>/hooks`, or a new `~/.zshenv` skips review there.
- `write_file` and `edit_file` open the target's anchor directory and every parent without following a symlink in any component, as `read_file` does, before checking the identities recorded at admission. Upstream opens the anchor by its absolute path, following symlinks above it. On macOS each of those directories must also be readable. A new file is put in place only if nothing has appeared at its path: through an exclusive rename, or, where the filesystem has none, a hard link that fails when the path exists, and the write fails where neither is available. A file that appears in that moment fails the write with the stale-preview message, where upstream replaces it. If the staged file's name cannot be removed after such a link, the success result names it. Before `write_file` reports `No changes to …`, it checks again that the parent directories, the file, and its content are the ones it read when the call was prepared. It fails with the stale-preview or changed-traversal message if any of them changed, and with `file mutation failed before commit` if the file can no longer be read. Upstream reports the content it read earlier. The diff preview upstream builds for its approval prompt is not built until approval prompts land.
- In auto mode, `shell` runs a command without approval when each of its `&&` stages is one of upstream's known reversible commands, such as `git status`, `git fetch`, `which`, `npm install`, `npm run <script>`, and `zig build`, and observes a session with `interact` without approval, as upstream does. oh-fx admits fewer commands: `git fetch` only with flags that cannot run a program or rewrite local refs and with no `+` refspec or `::` transport, `npm`, `pnpm`, `yarn`, `bun`, and `zig build` only with flags known to be inert before `--`, and no word that contains `^`, `#`, or `!` or starts with `=`, which a user's zsh options can expand into file names. Upstream also admits flags such as `git fetch --upload-pack=<program>` and `npm install --script-shell=<program>`. Only an unquoted, unescaped `&&` separates stages, so a quoted or escaped `&&` stays an argument of the command around it and that command's flags are still checked; upstream splits on it too. A reversible command whose `cwd` resolves outside the workspace needs review here, in keeping with the approval external reads need; upstream runs it. Upstream loads it at the start of every Codex run, because compaction sizes the conversation from the model's context window; oh-fx has no compaction yet, so a run without either setting makes no catalog or Codex release lookup.
- The Codex model catalog does not have to list `gpt-5.6-luna`. Upstream rejects a catalog without its permission reviewer and session title model as malformed, which broke its sign-in for two days when OpenAI retired the previous reviewer model; oh-fx has neither feature yet, so nothing uses that model.
- The Codex client version that model catalog requests send is cached in `$XDG_CACHE_HOME/oh-fx/provider-versions/codex.json` instead of `~/.fx/provider-versions/codex.json`. A cache file that group or others can access is ignored and looked up again, where upstream reads it.
- `oh-fx models` prints each Codex model id through terminal-safe encoding, so control characters or bidi overrides in a catalog response cannot reach the terminal; `--json` keeps the ids as sent. Upstream prints them as received.
- The settings writer follows upstream's settings store in `$XDG_CONFIG_HOME/oh-fx`, with backups in its `backups` folder, but it drops a leading UTF-8 byte order mark instead of refusing the file, and before it writes it checks only the top-level settings oh-fx reads, plus upstream's rule that `models` keys are spelled in lower case. Upstream checks every top-level setting it knows, so a file that oh-fx reads can be one upstream refuses to rewrite. It also refuses to rewrite a file holding a number it would write back with a different decimal value, such as an integer outside the 64-bit range or `9007199254740993.0`, since it rewrites numbers through 64-bit floats; upstream copies every number as written. When the previous file's backup cannot be written, the save fails and the file is left as it was, where upstream logs the failure and replaces the file without a backup. Pruning old backups never removes the one the save just wrote, and once backup sequence numbers run out a save still writes its backup, where upstream skips the backup. Copies of a corrupt file stay best effort, as upstream. Like upstream, the writer refuses a `settings.json` or profile folder that is a symbolic link or has a second hard link, although oh-fx's settings reader follows a symbolic link.
- When a panic unwinds through the terminal owner, a startup step fails after raw mode, or a SIGTERM or SIGHUP ends the interactive session, oh-fx restores termios at once with TCSANOW instead of after queued output drains, writes the abnormal restore sequence within a 100 ms deadline, and then discards input it has not read. The deadline covers only that write, and the next item describes where a blocking descriptor can still hold it. Rust's default panic hook writes the panic report to stderr before the unwind reaches the terminal owner, so when stderr is a terminal that has stopped reading, the panic waits in that write with termios still raw, as upstream's panic handler also writes its report first. The sequence ends synchronized output, turns off mouse tracking and focus reports, and leaves the alternate screen, in the order upstream's own alternate screen exit uses, then turns off the modes that oh-fx's inline session sets and that would break the shell: the kitty keyboard flags, which kitty keeps for each screen and so are popped only once the main screen is back, modifyOtherKeys, bracketed paste, theme notifications, the hidden cursor, and disabled autowrap. The keypad, insert, origin, and attribute resets come last. oh-fx does not yet set mouse tracking, focus reports, the alternate screen, or the keypad, insert, and origin modes; those resets match upstream's restore. Each escape sequence goes out in its own write, so a terminal that reads only part of the restore before the deadline gets those modes back first and is left between two sequences, unless its kernel splits a write of a few bytes. Upstream writes its sequences in one write, with the keyboard modes last. Discarding unread input, as the TCSAFLUSH of a normal exit does, keeps the shell from running a command typed for the session. It comes after the restore sequence is written, so it also drops keys typed while the sequence waits for the terminal, which still arrive in the kitty encoding until the keyboard flags are popped, and probe replies that arrive late. Upstream's panics abort without restoring the terminal, and its signal handler writes the sequence with one blocking write and leaves termios as it is, so after either the shell reads that input. A normal exit and a suspend wait for queued output before restoring termios, as upstream does.
- The interactive terminal writes through a nonblocking descriptor of its own. oh-fx reopens the terminal's path for it, or opens `/dev/tty` when the path cannot be opened and the terminal is the session's controlling terminal, and uses neither when poll reports it invalid, as macOS can for `/dev/tty`. On that descriptor a SIGTERM or SIGHUP ends a rendering write to a terminal that has stopped reading at once, and the restore that follows waits for room before each escape sequence and gives up when the 100 ms deadline passes. When neither works, as under `su <user> -c oh-fx`, which starts a session without a controlling terminal on a terminal that belongs to another user, oh-fx writes through a blocking duplicate of stdout, as upstream always does. On that descriptor a terminal that stops reading holds every rendering write until it reads again, and a SIGTERM or SIGHUP cannot end the write, as upstream. The abnormal restore still waits up to its deadline for the terminal to report room before each escape sequence and then writes that sequence with a blocking write, so it gives up after 100 ms on a terminal that has stopped reading. If something else writes to the terminal between that check and the write and fills its queue again, the write blocks until the terminal reads, as upstream's one blocking restore write does. If poll reports stdout itself invalid, the restore writes nothing rather than risk a blocking write it cannot bound.
- A bracketed paste settles only once the theme monitor has classified every byte that followed its end marker. When a read ends partway through what could be a terminal reply, such as `ESC [`, settlement waits for the next read or for the monitor's 75 ms idle timeout: a completed reply is filtered out and the paste is accepted, and anything else is a trailing suffix that rejects the paste, as a suffix that reaches the paste directly does. Upstream settles at the end of the read, so the rest of a split key sequence, such as `13u` or `A`, is then handled as Enter or Up.
- Terminal input zeroes each byte in its read queues and in the theme monitor's reply buffers as it consumes it, and wipes both when it is dropped, so no copy of an authorization code paste stays behind in them. Upstream reads into a reused stack buffer, leaves its reply buffers as they are, and zeroes only the paste capture.

## Parity tracking

[Upstream parity](upstream-parity.md) records the upstream commit oh-fx is synced to, where each upstream pull request since the previous sync point lands in oh-fx, and how to run the next parity pass. `parity/` will separately map every upstream source file to its Rust module, with a per-file status of `todo`, `partial`, `ported`, or `not-applicable`. CI will fail when an upstream file has no entry. Goldens dumped from upstream (tool schemas, help text, prompts) will be compared byte for byte.

## Delivery order

Crates land in the order they are wired into the binary.

1. Tooling, CI, releases, and self-upgrade.
2. A tracer bullet: contracts, provider connections with headers, the chat-completions transport, the agent loop, and `oh-fx ask`.
3. The command spec table replaces the binary's argument parser.
4. File tools, wired into `ask`.
5. The TUI: terminal input, the composer, markdown, and the simple renderer.
6. Permissions with the write tools and approvals, then the shell tool with `ofx-exec`.
7. MCP, skills, subagents, web tools, the Vercel AI Gateway protocol, menus, and the ported renderer.
8. ACP and subscription logins.
