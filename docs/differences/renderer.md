# Interactive renderer

- `/stats` prints upstream's renderer counters, measured on oh-fx's live-region renderer: `ansi_bytes` counts the frame bytes written to the terminal, `redraws` counts full-screen replays after a resize, a theme change, or a resume, and `debounced_resizes` counts each settled resize. `footer_updates` and `stream_chunks` stay 0, as upstream never counts them. Upstream's completion text calls the command token and turn statistics; its output is these counters.
- A resize, like upstream's, draws nothing until 100 ms have passed without another resize signal, and then clears the screen and scrollback inside the synchronized update and replays the transcript at the new size once, even when the size ends where it started or a theme change or resume asked for a replay meanwhile. Upstream also draws a frame at the new size after each signal while the size is still changing, placed by a cursor position probe, and replays only once the size settles; oh-fx shows the terminal's own reflow of the last frame until then, because those frames need upstream's frame engine. A replay, like upstream's, rewrites at most the last 256 KiB of the rendered transcript, cut at a row, so scrollback it clears loses what came before that; streamed output and a resumed session's history still reach the terminal whole. oh-fx still keeps every transcript entry and renders all of them for a replay, where upstream also drops the oldest entries past 1 MiB of retained text.
- Outside tmux the interactive session checks, as upstream does, whether the screen was cleared behind its back, by Cmd-K in iTerm2 or Terminal.app or by another process writing to the terminal. On a printable key, once a frame with the composer cursor is on screen and no approval, question, paste, partial key sequence, or resize is pending, it holds that key and the input after it, writes `\x1b[?2026h\x1b7\x1b[1G\x1b[6n\x1b[2G\x1b[6n\x1b8\x1b[?2026l`, and draws no frame, sends no theme query, and settles no resize until the terminal answers with the pair of cursor position reports at columns 1 and 2. A reply on a row other than the composer cursor's starts a fresh screen as Ctrl+L does, and then the held input is handled. Input that arrives during a probe does not start another, so one probe covers the keys typed within a round trip of the first, and the next printable key after it probes again. Cursor position reports outside that pair, such as Shift+F3 (`\x1b[1;2R`), stay input. No answer within 100 ms of the last byte read, more than 4 KiB of held input, or a failed write ends the probe and turns it off for the session, and a reply pair that arrives in the following 100 ms, or before a paste that began meanwhile has ended, is discarded, including from inside the paste: the pasted text keeps none of its bytes, and a pair right after the paste's end does not reject the paste as trailing input. A partial pair after the paste's end holds the paste until it completes, or until 100 ms pass without input, when the paste is rejected as trailing input, as any other suffix would be. Upstream hands the paste every byte it reads, so such a pair lands in the composer or rejects the paste. A reply that a resize may have moved, because a resize signal arrived or the terminal's size changed while the probe waited, starts no fresh screen; the resize's replay redraws the transcript instead. Upstream compares that reply too, so a resize that moves the cursor during its probe starts a fresh screen and drops the transcript. When held input passes 4 KiB, oh-fx hands it on in the order it arrived, where upstream hands on an unfinished report-shaped sequence at its end before the keys read just ahead of it. When the terminal takes none of the query at once, as one that has stopped reading output, oh-fx handles the key without a probe and probes again on the next one; upstream waits until it can write the query, and its keys wait with it.
- The interactive session picks its palette as upstream does: a non-empty `OH_FX_THEME` (upstream's `FX_THEME`) wins over the `theme` user setting, and `light` or `dark`, in any letter case, pins that palette, skips the background colour probe and the theme change notifications, and colours the diff markers; otherwise the terminal's background colour, then `COLORFGBG`, decides. Upstream also reads any other name as a theme file, `~/.fx/themes/<name>.json` in its own or the VS Code format with `-light` and `-dark` variants; oh-fx does not load theme files yet, so another name is detected as if none were set. The setting is read from the user settings, with workspace overrides, and ignored in a project's `.oh-fx.json`, as upstream ignores it there.
- Model names, notice bodies, and hyperlink targets are escaped as they enter a terminal row, so control sequences, line and paragraph separators, and bidi embedding, override, and isolate controls in them stay inert and visible, as assistant text already escapes them. Upstream writes them to the terminal as given. The approval panel escapes every string from the request with upstream's full terminal-safe encoding, which also makes zero-width and other invisible characters visible. It then also writes as `\u{…}` every code point, outside an RGI emoji sequence such as a keycap, a flag, or a skin-tone sequence, that takes no cells, is an emoji modifier or a variation selector, is unassigned, or takes a different number of cells in oh-fx's table than in `unicode-width`, so a command, path, or arguments preview measures the same in every terminal and its end cannot be pushed off screen. A text-default symbol followed by U+FE0F, such as `❤\u{fe0f}`, is shown that way too, because terminals draw it as one cell or two. Upstream shows these characters as given.
