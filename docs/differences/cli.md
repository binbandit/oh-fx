# Command line and help

- The top-level help links to the oh-fx repository instead of fx.sh/docs.
- oh-fx has no `slack` command (`slack install`, `slack status`, and `slack refresh`) and no one-command Slack MCP preset (`mcp add slack`, added upstream in vercel-labs/fx#1101). Both depend on fx's own Slack app, whose public Client ID and fx.sh OAuth bridge belong to Vercel, so they are omitted until oh-fx has a Slack app of its own. `oh-fx slack` fails as any unknown command does, and `oh-fx mcp add slack` keeps the usage error that upstream printed before the preset. Without the `slack` row, the top-level help's command column is one character narrower than upstream's, because `slack <install|status|refresh>` was its widest usage. Once MCP support lands, a user with their own Slack app can still add Slack's MCP server with `oh-fx mcp add --transport http slack https://mcp.slack.com/mcp` and set `oauth.client_id`, `oauth.client_secret_env`, and `oauth.callback_port` for it in the profile MCP configuration, as upstream allows: upstream authorizes any Slack Client ID other than fx's through its ordinary callback at `http://localhost:<callback_port>/callback`, and Slack offers no dynamic client registration, so the Client ID is required. Those fields alone are not enough: [Slack's MCP server documentation](https://docs.slack.dev/ai/slack-mcp-server/) limits it to internal apps and apps published in Slack's directory, and the app must also list that callback as an OAuth redirect URL and request the user scopes the MCP tools need.
- Top-level help narrower than its two-column layout needs (under 53 columns for commands and flags) puts each usage on its own line with the summary indented below, and stacks the resource links when their longest word does not fit beside the labels, so only unbreakable words overflow. Upstream keeps the two-column layout at every width.
- An unknown command is echoed through terminal-safe encoding capped at 160 bytes, so escape sequences, other control characters, and invalid UTF-8 print as escapes such as `\x1b` and `\xff`. Upstream writes the raw bytes to the terminal.
- A closed stdout cannot be detected: the Rust runtime reopens closed standard streams on `/dev/null` before `main` runs, so output is discarded where upstream reports `WriteFailed` or `NotOpenForWriting`. Full disks and closed pipes fail as upstream does.
- `oh-fx replay` renders a tape through `ofx-vt`, the port of upstream's terminal grid, and writes upstream's screen snapshots, frame headings, JSON summary, golden file, and frames directory byte for byte. Its messages say `oh-fx replay:` and keep upstream's 256- and 512-byte limits, which now include the longer prefix, so a path three bytes shorter than upstream's limit already falls back to the short message. A grid error, such as a tape with no columns or a synchronized update over 1 MiB, ends the replay with `oh-fx: <error>`. Replay writes no `debug_trace` lines, because oh-fx has no trace log yet, and a screen holding one of the characters whose width `ofx-text` corrects can differ from upstream's.
- Until their features land, commands and flags that oh-fx parses but cannot run fail with `oh-fx: <command> is not available yet` and exit status 1, where upstream runs them. Arguments are validated first, so malformed ones still fail with upstream's usage errors. With `--json`, such a command also prints `{"kind":"<command>","error":"<command> is not available yet","code":"NotAvailableYet"}` on stdout, and `ask --json` prints its JSON result with the error `NotAvailableYet`. This covers every command except `ask`, `pr`, `issue`, `upgrade`, `permissions`, `status`, `usage`, `doctor`, `sessions`, `session last`, `session <id>`, and `session migrate` (on the v1 store, and `session migrate` under `--sessions-v2` with upstream's refusal), `workspace`, `replay`, `help`, `--version`, `login codex`, `logout codex`, `login grok`, `logout grok`, `provider codex`, and `models` while Codex is the selected provider (so `login` and `logout` for Vercel, `provider` for the gateway, Grok, and custom connections, and `models` for the gateway, Grok, and custom connections are covered), the `--context-limit` launch modifier when it sets `image_adapter_output_bytes`, since `ask` and the interactive session have no image adapter for it to apply to (both apply every other limit from the command line), `--provider` on an interactive launch, and the `--sessions-v2` launch modifier on `ask` and on interactive launches. Commands that keep no sessions upstream, such as `upgrade`, `login codex`, `logout codex`, `help`, and `--version`, accept and ignore `--sessions-v2` as upstream does; `acp` and the other commands that use sessions upstream fail as not available yet with or without it.
- `oh-fx pr` and `oh-fx issue` draft a pull request or an issue as upstream does: they take upstream's git snapshot of the working directory, run `git --no-optional-locks` for the branch, the short status, the last five commits, and the staged and unstaged diff stats, and send upstream's drafting prompt, with any context words, to the model as an `ask` run saved to the session store, in auto mode with `--auto`. The draft is printed raw even on a terminal, as upstream prints it. `pr` outside a git repository fails with upstream's `oh-fx pr: requires running inside a git repository` before any request; `issue` drafts anywhere. With `--create` the draft runs quietly, as upstream's JSON capture runs it, and its final reply, never the text written before a tool call, is split into a title, without a leading heading marker or whole-line bold, and a body, then published with `gh pr create` or `gh issue create` in the working directory: `gh`'s trimmed answer, or `created successfully`, is printed, and its trimmed error, `gh command failed`, or `gh CLI not found in PATH` follows `oh-fx pr: ` or `oh-fx issue: ` on stderr with exit status 1. A reply without a title line and a body fails with upstream's `failed to parse drafted PR title/body` or `failed to parse drafted issue title/body` without running `gh`. A `gh` stopped by a signal counts as a failure; upstream reads an exit code it does not have. Like `ask`, they fail as not available yet under `--sessions-v2` or with an image `--context-limit`. Context words, git output, and `gh`'s answer that are not valid UTF-8 reach the prompt or the terminal with replacement characters, where upstream passes their bytes through.
- `oh-fx status` prints upstream's `[status]` lines and JSON without `update_channel`, `build_channel`, and `build_revision`, as `/status` does, and without `team`, since oh-fx has no Vercel AI Gateway connection. With the gateway or Grok selected it fails with the startup error that `ask` prints, as upstream's `status` does when startup cannot select a model, since oh-fx cannot run either provider yet. `connected_providers` lists the selected connection while its credential is available, Codex while a Codex login is saved, and Grok while a Grok login is saved; it never lists the gateway, which oh-fx holds no credentials for, and under `OH_FX_AUTH_MODE=host-managed` it lists only Codex, since oh-fx sends no Grok requests yet. A connection without a saved model reports the first model of its `models` list with `model_origin=default`, and the environment override is named `OH_FX_MODEL`. The Codex login is read without refreshing it, as upstream does, so an expired one shows `auth_expired=true`. The text lines encode the workspace path and the model through upstream's terminal-safe encoding, so a directory name with escape sequences or newlines cannot clear the screen or forge a line; upstream writes both raw. JSON keeps them as they are. `ultrafast_requested` is always `false`, since oh-fx reads neither upstream's `ultrafast_mode` setting nor its `FX_ULTRAFAST` override yet; Ultra mode is requested only for an interactive session, with `--ultrafast` or `/ultrafast`.
- `oh-fx usage` reports the `--period` window, 30 days unless `24h` or `7d` is given, with upstream's text and JSON from oh-fx's own profile usage ledger, as [usage](usage.md) records. It fails as upstream does: `oh-fx usage: HOME is not set`, `local usage storage is unsafe` for a data directory, ledger or lock with the wrong type, links or mode, and `local usage data is unavailable` otherwise, with the error's name as the `code` under `--json`.
- `oh-fx doctor` runs upstream's checks in upstream's order, with its text and JSON, and names oh-fx's files: `~/.config/oh-fx/settings.json`, `.oh-fx.json`, and `~/.config/oh-fx/mcp.json`, and the `sessions` directory under the data directory. After the state check it inspects up to 64 session folders, as upstream does, and reports each problem as a `session` check with upstream's recovery guidance: `canonical_state_invalid` (fail) for a session that does not load, `unsafe_path` (fail) for a session folder, or a `logs/commands`, `artifacts/browser`, `tool-results`, or `subagent` side folder, that is not a private folder of private regular files, and `authority_transition_pending` (warn) for a folder behind `authority.pending.json` or `commit.pending.json`, followed by a warning when more folders remain. The guidance names `oh-fx doctor`, `oh-fx session <id> --json`, and the sessions directory the state check prints, where upstream names `fx` and `~/.fx/sessions`. A session loads when its metadata, log, `usage-v2.json`, and recovery checkpoint read as `oh-fx session <id>` reads them, except that a log that is a symlink, a hard link, or not a regular file is reported as `unsafe_path`, as upstream's doctor reports it, where `oh-fx session <id>` answers `record not found` as upstream's detail does; upstream's read also checks the permission sidecar, which oh-fx does not read yet. Upstream also reports a `session.json` too large to read as `oversized_legacy_snapshot`, a legacy snapshot it can migrate; oh-fx reads no legacy snapshots and reports it as `canonical_state_invalid`. If the sessions directory itself cannot be listed, doctor leaves these checks out; upstream fails the whole doctor run. The other kinds upstream defines, such as projections, commit watermarks, log compaction, and cleanup candidates, are not reported by upstream's inspection at the synced commit either. With the gateway or Grok selected, the auth and startup checks fail with the "not available in oh-fx yet" error `ask` prints, and `model=` is empty. With settings that cannot be loaded, the auth check treats the gateway as selected, the startup check fails with upstream's `failed to resolve startup settings: <error>`, and `model=` is empty where upstream prints its compiled default gateway model, since oh-fx cannot run the gateway yet and has no default model of its own. Doctor never reports upstream's `team`, which only a Vercel sign-in provides, as in `status`. The workspace path and the model are terminal-safe in text, as in `status`. The auth check fails with the error `ask` reports when the selected connection cannot be resolved, such as a bearer token that is not visible ASCII or a header whose environment variable is unset, and the startup check fails with `InvalidProfileConfiguration` when the user settings are unusable, so doctor does not pass a profile that `ask` refuses; upstream's doctor reports both checks as ok.
- `oh-fx sessions` lists saved sessions with upstream's text and JSON, `--all`, `--limit`, `--cursor` paging, and its warning for unreadable sessions, and lists empty sessions as upstream does. It also lists the sessions fx saved, marked `fx`, as [sessions](sessions.md) records. `oh-fx session last` describes the newest session that listing shows for the workspace with upstream's text and JSON, and fails as upstream does when there is none: `no saved sessions for this workspace`, or `saved sessions are unreadable; run \`oh-fx doctor\` for recovery guidance` when the listing skipped unreadable sessions. Its text passes the session id and the stored language through the terminal-safe encoding `sessions` uses, so control characters, C1 controls, and bidirectional overrides in a stored language reach the terminal escaped; upstream writes them raw. The JSON keeps the stored values. `oh-fx session <id>` and `session --id <id>` show every turn the session saved, its compacted summaries in place, with upstream's text and JSON, and fail as upstream does: `record not found` for a missing or subagent session or one whose log cannot be read, `invalid session id`, `session <id> is corrupt; run \`oh-fx session recover <id>\``, which names a command that is not available yet, `session <id> uses an unsupported session version`, and `record is corrupt` for a recovery checkpoint or `usage-v2.json` that cannot be read. Upstream's read also checks the session's `permissions.json` and reports a corrupt one as `record is corrupt`; oh-fx does not read that file yet, as for its own sessions. The text output escapes what the session stored, as `session last` does: the id, language, tool call ids and names, and file paths pass through the terminal-safe encoding, and each line of a prompt, reply, argument list, tool output, or summary has its control characters, C1 controls, and line and bidirectional formatting characters escaped, keeping tabs and line breaks. Upstream writes all of them raw. The JSON keeps the stored values. `oh-fx session migrate <id>` reports upstream's `[session migration]` text and JSON. A session in the conversation format, oh-fx's or fx's, is `already_current` with source schema version 4 and 0 bytes and is left as it is. A schema-v3 session that fx 0.0.1 to 0.0.7 saved is copied and converted into oh-fx's store as `resume <id>` converts it, never in place, and reported `migrated` with source schema version 3 and the bytes of its committed log, the values upstream reports for its conversion in place. `--allow-large` is accepted and changes nothing, since it only lifts the size ceiling of the legacy snapshots oh-fx does not read. Under `--sessions-v2` or `OH_FX_SESSIONS_V2` it fails with upstream's `session migrate converts v1 sessions and is not available with sessions v2 yet`. A folder in oh-fx's store without conversation metadata, which oh-fx never writes, fails with the reason its metadata cannot be read (`record not found`, `record is corrupt`, or `record uses an unsupported session version`), where upstream converts a legacy or schema-v3 folder in place. An fx session in neither format fails with the import's `this fx session holds data oh-fx cannot read yet`, and an fx subagent child fails with `record not found`, since the import leaves children with fx; upstream migrates both. `session recover` is not available yet.
- `oh-fx workspace` lists, adds, removes, and clears the additional directories saved for the workspace under its `workspaces` entry in `settings.json`, with upstream's text, JSON, errors, warnings, and reconciliation of a settings commit whose durability is uncertain. It reads settings without selecting a provider and model, so it also runs where none can be selected, where upstream's startup fails first. Without `HOME` it still lists the saved directories of the profile it finds through `XDG_CONFIG_HOME` or the user database, where upstream has no profile to read, but a change fails with `HomeNotSet` before it is saved, as upstream's does.
- `--add-dir` and the directories saved for the workspace under `workspaces.<root>.additional_directories` in the user settings grant access to additional directories, as upstream does, in `ask` and the interactive session. A launch directory resolves from the workspace through symlinks; one that is invalid, missing, not a directory, the workspace itself, or past the limit of 16 ends the launch before any request with upstream's `oh-fx: InvalidPath`, `PathNotFound`, `NotDirectory`, `PrimaryDirectory`, or `TooManyDirectories`, which `ask --json` reports as its result's error. A saved directory that is missing stays inactive, and `--no-additional-dirs` leaves every saved one inactive. The model receives upstream's runtime context message naming the active directories, and a subagent works with the same directories, as upstream's children share their parent's access scope. Reads and searches inside an active additional directory run without approval, confined to it, and in auto mode a known reversible command whose `cwd` is inside one runs without review, as in the workspace; upstream needs no approval for reads anywhere. `write_file` and `edit_file` read a target there before admission, as they read workspace targets, and in auto mode a change there is reversible and runs without review, as upstream treats it; ask mode still asks for approval. A saved list that does not resolve, such as one naming the workspace, is dropped with upstream's `invalid_additional_directories` diagnostic when `ask`, the interactive session, or `oh-fx workspace` loads the settings; other commands that read them check only the list's shape, size, duplicates, and absolute paths. `oh-fx workspace` and `/workspace` change the saved list, and `/workspace` applies the change to the running session from its next call.
