# Command line and help

- The top-level help links to the oh-fx repository instead of fx.sh/docs.
- oh-fx has no `slack` command (`slack install`, `slack status`, and `slack refresh`) and no one-command Slack MCP preset (`mcp add slack`, added upstream in vercel-labs/fx#1101). Both depend on fx's own Slack app, whose public Client ID and fx.sh OAuth bridge belong to Vercel, so they are omitted until oh-fx has a Slack app of its own. `oh-fx slack` fails as any unknown command does, and `oh-fx mcp add slack` keeps the usage error that upstream printed before the preset. Without the `slack` row, the top-level help's command column is one character narrower than upstream's, because `slack <install|status|refresh>` was its widest usage. Once MCP support lands, a user with their own Slack app can still add Slack's MCP server with `oh-fx mcp add --transport http slack https://mcp.slack.com/mcp` and set `oauth.client_id`, `oauth.client_secret_env`, and `oauth.callback_port` for it in the profile MCP configuration, as upstream allows: upstream authorizes any Slack Client ID other than fx's through its ordinary callback at `http://localhost:<callback_port>/callback`, and Slack offers no dynamic client registration, so the Client ID is required. Those fields alone are not enough: [Slack's MCP server documentation](https://docs.slack.dev/ai/slack-mcp-server/) limits it to internal apps and apps published in Slack's directory, and the app must also list that callback as an OAuth redirect URL and request the user scopes the MCP tools need.
- Top-level help narrower than its two-column layout needs (under 53 columns for commands and flags) puts each usage on its own line with the summary indented below, and stacks the resource links when their longest word does not fit beside the labels, so only unbreakable words overflow. Upstream keeps the two-column layout at every width.
- An unknown command is echoed through terminal-safe encoding capped at 160 bytes, so escape sequences, other control characters, and invalid UTF-8 print as escapes such as `\x1b` and `\xff`. Upstream writes the raw bytes to the terminal.
- A closed stdout cannot be detected: the Rust runtime reopens closed standard streams on `/dev/null` before `main` runs, so output is discarded where upstream reports `WriteFailed` or `NotOpenForWriting`. Full disks and closed pipes fail as upstream does.
- Until their features land, commands and flags that oh-fx parses but cannot run fail with `oh-fx: <command> is not available yet` and exit status 1, where upstream runs them. Arguments are validated first, so malformed ones still fail with upstream's usage errors. With `--json`, such a command also prints `{"kind":"<command>","error":"<command> is not available yet","code":"NotAvailableYet"}` on stdout, and `ask --json` prints its JSON result with the error `NotAvailableYet`. This covers every command except `ask`, `upgrade`, `permissions`, `status`, `usage`, `doctor` (on the v1 store), `workspace`, `help`, `--version`, `login codex`, `logout codex`, `login grok`, `logout grok`, `provider codex`, and `models` while Codex is the selected provider (so `login` and `logout` for Vercel, `provider` for the gateway, Grok, and custom connections, and `models` for the gateway, Grok, and custom connections are covered), the `--context-limit` launch modifier when it sets an MCP or image limit, since `ask` and the interactive session have no image attachments for it to apply to and take MCP limits only from `context_limits` in `settings.json` until the flag's full port adds its MCP keys (both apply the four skill limits, `project_instruction_file_bytes`, and `project_instructions_total_bytes` from the command line), `--provider` on an interactive launch, and the `--sessions-v2` launch modifier on `ask` and on interactive launches. Commands that keep no sessions upstream, such as `upgrade`, `login codex`, `logout codex`, `help`, and `--version`, accept and ignore `--sessions-v2` as upstream does; `acp` and the other commands that use sessions upstream fail as not available yet with or without it.
- `oh-fx status` prints upstream's `[status]` lines and JSON without `update_channel`, `build_channel`, and `build_revision`, as `/status` does, and without `team`, since oh-fx has no Vercel AI Gateway connection. With the gateway or Grok selected it fails with the startup error that `ask` prints, as upstream's `status` does when startup cannot select a model, since oh-fx cannot run either provider yet. `connected_providers` lists the selected connection while its credential is available, Codex while a Codex login is saved, and Grok while a Grok login is saved; it never lists the gateway, which oh-fx holds no credentials for, and under `OH_FX_AUTH_MODE=host-managed` it lists only Codex, since oh-fx sends no Grok requests yet. A connection without a saved model reports the first model of its `models` list with `model_origin=default`, and the environment override is named `OH_FX_MODEL`. The Codex login is read without refreshing it, as upstream does, so an expired one shows `auth_expired=true`. The text lines encode the workspace path and the model through upstream's terminal-safe encoding, so a directory name with escape sequences or newlines cannot clear the screen or forge a line; upstream writes both raw. JSON keeps them as they are. `ultrafast_requested` is always `false`, since oh-fx reads neither upstream's `ultrafast_mode` setting nor its `FX_ULTRAFAST` override yet; Ultra mode is requested only for an interactive session, with `--ultrafast` or `/ultrafast`.
- `oh-fx usage` fails as upstream's does in a host without durable profile usage, with `oh-fx usage: local usage data is unavailable` on stderr, or `{"kind":"usage","error":"local usage data is unavailable","code":"ProfileUsageUnavailable"}` with `--json`, after upstream's `HomeNotSet` check. Its report for the `--period` window (coverage, token and spend totals, and the per-model table) arrives with the usage ledger that `/usage` waits for.
- `oh-fx doctor` runs upstream's checks in upstream's order, with its text and JSON, and names oh-fx's files: `~/.config/oh-fx/settings.json`, `.oh-fx.json`, and `~/.config/oh-fx/mcp.json`, and the `sessions` directory under the data directory. It reports no per-session diagnostics (authority transitions, projections, commit watermarks, log compaction, or cleanup candidates), since oh-fx's session store keeps none of that state, so there is no truncation check either. With the gateway or Grok selected, or with settings that cannot be loaded, the auth and startup checks fail with the "not available in oh-fx yet" error `ask` prints. The workspace path and the model are terminal-safe in text, as in `status`. The auth check fails with the error `ask` reports when the selected connection cannot be resolved, such as a bearer token that is not visible ASCII or a header whose environment variable is unset, and the startup check fails with `InvalidProfileConfiguration` when the user settings are unusable, so doctor does not pass a profile that `ask` refuses; upstream's doctor reports both checks as ok.
- `oh-fx workspace` lists, adds, removes, and clears the additional directories saved for the workspace under its `workspaces` entry in `settings.json`, with upstream's text, JSON, errors, warnings, and reconciliation of a settings commit whose durability is uncertain. It reads settings without selecting a provider and model, so it also runs where none can be selected, where upstream's startup fails first. Saving needs `HOME`, as upstream's does, even where oh-fx could find the profile through the user database.
- `--add-dir` and the directories saved for the workspace under `workspaces.<root>.additional_directories` in the user settings grant access to additional directories, as upstream does, in `ask` and the interactive session. A launch directory resolves from the workspace through symlinks; one that is invalid, missing, not a directory, the workspace itself, or past the limit of 16 ends the launch before any request with upstream's `oh-fx: InvalidPath`, `PathNotFound`, `NotDirectory`, `PrimaryDirectory`, or `TooManyDirectories`, which `ask --json` reports as its result's error. A saved directory that is missing stays inactive, and `--no-additional-dirs` leaves every saved one inactive. The model receives upstream's runtime context message naming the active directories, and a subagent works with the same directories, as upstream's children share their parent's access scope. Reads and searches inside an active additional directory run without approval, confined to it, and in auto mode a known reversible command whose `cwd` is inside one runs without review, as in the workspace; upstream needs no approval for reads anywhere. `write_file` and `edit_file` read a target there before admission, as they read workspace targets, and in auto mode a change there is reversible and runs without review, as upstream treats it; ask mode still asks for approval. A saved list that does not resolve, such as one naming the workspace, is dropped with upstream's `invalid_additional_directories` diagnostic when `ask`, the interactive session, or `oh-fx workspace` loads the settings; other commands that read them check only the list's shape, size, duplicates, and absolute paths. `/workspace` and its menu are not ported yet, so only `oh-fx workspace` changes the saved list.
