# Command line and help

- The top-level help links to the oh-fx repository instead of fx.sh/docs.
- oh-fx has no `slack` command (`slack install`, `slack status`, and `slack refresh`) and no one-command Slack MCP preset (`mcp add slack`, added upstream in vercel-labs/fx#1101). Both depend on fx's own Slack app, whose public Client ID and fx.sh OAuth bridge belong to Vercel, so they are omitted until oh-fx has a Slack app of its own. `oh-fx slack` fails as any unknown command does, and `oh-fx mcp add slack` keeps the usage error that upstream printed before the preset. Without the `slack` row, the top-level help's command column is one character narrower than upstream's, because `slack <install|status|refresh>` was its widest usage. Once MCP support lands, a user with their own Slack app can still add Slack's MCP server with `oh-fx mcp add --transport http slack https://mcp.slack.com/mcp` and set `oauth.client_id`, `oauth.client_secret_env`, and `oauth.callback_port` for it in the profile MCP configuration, as upstream allows: upstream authorizes any Slack Client ID other than fx's through its ordinary callback at `http://localhost:<callback_port>/callback`, and Slack offers no dynamic client registration, so the Client ID is required. Those fields alone are not enough: [Slack's MCP server documentation](https://docs.slack.dev/ai/slack-mcp-server/) limits it to internal apps and apps published in Slack's directory, and the app must also list that callback as an OAuth redirect URL and request the user scopes the MCP tools need.
- Top-level help narrower than its two-column layout needs (under 53 columns for commands and flags) puts each usage on its own line with the summary indented below, and stacks the resource links when their longest word does not fit beside the labels, so only unbreakable words overflow. Upstream keeps the two-column layout at every width.
- An unknown command is echoed through terminal-safe encoding capped at 160 bytes, so escape sequences, other control characters, and invalid UTF-8 print as escapes such as `\x1b` and `\xff`. Upstream writes the raw bytes to the terminal.
- A closed stdout cannot be detected: the Rust runtime reopens closed standard streams on `/dev/null` before `main` runs, so output is discarded where upstream reports `WriteFailed` or `NotOpenForWriting`. Full disks and closed pipes fail as upstream does.
- Until their features land, commands and flags that oh-fx parses but cannot run fail with `oh-fx: <command> is not available yet` and exit status 1, where upstream runs them. Arguments are validated first, so malformed ones still fail with upstream's usage errors. With `--json`, such a command also prints `{"kind":"<command>","error":"<command> is not available yet","code":"NotAvailableYet"}` on stdout, and `ask --json` prints its JSON result with the error `NotAvailableYet`. This covers every command except `ask`, `upgrade`, `permissions`, `help`, `--version`, `login codex`, `logout codex`, `login grok`, `logout grok`, `provider codex`, and `models` while Codex is the selected provider (so `login` and `logout` for Vercel, `provider` for the gateway, Grok, and custom connections, and `models` for the gateway, Grok, and custom connections are covered), the `--context-limit` launch modifier when it sets an MCP or image limit, since `ask` and the interactive session have no image attachments for it to apply to and take MCP limits only from `context_limits` in `settings.json` until the flag's full port adds its MCP keys (both apply the four skill limits, `project_instruction_file_bytes`, and `project_instructions_total_bytes` from the command line), `--provider` on an interactive launch, and the `--sessions-v2` launch modifier on `ask` and on interactive launches. Commands that keep no sessions upstream, such as `upgrade`, `login codex`, `logout codex`, `help`, and `--version`, accept and ignore `--sessions-v2` as upstream does; `acp` and the other commands that use sessions upstream fail as not available yet with or without it.
- `--add-dir` and the directories saved for the workspace under `workspaces.<root>.additional_directories` in the user settings grant access to additional directories, as upstream does, in `ask` and the interactive session. A launch directory resolves from the workspace through symlinks; one that is invalid, missing, not a directory, the workspace itself, or past the limit of 16 ends the launch before any request with upstream's `oh-fx: InvalidPath`, `PathNotFound`, `NotDirectory`, `PrimaryDirectory`, or `TooManyDirectories`, which `ask --json` reports as its result's error. A saved directory that is missing stays inactive, and `--no-additional-dirs` leaves every saved one inactive. The model receives upstream's runtime context message naming the active directories. Reads and searches inside an active additional directory run without approval, confined to it, and in auto mode a known reversible command whose `cwd` is inside one runs without review, as in the workspace; upstream needs no approval for reads anywhere. A file change there still needs approval in ask mode, and in auto mode a change to an existing file there goes to the reviewer, because oh-fx reads only workspace targets before admission; upstream treats it as reversible and skips the review. A saved list that does not resolve, such as one naming the workspace, is dropped with upstream's `invalid_additional_directories` diagnostic when `ask` or the interactive session loads the settings; other commands that read them check only the list's shape, size, duplicates, and absolute paths. `oh-fx workspace`, `/workspace`, and its menu, which change the saved list, are not ported yet.
