# Model retries and turn recovery

- A retryable failure after reply text has streamed restarts the response, as upstream's `continue_response` does. The status reads `restarting response`; after the wait, upstream's `[Response interrupted. Restarting.]` notice follows the partial text, and the request ends with upstream's note asking the model to restart that response from the beginning without repeating completed tool actions. The note stays on later retries of that request, except one sent after a connectivity wait or connection check and the request steering sends after interrupting the restarted reply, as upstream drops it there. A reply the response language check still holds is dropped without the notice, as upstream drops its held candidate, and the shell starts the restarted reply as a fresh Markdown block, so a reply cut inside a code block does not swallow the notice. The response language check starts again for the restarted reply, and a restart keeps Fast mode, which upstream switches off only for a request it can replay. `ask` writes the notice into its raw output, to stderr with `--json` and `--quiet`, and in place in the terminal; `--json` drops the interrupted text from `output` once the restarted reply starts or the turn completes, as upstream drops its preview. A failure after the model started a tool call regenerates the call instead, as upstream's `regenerate_tool` does: the status reads `regenerating unstarted tool` and the request ends with upstream's note that the call was not executed and should be recreated only if it is still needed. A provider failure reported inside the stream after a tool call started, or a cut-off call to a tool the provider runs, leaves the call uncertain, as upstream treats a failed completion that carries calls: the retry reads `checking uncertain tool state`, ends with upstream's note to reconcile the tool evidence first, and withholds tools. The tool evidence holds across retries that stream nothing, and a turn continued from a checkpoint starts from the evidence its strategy was saved with, so a connectivity wait or connection check drops the note for its request and a later failure brings it back, as upstream derives it again. The Codex transport reports tool starts and their streamed input; a custom Chat Completions connection reports neither, as upstream's does not. Model retries do not retry TLS or proxy tunnel failures. As upstream does, the attempt budget does not end a turn: HTTP 429 and 5xx answers and connectivity losses keep retrying, and once a turn has been recovering for 15 minutes its retries wait at least a minute. A network failure, or a server failure the provider reports inside its stream, such as a retryable Codex `response.failed` or `error` event, that repeats three times in a row at the same number of streamed text and reasoning bytes stops the turn under upstream's `⚠ Network interrupted · RequestFailed · kept failing at the same point · stopped` or `⚠ Provider unavailable · … · kept failing at the same point · stopped` and discards the recovery checkpoint; HTTP 429 and 5xx answers carry no progress and never stop this way, as upstream exempts them. A streamed tool call's input counts as progress too, as upstream counts it. A retried request that fails without an HTTP status reports upstream's terminal recovery status, such as `⚠ Provider unavailable · ConnectionFailed · stopped after 2 attempts`, with a rate-limited stop reading upstream's `server requested a longer wait · recovery paused · attempt N`; `ask` prints these even with `--quiet`, adds upstream's `--no-save` notice when the run saves no session, and reports its JSON `recovery.state` as `failed`.
- A model stream that goes quiet is ended by upstream's stall watchdog from `src/gateway/client.zig`: once the response head has arrived, a stream that delivers no event for ten minutes, the window upstream gives its agent path, fails as `StreamStalled`. Keep-alive comments do not hold it off, as upstream counts only data events. Its retry checks the connection under upstream's unbudgeted `⚠ Gateway stream timed out · checking the connection` label, and stalls that repeat at the same point stop the turn. Upstream runs the watchdog only in its Vercel AI Gateway client, which oh-fx does not have; oh-fx runs it on the Codex transport and custom connections, where upstream's transports have none and wait until Esc. Upstream's gateway client is the proxy most of its traffic goes through, and custom connections usually point at proxies too, such as Portkey, so without the watchdog a stream a proxy keeps open but silent would hang a turn that upstream's gateway path recovers from; the watchdog moves to the gateway client when oh-fx has one. That retry sends the whole request again, as upstream's does, so once the turn has been recovering for 15 minutes it waits at least a minute like any other retry; upstream's `decide` in `src/core/agent/runtime/model_response_recovery.zig` treats the check as sending nothing and keeps its short cadence. Any other timeout, such as a custom connection's two-minute wait for the response head, retries as a network interruption under `⚠ Network interrupted · timed out`, as upstream's does.
- While a model request waits to be retried, the activity row above the composer shows upstream's route recovery label in the warning tone in place of the turn activity, such as `⚠ Rate limited · HTTP 429 · slow · retrying request in 3s`, counting the seconds down as upstream does and dropping the ` in Ns` part at the deadline. The retried request publishes the label again when the provider admits it, just before it connects, as upstream does, and keeps it while it runs; a retried request refused before admission, such as one without a valid ChatGPT account, publishes no label and is not counted in the stop label's attempts, as upstream counts only admitted attempts; a recovery shows `✓ recovered · attempt N` for 1.5 seconds, and the row ends with its turn, except a terminal status, which stays in the danger tone until the next prompt starts, as upstream keeps it, beside the failed turn's error in the transcript. Steering that ends a waiting or retried request clears the label at once, as upstream does when the cancelled attempt was recovering, and leaves a `✓ recovered` label to expire. A connectivity wait ends its label with upstream's ` · esc to pause`, and one Esc during the wait or its retried request pauses the recovery as upstream does: the turn ends without a cancellation line under upstream's `⚠ Connection lost · ConnectionFailed · recovery paused after 1 attempt · send a new message when you're ready`, which stays until the next prompt starts. As upstream, the paused turn is neither saved nor kept in the conversation: its prompt, finished tool steps, and any text the retried request had streamed stay only in the `paused` checkpoint of a saved session, and a session that is not saved drops them. A saved session keeps the checkpoint until the next turn is saved, and reopening the session continues the paused request. When a mid-turn compaction already saved part of the paused turn, the next message first commits it as interrupted from the checkpoint and sends it in that message's request, as upstream does; otherwise the next message runs without it, as upstream's does. The diagnostic names the provider's error code, such as `ConnectionFailed`, where upstream names the operating system's error, such as `connection refused`. Upstream also keeps a `recovery` record of each status for its full transcript (Ctrl+O), which oh-fx has not ported.
- A writable open reads `recovery.json` as upstream does: a checkpoint saved at an earlier `seq` is stale and left in place, one saved at a later `seq` fails the open as `InvalidRecoveryCheckpoint`, and one saved at the log's last `seq` belongs to the unfinished turn and stays pending.
  - `ask --continue-recovery` continues that turn as upstream does: it sends the checkpoint's prompt with its finished tool steps and steering, without running those tools again, and adds upstream's note for the saved tool state (continue after a confirmed tool, recreate an unexecuted call, or reconcile an uncertain one with tools withheld for that request). A request the provider may have received continues only under the credential that sent it, and the saved Fast mode applies only while the provider, model, and requested Fast mode are unchanged. The continued turn saves the checkpoint's file evidence as it was saved, with its whole-file views, and adds the evidence of the tools it runs after the checkpoint, whose later writes and edits mark the checkpoint's reads of the same path stale. The checkpoint is removed once the continued turn is saved. Without a pending checkpoint the run fails as `NoPendingRecovery` before any request.
  - Committing the checkpoint's turn writes it as `interrupted` (`failed`) with its partial reply, tool steps, steering, and file evidence, after any part a mid-turn compaction already saved, and then removes `recovery.json` and `recovery.asked`.
  - `ask` with a new prompt commits it first only when a mid-turn compaction left the turn open, as upstream does. Otherwise the new prompt runs without it and the checkpoint is removed once the new turn is saved.
  - The interactive session and the session picker show the paused turn's prompt, replies, steering, and partial reply after the resumed transcript, as upstream does, but without its tool rows, which the resumed transcript does not show yet.
  - After a clean exit they continue it on their own, with upstream's "model response recovery paused and continues automatically" notice. The continuation runs ahead of any message typed while the session opened, as upstream queues it first, and shows its prompt again when such a message was shown or cancelled before it started. A continuation that waits for a skill installation to finish keeps its session: `/resume` and the picker refuse to switch sessions until it has run, as they do during a turn. One that cannot start, such as under another credential, shows upstream's "could not continue automatically" notice and leaves the checkpoint pending for the next message, as after an unclean exit.
  - After an unclean exit, or once they have asked, they leave it for the next message, say so with upstream's notice, and mark `recovery.asked`, so the question stays until the checkpoint changes. A turn a mid-turn compaction left open stays open and is committed as interrupted when the next prompt arrives, as upstream does.
  - A `compaction_prepared` checkpoint is committed as interrupted when the session opens, as upstream does.
  - A continued turn restarts a response the checkpoint caught part-way, as upstream's `continue_response` strategy does, rather than resuming from the saved partial text; upstream shows that partial text first. oh-fx reads the checkpoint form upstream writes today, version 2 with execution memory schema 10; upstream also reads version 1 and legacy route checkpoints with older execution schemas, which fail in oh-fx as `InvalidRecoveryCheckpoint`.
- A saved session writes `recovery.json` as upstream does when the retry loop retries a model request: before each retry wait, as `retrying_request`, `continuing_response`, `waiting_for_connectivity`, or `checking_liveness`, and as `paused` when Esc pauses the recovery, with the attempts the provider admitted. A recovery that stops because it kept failing at the same point discards its checkpoint, as upstream does. The checkpoint holds the turn's finished tool steps, steering, and file evidence, and outputs over 4 KiB go to `tool-results` with their handle. The next saved turn removes it, cancelling a retry wait discards it, and JSON results from a saved `ask` report `recovery.durable` as `true`. A checkpoint writes each tool call's `provider_result` as `null` and reads only `null`, where upstream keeps a provider-executed call's result there; no connection oh-fx supports produces provider-executed calls until the gateway transport arrives, and the encoder and reader take the call's own result with it.
  - Like upstream, a turn that fails before doing anything is left out of `events.jsonl`, so its checkpoint is what `--continue-recovery` continues. So is a turn that ends `paused`, whatever it did first, as upstream leaves it out.
  - A checkpoint written while a response restarts saves `assistant_source` empty, so `--continue-recovery` from it asks again without the restart note and without showing the partial text, where upstream saves the partial text there and restarts the response from it. Writing it is deferred to the next recovery slice, which also shows the saved partial text when a turn continues (`src/core/agent/runtime/orchestrator.zig`, `persistRecoveryCheckpoint` and `restoreRecoverySource`).
  - A checkpoint always saves `tool_state` as `none`, so continuing one written while a tool call is regenerated or reconciled asks again without the tool note, where upstream saves the turn's tool evidence there. Writing it is deferred to the same slice as `assistant_source`.
  - Upstream pauses a recovery whose reconciling request starts another tool call, and names the action a paused or uncertain recovery needs (`continue_later` or `inspect_uncertain_tool`) in its status. oh-fx has no required action but the stall's yet, so these are deferred to the recovery pause slice (`src/core/agent/runtime/orchestrator.zig`, `pausedRequiredAction` and the reconciliation check after a stream error).
  - Upstream also writes a checkpoint for a failure it does not retry, before each Gateway request, and before an automatic compaction (`compaction_prepared`). oh-fx writes one only before a retry wait or a pause and has no Gateway route, so it writes none of these; a checkpoint for a failure that is not retried is deferred to a later recovery slice.
  - A continued turn starts with a fresh attempt budget; upstream carries the consumed attempts over.
- Before retrying a model request, ask forgets every provisional tool identity from the failed attempt, so abandoned identities cannot suppress a later rejection's step count without a new start. Upstream retains identities that also appear in a recovered completion. A retried call must therefore publish a new provisional start here to keep its rejected completion from counting as an executed step. A local tool start followed by a retryable stream failure before assistant text repeats the original request; upstream asks the model to recreate the unexecuted call only if it is still needed. The call remains unexecuted until a complete request admits it in either case.
