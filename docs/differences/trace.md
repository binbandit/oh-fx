# Trace log and `/trace`

- The trace log reads `OH_FX_TRACE_LOG`, `OH_FX_TRACE`, `OH_FX_TRACE_STDERR`, and `OH_FX_TRACE_SCOPES` in place of upstream's `FX_TRACE_LOG`, `FX_TRACE`, `FX_TRACE_STDERR`, and `FX_TRACE_SCOPES`, as every oh-fx variable takes the `OH_FX_` prefix. `OH_FX_TRACE` writes to `$XDG_STATE_HOME/oh-fx/logs/trace.log` (default `~/.local/state/oh-fx/logs/trace.log`) where upstream writes `~/.fx/logs/trace.log`, because oh-fx keeps its logs under its state directory, and without a profile it writes `/tmp/oh-fx-trace-<ms>.log` where upstream writes `/tmp/fx-trace-<ms>.log`. The interactive session, `ask`, `permissions`, and `doctor` configure the log when they load the profile, as upstream configures it when it loads its startup state. The log lives for the whole process, so there is no shutdown that would let a later configuration replace it.
- Text cut to a byte limit for the trace, such as a compaction ring detail or a provider error preview, ends at a character boundary, where upstream may cut inside a UTF-8 sequence. The trace line still writes every byte outside printable ASCII as `\xNN`, as upstream's does. Secrets are masked before anything is cut: a provider error preview is masked whole and then cut, as upstream does, and, as a security difference, the report's Trace Tail leaves out the partial line at the start of its 6 KiB window, where upstream masks that partial line as it is, so a window that starts inside a credential, such as after the `https://` of a URL's `user:password@`, cannot leave its end unmasked.
- The agent's trace lines keep upstream's events, scopes and fields, with these differences. `finish_reason` is `stop` or `tool-calls`, because oh-fx's transports report a length, content-filter or provider-error finish as an error, and `prompt_finish` names such a turn's outcome from that error's code: `provider_length`, `content_filter`, `provider_error` or `stream_interrupted`, otherwise `http_error`. A tool that panics is traced with `err=Panicked`, oh-fx's code for it, and recorded as `runtime_failed` with an empty result. `cancel_observed` and the interrupted-persistence lines are written once, when the interrupted turn is kept, where upstream writes them at the check that saw the cancellation; the call that was running or about to run is named as the active tool, as upstream names it. A shell call refused by validation is not counted among a turn's completed tools, where upstream counts its prepared shell's validation and availability failures. A child's `trace_identity` names `parent_id=unknown` when the parent's session is not saved. The permission lines, the lines for a call rejected before it runs or deferred by the project gate, the history projection lines, and the worker's enqueue and steering lines come with what they report: permission reasons, the argument integrity tag on a rejection, the history turn shapes, and turn ids taken when a prompt is queued. `tool_presentation_group`, `provider_completion_blocked` and `subagent_parent_continuation` are not written, because oh-fx has no presentation groups, its transports report a blocked finish as an error, and it does not steer a running child. The JSON shape of tool arguments is read with serde_json: arguments that repeat a key show the shape of their last value, where upstream shows `<invalid-json bytes=N>`, and arguments nested more than 128 levels deep show as invalid.
- A failed model request writes upstream's stream and recovery lines, sorted as upstream sorts its results, because oh-fx's transports report every failure as an error. An HTTP status writes no line. A failure the stream reported as its finish writes `route_failure` with `http_status=200`, then `provider_completion_failed` when it is not retried, or `provider_finish_missing` for a stream that ended without a finish; a length finish is a failure in oh-fx and writes no line, as upstream completes such a turn. Any other failure, a cancellation included, writes `stream_error`, whose `err=` names oh-fx's error code, such as `ReadFailed`, where upstream names a Zig error. `route_failure`'s `detail=` is oh-fx's provider detail, masked before it is cut to 240 bytes. `route=` is the selected model, because oh-fx sends Fast mode as an option rather than as a different route model, so `recovery_fast_fallback` names that model twice. `recovery_checkpoint_set` is written where oh-fx saves a checkpoint, before a retry wait and on a pause, as [recovery.md](recovery.md) records, with `outstanding=false` and upstream's `transport_interrupted` for oh-fx's `network_interrupted` cause; a failure that pauses a reconciling request writes `recovery=pause`. The `failed to clear due retry status`, token progress and network record publication lines are not written, because oh-fx's event sink cannot fail and it keeps no full-detail network records. The auth replay and credential refresh lines come with the auth lines, `route_recovery_decision` with route recovery, and `ultrafast_served_tier` with a served service tier.
- The gateway lines are those of the transports oh-fx has: the Codex `provider_replay_omitted` line, the provider version lookup lines, and the bounded termination lines of the GET that the Codex model catalog and version lookups use, whose failure names `Timeout`, `ConnectionFailed`, `RequestFailed` or `StreamTooLong`. Upstream's attempt, pool, request, SSE, resolved model and generation usage lines belong to its Vercel AI Gateway client, which oh-fx does not have, and the chat-completions transport keeps no reasoning replay, so it writes no replay lines.
- `/trace` writes its report to `$TMPDIR/oh-fx-trace-<date>-<time>-<hex>.md`, titled `# oh-fx trace`, where upstream writes `fx-trace-…` titled `# fx trace`. It copies the report's text with the composer's clipboard command, `pbcopy` on macOS and `xclip -selection clipboard` on Linux, where upstream puts a reference to the file on the macOS pasteboard through `osascript` and copies nothing elsewhere. The outcome notices keep upstream's wording and platform split: a failed copy reports `Clipboard copy failed. Trace saved at <path>` on macOS and `Trace saved at <path>` elsewhere. oh-fx's transcript has no notice that a later one replaces, so the report is built on a worker thread without upstream's `Preparing trace...` row, and only the outcome notice appears.
- The report's Tool Calls section lists the calls the tool-call ring recorded, as upstream's Local part does, without the `### Web Search` part, which upstream projects from the conversation history and which comes with the report's history-derived sections. As a security difference, the tool-call ring masks secrets in a call's arguments and result before it cuts them to 1,200 and 2,000 bytes, and keeps the masked size as their full size, so the report's `... (N more bytes)` counts masked text. Upstream cuts first and masks only when it writes the report, so a cut that falls inside a credential, such as before the `@` of a URL's `user:password@`, can leave its start unmasked.
- The network ring records each model request the agent, a compaction summary, a session title and a chat-completions review send, and each `web_fetch` target, as upstream's does, and lives in `ofx-trace` because those crates all record into it. A request that fails before an HTTP answer is recorded with oh-fx's error code, and an HTTP failure's `bytes=` counts oh-fx's formatted error detail, where upstream counts the raw body. Codex reviews are not recorded, as upstream sends them past its recording funnel. The Network Calls section has no gateway schema, request shape or `web_search` calls yet, which come with the Vercel transport and the web search runtime, and its coverage line names `OH_FX_TRACE_LOG`. `/clear`, `/new`, `/reset` and a resumed session reset the ring with the others.
- The report's `version` line has no commit in parentheses, because oh-fx builds carry only their release version, whose dev number already names the commit on `main`, and `build` says `Debug` or `Release` where upstream names its Zig optimize mode. The active-turn problem reports `stream_active=true` while a turn runs, since the controller that builds the report does not see the shell's stream state.
