# Trace log and `/trace`

- The trace log reads `OH_FX_TRACE_LOG`, `OH_FX_TRACE`, `OH_FX_TRACE_STDERR`, and `OH_FX_TRACE_SCOPES` in place of upstream's `FX_TRACE_LOG`, `FX_TRACE`, `FX_TRACE_STDERR`, and `FX_TRACE_SCOPES`, as every oh-fx variable takes the `OH_FX_` prefix. `OH_FX_TRACE` writes to `$XDG_STATE_HOME/oh-fx/logs/trace.log` (default `~/.local/state/oh-fx/logs/trace.log`) where upstream writes `~/.fx/logs/trace.log`, because oh-fx keeps its logs under its state directory, and without a profile it writes `/tmp/oh-fx-trace-<ms>.log` where upstream writes `/tmp/fx-trace-<ms>.log`. The interactive session, `ask`, `models`, `permissions`, `doctor` and `status` configure the log when they load the profile, as upstream configures it when it loads its startup state. `setup`, `login`, `teams`, and `logout` configure it too, so their stored-key, sign-in, refresh, and revocation failures are written, where upstream's `fx setup`, `fx login`, `fx teams`, and `fx logout` leave the log unconfigured. The log lives for the whole process, so there is no shutdown that would let a later configuration replace it.
- Text cut to a byte limit for the trace, such as a compaction ring detail or a provider error preview, ends at a character boundary, where upstream may cut inside a UTF-8 sequence. The trace line still writes every byte outside printable ASCII as `\xNN`, as upstream's does. Secrets are masked before anything is cut: a provider error preview is masked whole and then cut, as upstream does, and, as a security difference, the report's Trace Tail leaves out the partial line at the start of its 6 KiB window, where upstream masks that partial line as it is, so a window that starts inside a credential, such as after the `https://` of a URL's `user:password@`, cannot leave its end unmasked.
- The agent's trace lines keep upstream's events, scopes and fields, with these differences. `finish_reason` is `stop` or `tool-calls`, because oh-fx's transports report a length, content-filter or provider-error finish as an error, and `prompt_finish` names such a turn's outcome from that error's code: `provider_length`, `content_filter`, `provider_error` or `stream_interrupted`, otherwise `http_error`. A tool that panics is traced with `err=Panicked`, oh-fx's code for it, and recorded as `runtime_failed` with an empty result. `cancel_observed` and the interrupted-persistence lines are written once, when the interrupted turn is kept, where upstream writes them at the check that saw the cancellation; the call that was running or about to run is named as the active tool, as upstream names it. A shell call refused by validation is not counted among a turn's completed tools, where upstream counts its prepared shell's validation and availability failures. A child's `trace_identity` names `parent_id=unknown` when the parent's session is not saved. `tool_presentation_group`, `provider_completion_blocked` and `subagent_parent_continuation` are not written, because oh-fx has no presentation groups, its transports report a blocked finish as an error, and it does not steer a running child. The JSON shape of tool arguments is read with serde_json: arguments that repeat a key show the shape of their last value, where upstream shows `<invalid-json bytes=N>`, and arguments nested more than 128 levels deep show as invalid.
- A failed model request writes upstream's stream and recovery lines, sorted as upstream sorts its results, because oh-fx's transports report every failure as an error. An HTTP status writes no line. A failure the stream reported as its finish writes `route_failure` with `http_status=200`, then `provider_completion_failed` when it is not retried, or `provider_finish_missing` for a stream that ended without a finish; a length finish is a failure in oh-fx and writes no line, as upstream completes such a turn. Any other failure, a cancellation included, writes `stream_error`, whose `err=` names oh-fx's error code, such as `ReadFailed`, where upstream names a Zig error. `route_failure`'s `detail=` is oh-fx's provider detail, masked before it is cut to 240 bytes. `route=` is the selected model, because oh-fx sends Fast mode as an option rather than as a different route model, so `recovery_fast_fallback` names that model twice. `recovery_checkpoint_set` is written where oh-fx saves a checkpoint, before a retry wait and on a pause, as [recovery.md](recovery.md) records, with `outstanding=false` and upstream's `transport_interrupted` for oh-fx's `network_interrupted` cause; a failure that pauses a reconciling request writes `recovery=pause`. The `failed to clear due retry status`, token progress and network record publication lines are not written, because oh-fx's event sink cannot fail and it keeps no full-detail network records. `route_recovery_decision` comes with route recovery, and `ultrafast_served_tier` with a served service tier.
- The worker lines follow upstream's queue. A prompt takes its turn id when it is queued, and `prompt_enqueue`, `worker_begin` and the agent's lines for its turn carry it, so a prompt that steers a running turn keeps an id no turn starts with, as upstream's does. A prompt queued while a turn runs writes `steering_admission` with the running turn's id, since oh-fx steers each such prompt, and `tool_boundary` is true while the turn runs tools; every steering boundary writes `steering_boundary_check`, steering taken into the turn writes `prompt_steering_consumed`, a steer taken back for editing writes `prompt_steering_retracted`, steering left when the turn ends writes `steering_deferred_to_next_turn`, and a prompt dropped when the conversation is cleared back to an earlier prompt writes `queued_prompt_removed`. `fast_mode` and `effort` are the settings when the prompt was queued, as upstream records them. `ask` runs its prompt without the queue, so its turn takes its id when it starts. The compaction queue lines come with queued compactions, because oh-fx runs `/compact` at once, and the worker event delivery, turn start hold, stale delivery, queued history and late question lines come with those parts of upstream's worker.
- The permission lines follow upstream's request and decision. Each call the gate decides writes `before_permission_wait` and `permission_requested`, then `after_permission_decision` and `permission_decision`, with the permission mode (`ask`, `auto` or `yolo`), the session grants, and whether its target is outside the workspace: `true`, `false`, `not_path`, or `unknown` for a file change, as upstream classifies it. The decision is `once` for a call the mode, a grant, an approval or a cleared review allows, `always` for an approval to always allow, `deny` for a denied approval or a review hold, and `permission_required` when no one can approve it, and a cancelled approval or review writes `permission_error err=Cancelled`. `approval_source` names the denial, a file change, a session grant or the mode as upstream does, and for a command names the grant or the mode, where upstream names the command's execution authority, which oh-fx does not keep. A review hold reused within the turn writes `turn_permission_denial_preserved`. `missing_execution_authority`, `live_authority_target_failure` and `permission_target_resolution_error` are not written, because oh-fx keeps no execution authority, has no live tool authority, and resolves targets while it prepares a call. The automatic review writes upstream's lines: `auto_review_start` with the action kind, the classifier's `auto_review_compose_start` with `origin=root`, as oh-fx's review data names every review, `auto_review_compose_result`, `auto_review_send` for each attempt, `auto_review_transport_retry` and `auto_review_format_retry`, the transport's `auto_review_transport` result, and `auto_review_result` with its decision and fallback reason, `cancelled_or_error` when the review is cancelled while it waits; a review the policy cannot start writes `auto_review_result decision=unavailable`, after `auto_review_budget_exhausted` when the turn's review budget is spent. The transport names an HTTP failure's kind, a refused finish, or oh-fx's error code for any other failure, and a completion's `finish_reason` is `stop` or `tool_calls`, `length` for a cut-off reply, or `absent` for a reply without a decision that oh-fx's transport reports as an error. The Vercel AI Gateway reviewer also writes `auto_review_transport_start` with its model and names an HTTP failure by its `http_status`, as upstream's does, and never writes `reason=missing_gateway_config`, because oh-fx builds it only with a credential; it is not routed yet. `auto_review_usage` is not written, because oh-fx counts a review's usage with its turn and has no separate settlement that can fail. The shell writes upstream's permission mode, full-access acknowledgment and `approval response submitted` lines. The approval screen and file approval confirmation lines belong to upstream's full-screen approval view, the feedback discard lines to its feedback drafts, and the rule management lines to saved-session permission rules, and oh-fx writes none of them yet.
- The config lines follow upstream's settings store. Each save writes `settings operation=… path_category=user_settings scope=… mutation_mode=…` with `outcome=committed` and its cleanup counts, `outcome=unchanged`, or `outcome=failed` with oh-fx's error code, under upstream's operation names: `user_patch`, `permission_patch`, `workspace_directory_patch` and `project_mcp_patch`. A corrupt-file copy or backup prune that fails writes `settings corrupt copy skipped` or `settings backup prune skipped`. `settings backup skipped` is never written, because a backup that cannot be written fails the save, as [config.md](config.md) records. `/allowlist` writes `allowlist add failed`, `remove failed` or `reset failed` with the scope and error. A settings notice whose source cannot be resolved again writes `post-commit source resolution failed` or `diagnostic`. `oh-fx provider` writes `provider selection settings load failed` and `persistence failed`, but like upstream's `fx provider` it does not configure the trace log, so these appear only in a log another part of the process configured. The lines for upstream's `FX_PROVIDER_ORDER`, `FX_PROVIDER_STRICT`, `FX_REVIEW_MODEL` and `FX_ULTRAFAST` overrides and its model provenance table come with those overrides, and the host config lines come with embedded hosts.
- The hook lines follow upstream's: each handler writes `handler_start` and `handler_finish` with its lifecycle event, name, scope, the call id for `PreToolUse`, its duration, and upstream's outcome names, or `outcome=error` with oh-fx's error code. Agent-dispatched hooks carry the turn's trace and subagent ids. `AttentionRequired` hooks from the shell carry none, because the shell knows its turn but not the agent's trace turn. The Herdr lines write `disabled` with the socket, pane and `OH_FX_HERDR` value under upstream's `fx_herdr=` field, `enabled`, `sent` with upstream's request kind, and `send failed` with an error named from the socket error's kind. The sound and notification lines come with notifications, which oh-fx does not have yet.
- The session store writes upstream's `session` lines for the cases oh-fx has. A pristine session discarded at exit writes `pristine_session_discard` as `discarded`, `retained` with `guard_failed`, `store_root_mismatch` or `store_root_unverified`, or `indeterminate` with its delete or sync stage. A session recovery writes `session_recovery_target_promotion_failed` and `session_recovery_target_indeterminate`, and `recovery_staging_discard` and `session_recovery_unpublished_target_cleanup` for its staged copy. A writable layout that cannot be created writes `writable_layout_failed`. A schema-v3 session that fails its replay while it is listed writes `schema_v3 log replay failed`. An fx display sidecar that cannot be read or decoded writes `display_sidecar_unreadable` or `display_sidecar_invalid err=InvalidDisplayMetadata`. A rejected conversation event writes `conversation event rejected` with upstream's rule names. An imported tool call whose stored arguments are repaired writes `persisted_tool_arguments_repaired source=schema_v3`. Errors are named with oh-fx's codes. The recovery staging root, subagent child, latest selection index, legacy image and cancelled replay handle lines are not written, because oh-fx stages a recovery inside its sessions folder, keeps a session's subagent children when it is discarded, writes its index through the sessions folder, and has no legacy image repair or replay handle notice. As upstream does, a pristine discard whose ownership check fails now leaves the session retained, where oh-fx reported it indeterminate, and a discarded recovery copy syncs the sessions folder.
- The session log writes upstream's `session` lines for the cases oh-fx has: an unfinished turn cut when a log is opened, a writer changed outside its ownership, an append rolled back or not, an oversized recovery checkpoint, the recovery ask marker failures, a checkpoint result left inline, a compaction source restored and its cleanup failure, a committed turn whose recovery cleanup failed, the history cache verify, append-open, rebuild-open, create-on-import, scan and replay fallbacks, detail history that cannot be read, the recovery boundary and prefix, a provider replay dropped from an interrupted turn, a saved result that cannot be read back, the owner liveness marker failures, language metadata and derived titles that cannot be saved, and session creation that is discarded, cannot be cleaned up, cannot be published or is published without a durable sync. Errors are named with oh-fx's codes, and a saved result that cannot be read back names `FileNotFound`, `ResultSizeMismatch`, `ResultSizeUnsupported` or `InvalidUtf8`, as upstream's reader does. A removal whose folder sync failed names `StorageFailed`, because oh-fx keeps no sync error. `legacy recovery archived`, `legacy import discarded file evidence` and `diff_content_spilled` are written when oh-fx imports one of fx's schema-v3 sessions, where upstream writes them for its legacy snapshot import. The allocation failure lines are not written, because oh-fx cannot recover from an allocation failure; the realpath, history source refresh and archive cache lines are not written, because oh-fx works through directory handles, never re-reads a log's length and reads an archive from its log; the derived title check cannot fail, because oh-fx checks the title in memory; the legacy cleanup line is not written, because oh-fx never deletes fx's files; `diff_content_spill_failed` is not written, because oh-fx packs the content in memory and a storage failure fails the import; and the log compaction line comes with session log compaction.
- The history cache writes upstream's `history cache create failed`, `append failed`, `truncate failed` and `delete failed` lines, and an interrupted step that keeps fewer calls than it issued writes `provider replay omitted reason=interrupted_incomplete_association` when it drops its replay. `history cache sync failed` is not written, because oh-fx does not sync its history cache, and an append refused before it is written names `FrameOffsetMismatch` or `PayloadTooLarge`. oh-fx writes cached frames in batches, so a write that fails names the `events.jsonl` offset of the first frame in the failed batch, in the same coordinates as upstream's per-frame line. The `sessions_v2` lines come with the sessions v2 store, the command replay lines with command replay capture, `committed file resume presentation unavailable` is not written because copying the presentation cannot fail in oh-fx, and `usage code accounting failed` is not written because oh-fx records committed lines without a failure to report.
- The app's session runtime writes upstream's `session` lines when the interactive child capability or subagent host is unavailable, an auto-continue is skipped for a compaction checkpoint, suppressed after an unclean exit with the checkpoint's turn id, or fails, a fresh session cannot start after the picker is cancelled, an open turn is blocked after its first failed save, a finished prompt cannot be saved, a resume handoff finds the session unwritable, session persistence fails or stays degraded, a session cannot be remembered, the picker cannot resume a session, and Fast or Ultra mode changes. The `settings persistence failed` and `session persistence failed` lines carry upstream's labels, `model`, `model picker`, `fast`, `ultrafast` or `effort`. Lines carry ids, turn ids, model ids and error codes, never session text. `supports_ultrafast` is `false`, because oh-fx models have no Ultra mode, as [sessions.md](sessions.md) records, and `picker_active` is `true`, because oh-fx resumes a session from the shell only through the picker. A provider switch keeps no degraded state, so its failure writes no `canonical persistence remains degraded` line. The remaining app session lines come with the features that write them: the JS host, sessions v2, live session transitions and scrollback handoff, historical labels and reflow, command replay, deferred diff content, fresh-prompt boundary waits, cancelled-command capture and legacy process migration.
- The command line writes upstream's lines for the cases oh-fx has:
  - `ask` writes `event=ask_session_store_unavailable error=…` when its session store cannot open, and `discarding interrupted JSON preview bytes=…` when a restarted JSON response drops its preview;
  - Codex and Grok sign-ins write `provider sign-in failed provider=… err=…`, as the gateway's already did;
  - a provider switch whose model catalog fails writes `provider selection catalog failed provider=codex category=…`;
  - `replay` writes `replay_start`, `replay_header` and `replay_complete`;
  - the shell writes `prompt` `enqueue bytes=… stream_active=… queued_before=… preview="…"` for each prompt it queues.
  The sign-in and catalog lines are written when `oh-fx login` or `oh-fx setup` runs the activation, because both configure the trace log. `oh-fx provider` does not configure it, as upstream's `fx provider` does not (`activateProviderSelection` in cli_surface.zig loads settings without `debug_trace.configureFromEnv`), so neither line appears from it, as with upstream's. The prompt preview has secrets masked before it is cut to 120 bytes, where upstream writes the prompt's first bytes as they are. The terminal probe, theme and transcript depth lines come with the shell's trace dependency. `ask subagent host unavailable` comes with the interactive subagent host line. Some lines are not written: the sessions v2, notification sound, legacy process migration and stale shell handle lines come with their features. The usage flush, title spawn, recently verified credential, capture and fresh-session checkpoint lines cannot happen, because oh-fx saves usage per request, spawns titles with tokio, keeps no verification window, records calls in memory and discards a pristine session.
- The clipboard writes upstream's `host` lines when its command cannot be spawned, its input cannot be written or is missing, it cannot be waited for, or it exits unsuccessfully with its exit code or signal, and the URL opener writes upstream's `core` lines when its launcher cannot be started or exits unsuccessfully. A spawn names `AccessDenied` when a `PATH` entry holds the command without execute permission and no entry can run it, and otherwise the last entry's error, `FileNotFound` or `NotDir`, as upstream's search does. oh-fx bounds a copy at 5 seconds, so a copy that does not finish in time writes `clipboard copy wait failed err=Timeout`, or `clipboard copy write failed err=Timeout` while its input is still being written, where upstream waits for the command. A URL opened without a bound reports its launcher's exit from a background wait, after oh-fx has already returned. The file clipboard lines are not written, because `/trace` copies the report's text, as recorded above.
- Captured commands write upstream's `core` lines:
  - `command runner explicit environment=… shell=…`, which names the shell path and never the command;
  - `command termination requested source=cancelled force=…` or `source=timeout`;
  - `command force-killed reason=termination_grace_expired|force_cancel`;
  - `captured command leader completed`, either with the remaining group terminated or during a termination;
  - `command termination settlement expired boundary=post_force`;
  - `command termination became indeterminate boundary=child_term`;
  - `command wait authority unavailable after spawn`.
  Managed executions write `became lost boundary=worker_route`, `stop became lost boundary=settle_deadline` and `termination indeterminate boundary=command_result`. `wait_ready` reports whether oh-fx has seen the leader exit. The cleanup, output drain and cancelled or timed-out phase failure lines come with a follow-up. The terminal and native session lines come after the TTY work lands. The supervisor and launcher lines are not written, because those child processes never configure tracing, as upstream's never do.
- A call oh-fx settles without running it writes upstream's `execution_result` with the reason in place of the execution lines. Arguments that are malformed or not an object write `argument_integrity_rejected` and `result_kind=malformed_arguments` with their `argument_integrity`; a PreToolUse block writes `pre_tool_use_blocked` and its `lifecycle_block` or `lifecycle_failed_closed` result with `argument_integrity=valid`; a call the mode forbids or whose tool refuses its input writes `validation_failure`; a denied call writes `permission_denied` with `user_denied`, or with `review_caution`, `review_evidence_incomplete` or `review_unavailable` when an automatic review holds it; and a call the project gate does not run writes `context_deferred` or `applicable_targets_changed`. A call to a tool oh-fx does not offer, or to a dynamic tool that is not selected, is refused before it runs and writes `availability_failure`, where upstream runs a call to an unknown tool and writes its failure, and a call whose tool panics while it is prepared writes `validation_failure err=Panicked`. Malformed arguments and unknown tools reach these lines only through a transport that passes them on, as upstream's Vercel transport does, because oh-fx's chat-completions and Codex transports refuse them as upstream's do, and its Vercel AI Gateway transport, which passes them on, is not routed yet; nothing registers a PreToolUse hook yet.
- The history lines describe the conversation oh-fx sends, which it keeps as messages where upstream keeps turns that it projects into messages at each prompt. `projection_start` and `projection_end` are written when a turn's first request is built, after `prompt_start` and before `step_begin`, as upstream writes them; `gateway_messages_before` counts oh-fx's instructions, and the turn kinds are read from the messages: a leading summary is `compacted_summary`, a turn that ends with oh-fx's interruption note or is still open for steering is `interrupted`, and an interrupted turn that wrote text and ran no tool is a partial closure. `legacy_tool_history_projected` is written whenever a request sends shell calls from the history in their request form, as upstream writes it, with `terminal=true subagent=false`, because oh-fx's subagent calls need no projection and it reads no legacy `terminal` calls; oh-fx writes it as the request's messages are built, just before `step_begin`, where upstream writes it just after. `assistant_tail_continued` is never written, because oh-fx never builds a request that ends with an assistant message, as [recovery.md](recovery.md) records. `empty_assistant_replay_projected` is written between them, as upstream writes it, and again after a compaction within the turn for the earlier messages it keeps; `message_index` counts the earlier messages oh-fx sends, from the compaction summary when there is one and from the first kept message after a compaction. `native_vision_history_projected` comes with vision routing.
- The gateway lines are those of the transports oh-fx has: the Codex `provider_replay_omitted` line, the provider version lookup lines, the bounded termination lines of the GET that the Codex and gateway model catalogs and the Codex version lookups use, which upstream's gateway catalog request does not write, whose failure names `Timeout`, `ConnectionFailed`, `RequestFailed` or `StreamTooLong`, and the Vercel AI Gateway transport's attempt, request, SSE and resolved model lines, whose timing and missing pool lines are recorded with [the gateway's differences](gateway.md). Upstream's generation usage lines come with generation usage, and the chat-completions transport keeps no reasoning replay, so it writes no replay lines.
- The auth lines are those of the logins oh-fx has. The Codex login writes its session load, storage, refresh, retirement, OAuth rejection and browser callback lines and `credential preparation failed`, and the Grok login writes its session load, logout, OAuth rejection and browser callback lines. Every `err=` and `reason=` is an error name, and a rejected OAuth request names its endpoint, never a token, code or response body. The Codex transport refreshes its login inside the request, so it reports the refresh and the replay to the agent, which writes `credential_refreshed`, `credential_refresh_failed` and `authenticated_request_replayed` with the step's ids, as upstream's orchestrator does; `authenticated_request_replayed` follows the replay's response, including a replay that fails again. A step refreshes the login only when it is due, so `credential_refreshed mode=if_needed` is written only for a due refresh, where upstream asks at every step and writes `credential_refreshed`, or `credential refresh skipped reason=verified_recently` once a request has verified the login, which oh-fx does not track. In the shell, `/login` writes `ChatGPT login failed`, a provider switch writes `Codex login failed`, a failed sign-in writes `login failed source=chatgpt_subscription`, and a browser that does not open writes `login browser launcher failed`. `provider sign-in failed` is not written, because upstream writes it only from `fx login` and `fx provider`, which do not configure the trace log, and neither do `oh-fx login` and `oh-fx provider`. The lines of sign-ins and sources oh-fx does not have come with them: the Vercel sign-in, team, stored API key and ACP credential lines, the Grok refresh and in-shell Grok sign-in lines, and the startup credential worker, source inventory, credential preference and resumed-credential lines of upstream's multi-source credential runtime, since oh-fx prepares the Codex login directly. Upstream's OAuth callback timeout setup lines are not written, because oh-fx bounds the callback with async timeouts rather than socket options.
- `/trace` writes its report to `$TMPDIR/oh-fx-trace-<date>-<time>-<hex>.md`, titled `# oh-fx trace`, where upstream writes `fx-trace-…` titled `# fx trace`. It copies the report's text with the composer's clipboard command, `pbcopy` on macOS and `xclip -selection clipboard` on Linux, where upstream puts a reference to the file on the macOS pasteboard through `osascript` and copies nothing elsewhere. The outcome notices keep upstream's wording and platform split: a failed copy reports `Clipboard copy failed. Trace saved at <path>` on macOS and `Trace saved at <path>` elsewhere. oh-fx's transcript has no notice that a later one replaces, so the report is built on a worker thread without upstream's `Preparing trace...` row, and only the outcome notice appears.
- The report's Session Title section shows the session-title setting, the current title, masked, and the background generation that is running or its last outcome, with upstream's `none`, `installed`, `dropped` and `failed` statuses and reasons, and Problems names a failed or dropped generation, as upstream's do. The generation writes upstream's `title_generation` and `title_generation_apply` lines, and `title_generation_dropped reason=deinit` when the shell stops a running generation; `transport_error` details name oh-fx's error code. Only Codex has a title model, so only Codex sessions generate titles. A generation holds its own session, so one whose session closed is dropped as `no_active_session`, and `session_changed`, `not_writable` and the superseded drop are never reported, because oh-fx starts no generation while one runs and generates titles only for a saved session.
- The report's Interrupted Turn section and its Problems entry follow upstream's: when the last turn was interrupted, or a failed reply kept its partial text, they name the call that was running or about to run, its arguments masked and cut to 1,200 bytes, and the tools the turn completed. The arguments are masked before they are cut, so a cut cannot split a secret that masking would hide, and the bytes left out are counted in the masked text, where upstream cuts the raw arguments at a byte offset and masks what it kept. The agent keeps these facts for the turn it just ran, so a resumed session shows no Interrupted Turn section until a turn is interrupted, because oh-fx's saved sessions do not record the running call.
- An interactive session that ends normally writes upstream's `shutdown` stage lines and saves upstream's report, `{"version":1,"recorded_at_ms":…,"total_ms":…,"stages":[…]}` with at most 16 stages, to `$XDG_STATE_HOME/oh-fx/diagnostics/last-shutdown.json` (default `~/.local/state/oh-fx/diagnostics/last-shutdown.json`), where upstream writes `~/.fx/diagnostics/last-shutdown.json`, because oh-fx keeps its diagnostics under its state directory. The directories are private and the file is replaced atomically with mode 0600, as upstream's are, and it holds only fixed stage names and numbers. The next session's `/trace` shows it in the Last Shutdown section, with `(none recorded)` or `(last shutdown report unreadable)` as upstream writes them; stage names read back are masked and kept to one line, and a report whose fields have the wrong type shows upstream's `?` and `-1` where upstream would fail. oh-fx's agent worker owns the session, MCP servers, terminals and credential refreshes, so it marks `persistence_finalized`, `mcp_children_terminated`, `terminals_ended` and `credentials_saved` as it finishes them, before `worker_thread_joined`, where upstream joins its worker first. The stage clock starts when the shell leaves its loop, and `terminal_released` and `background_stops_requested` are marked before the worker is told to stop, as upstream orders them, including on the exit a ready upgrade requests, where the agent now waits for the shell to leave before it closes the session; a clipboard copy still running at exit is waited for after that, so its time counts toward `worker_thread_joined`. When the worker has not finished two seconds after exit, oh-fx stops waiting for it, as it already did, and writes `worker_thread_join_timed_out` in place of `worker_thread_joined` and no `complete`, where upstream waits for its worker; the report is still saved. A session that ends with a terminal or agent failure writes no report, and `ctrl_c_exit_activated` comes with the shell's input lines.
- The report's Tool Calls section lists the calls the tool-call ring recorded, as upstream's Local part does, and its `### Web Search` part lists the status of the last 64 provider searches the conversation keeps, without their names, arguments or results, as upstream's does. The shell takes that list from the agent when a turn ends, a session is resumed or the conversation is cleared, so a search in a running turn appears once the turn ends. As a security difference, the tool-call ring masks secrets in a call's arguments and result before it cuts them to 1,200 and 2,000 bytes, and keeps the masked size as their full size, so the report's `... (N more bytes)` counts masked text. Upstream cuts first and masks only when it writes the report, so a cut that falls inside a credential, such as before the `@` of a URL's `user:password@`, can leave its start unmasked.
- The network ring records each model request the agent, a compaction summary, a session title and a chat-completions review send, and each `web_fetch` target, as upstream's does, and lives in `ofx-trace` because those crates all record into it. A request that fails before an HTTP answer is recorded with oh-fx's error code, and an HTTP failure's `bytes=` counts oh-fx's formatted error detail, where upstream counts the raw body. Codex and Vercel AI Gateway reviews are not recorded, as upstream sends them past its recording funnel.
