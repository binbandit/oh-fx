# Trace log and `/trace`

- The trace log reads `OH_FX_TRACE_LOG`, `OH_FX_TRACE`, `OH_FX_TRACE_STDERR`, and `OH_FX_TRACE_SCOPES` in place of upstream's `FX_TRACE_LOG`, `FX_TRACE`, `FX_TRACE_STDERR`, and `FX_TRACE_SCOPES`, as every oh-fx variable takes the `OH_FX_` prefix. `OH_FX_TRACE` writes to `$XDG_STATE_HOME/oh-fx/logs/trace.log` (default `~/.local/state/oh-fx/logs/trace.log`) where upstream writes `~/.fx/logs/trace.log`, because oh-fx keeps its logs under its state directory, and without a profile it writes `/tmp/oh-fx-trace-<ms>.log` where upstream writes `/tmp/fx-trace-<ms>.log`. The interactive session, `ask`, `permissions`, and `doctor` configure the log when they load the profile, as upstream configures it when it loads its startup state. The log lives for the whole process, so there is no shutdown that would let a later configuration replace it.
- Text cut to a byte limit for the trace, such as a compaction ring detail or a provider error preview, ends at a character boundary, where upstream may cut inside a UTF-8 sequence. The trace line still writes every byte outside printable ASCII as `\xNN`, as upstream's does. Secrets are masked before anything is cut: a provider error preview is masked whole and then cut, as upstream does, and, as a security difference, the report's Trace Tail leaves out the partial line at the start of its 6 KiB window, where upstream masks that partial line as it is, so a window that starts inside a credential, such as after the `https://` of a URL's `user:password@`, cannot leave its end unmasked.
- `/trace` writes its report to `$TMPDIR/oh-fx-trace-<date>-<time>-<hex>.md`, titled `# oh-fx trace`, where upstream writes `fx-trace-…` titled `# fx trace`. It copies the report's text with the composer's clipboard command, `pbcopy` on macOS and `xclip -selection clipboard` on Linux, where upstream puts a reference to the file on the macOS pasteboard through `osascript` and copies nothing elsewhere. The outcome notices keep upstream's wording and platform split: a failed copy reports `Clipboard copy failed. Trace saved at <path>` on macOS and `Trace saved at <path>` elsewhere. oh-fx's transcript has no notice that a later one replaces, so the report is built on a worker thread without upstream's `Preparing trace...` row, and only the outcome notice appears.
- The report's `version` line has no commit in parentheses, because oh-fx builds carry only their release version, whose dev number already names the commit on `main`, and `build` says `Debug` or `Release` where upstream names its Zig optimize mode. The active-turn problem reports `stream_active=true` while a turn runs, since the controller that builds the report does not see the shell's stream state.
