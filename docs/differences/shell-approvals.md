# Interactive approval and question panels

- The interactive approval panel shows a shell command as upstream does: the Command kind, upstream's question, a reason row that names the host of the earliest `http://` or `https://` URL in the command, "This command may make a network request to <host>.", or stays blank, and the complete command after `$ `, wrapped at word boundaries over as many rows as it needs, with line feeds kept as row breaks and every other control made visible. Upstream puts a `# shell.run profile=… shell=…` line in front of every command, inside the command block, so a command whose first line is `# shell.run cwd=…` reads as a header there. oh-fx draws the `# shell.run` line dimmed on rows of its own above the `$ ` row, where no command row can start, and always names the resolved working directory, followed by `profile=clean`, `tty=true`, and `shell=…` when the command runs with the clean profile, in a terminal, or with a shell the call names, never the account's login shell, which no call argument can change. A `cwd` or `shell` value holding anything but letters, digits, and `/._-+,:@%` is shown in shell single quotes, so a directory named `x cwd=/home/u/proj` cannot pass for another setting, here and on the second choice. The URL is the earliest `<letters>://` anywhere in the raw command text, comments and quoted strings included, and its word runs from the nearest whitespace or `;`, `&`, `|`, `(`, `)`, `<`, or `>` before it to the next one after it, without reading quotes. A host is named only when that word is plain, holding no `\`, `'`, `"`, `$`, backquote, or control character, or is exactly one `'…'` or `"…"` string, which may hold those delimiters, with no `\`, `$`, backquote, whitespace, or control character inside. Otherwise the shell's quoting, escapes, line continuations, or expansions could change the word, and the reason says the command may make a network request to a host that cannot be determined; a later URL is never named in its place. The host is what follows the last `@` of the authority, which ends at `/`, `?`, `#`, or the end of the word, up to its port, with brackets kept around an IPv6 address and the scheme matched in any letter case, so `"https://good.example;@evil.example/"` names `evil.example`. A URL whose host is empty, such as `echo https://` or `cat file:///etc/hosts`, names nothing and the next URL is used; `http` and `https` skip extra slashes before the host first, as upstream does. A host name with non-ASCII characters is shown with them as `\u{…}` escapes and called out as such. Upstream looks only for `http://` and `https://`, names the first `https://` URL even when an `http://` one comes earlier, matches the scheme in lower case only, ends the host at the first `:`, quote, or metacharacter whether quoted or not, and so names `github.com` for `https://github.com:x@evil.example/` and `good.example` for `'http://good.example;@evil.example/'`. Input for a running command is shown whole after `> `, with its controls made visible, below the progress title that names the command, which upstream leaves out of its request. A `read_file`, `glob_files`, or `grep_files` call outside the workspace is named in upstream's permission label form, `read_file <path>`, but with the canonical path the gate resolved, made terminal-safe from its raw bytes and shortened from the front only as far as the file name stays whole, where upstream shows the path the model wrote. A `write_file` or `edit_file` change is shown in upstream's file review, described below. A request that names no command, file, or target shows its progress title followed by its arguments preview, `<title> · Arguments for this request: <preview>`, as upstream shows a dynamic MCP tool's arguments, but wrapped over as many rows as it needs, so a preview too long for one row is reviewed like a tall command, scrolling where the panel does not fit, before a yes is accepted. Upstream cuts it to one row with `…` and accepts a yes on the cut row. When the preview itself was cut at 4 KiB, the panel shows the progress title and "Its arguments are too long to show in full, so it can only be denied." and offers only "3. No"; upstream shows the cut preview and accepts a yes. The preview is already terminal-safe and is not escaped again. Shell `interact` and `stop` requests are named by their progress title, as `ask`'s blocked-action guidance does, where upstream shows its permission label. Its reason line says oh-fx instead of fx. Tab on `1. Yes` or `3. No` opens upstream's feedback draft on that row, `1. Yes, and tell oh-fx what to do next` or `3. No, and tell oh-fx what to do differently`, saying oh-fx where upstream says fx, and on a file review `Apply once, …` or `Don't apply, …`, edited with the composer's editing keys, and the hint offers `tab amend` while such a choice is selected. Tab on the remembering choice moves to the next choice, the arrow keys move between the choices and keep each draft, and left and right move the choice while no draft is open, as upstream. A draft holds one line, so a paste into it joins its lines with spaces. The selected choice's draft is sent with the answer, and the agent shows it as a user turn below its call and adds it to the conversation as a user message after every result of the step, as upstream does. The feedback is saved with its call's result as upstream's `permission_feedback`, so a resumed session shows it again and gives it to the model after the step's results, as upstream does.
- The second choice names exactly the grant in the request's `scope.always`: "Yes, and don't ask again for this exact command in <directory>" for a shell command, upstream's wording followed by the resolved working directory the grant binds, which upstream binds without naming it, and then the `profile=clean`, `tty=true`, and `shell=…` parts the grant binds; "Apply + allow workspace file access for this session" or "Apply + allow file changes under <directory> for this session" for a file change, upstream's wording; and "allow reads under", "allow name searches under", or "allow content searches under" a directory "for this session" for the external reads and searches upstream would offer as "don't ask again for this request". A directory is shortened from the front when the row is too narrow, keeping its last name whole, and a yes is refused while it cannot be. The choice is offered only when `scope.always` names a grant, and answering it records exactly that grant. A request that would remember nothing, such as a shell `interact` action, shows "1. Yes" and "3. No" without a second choice, keeping each choice's number as upstream does when it shows only some of its choices, and 2 does nothing; upstream offers the second choice on every approval.
- The approval panel accepts a yes, by 1, 2, or Enter on a yes choice, only once a frame has shown the request's action and every choice in full at the current terminal size, or for a file change the rows the file review below requires, and only 500 ms after that frame has been written out to the terminal, so time spent blocked on a slow terminal does not count, after the last key typed at the prompt, after the last 1, 2, or Enter on a yes pressed before then, and after the end of the last paste, so keys typed before the prompt appeared, typed on without reading it, held down, or pasted, never approve it. Any resize signal, even one that ends at the size the prompt was shown at, redrawing the whole screen after a theme change or a resume from job control, and losing the terminal size, by a terminal too small to draw on or a size that cannot be read after a resume, start the review and the 500 ms over. Upstream holds a yes back this way only for file changes, waiting for a frame that shows the file and every choice, and has no delay. No, Ctrl+C, and Esc answer at once, as upstream. Text typed at the prompt goes into the hidden draft, and a digit typed among it joins the draft, where upstream drops text typed at a prompt, unless a feedback draft is open, which takes it as upstream does. Keys typed into a feedback draft count as keys typed at the prompt, so a yes waits 500 ms after the last of them, where upstream has no delay. As upstream does, a paste that begins while the prompt is open is discarded and never decides it unless a feedback draft is open, which it joins, and a paste that began before the prompt appeared still reaches the hidden draft.
- When the approval panel does not fit above the status line, the prompt takes the full height of the terminal in upstream's command review layout: the header, question, and reason, the action in a window, the choices, and a hint, or only the window and the choices on a terminal shorter than that layout. oh-fx draws it in the live region, where upstream switches to the alternate screen, and pgup and pgdn scroll the window, where upstream scrolls with the mouse wheel, since mouse reporting is not enabled. Every request but a file change uses it when it does not fit, where upstream uses it for commands only. Until every row of the action has been on screen at the current size, a yes is refused and its choices are drawn as upstream draws a blocked file-change choice, with `!` and `· scroll to review`, or upstream's `· resize to review` when even one row of the action cannot be shown. Upstream accepts a yes on a command whose review was never scrolled.
- A `write_file` or `edit_file` approval shows upstream's file review: a blank row and a divider below the transcript, then every row of upstream's full review of the change, each changed line with its number and `+` or `-`, five lines of context around each run of changes, `N unchanged lines ⋯` for the lines between, and `(trailing newline added)` or `(trailing newline removed)`, a line too long for a row wrapping under its text, then upstream's controls: a dotted divider, `Permission needed · Review change` with the action and its `+N  -M` counts, the path and `Apply this change?`, `Apply once`, `Apply + allow …`, and `Don't apply`, a divider, and the hint, spaced or compact as upstream lays them out by height, and only the choices below eight rows. Colours, gutters, and the number column follow upstream's review rows. Heights are measured against the rows above the status line, where upstream measures the whole terminal. A change that would leave the file as it is uses upstream's `Review file`, `Check`, and `Reveal` wording, though no permission mode asks about one today. Upstream draws the transcript, the review, and the controls as one document on the alternate screen, opened at its end and scrolled with the mouse wheel. oh-fx draws the review in the live region below the transcript, which stays in the terminal's scrollback instead of being drawn again, and a review that does not fit opens at its end in a window above controls that stay in place, without the blank row and divider, and scrolls with pgup and pgdn; one that stops fitting after a resize opens at its end too. As upstream requires, a yes waits for a frame at the current size that shows the header with the file name whole and every choice in full, while a changed line or the notice is on screen or has been on screen for the request before, so a long change opened at its end can be approved without paging through it; every other request still needs every row of its action seen. Until a changed line has been seen the yes choices are marked with `· scroll to review`, where upstream says `· resize to review` though its review scrolls too, a terminal too narrow to draw a line of the review refuses a yes with `· resize to review`, where upstream fails the screen and denies the request, and so does one too narrow for a choice, where upstream refuses the yes without marking the choices. A change to an existing file outside the workspace, which is not read before approval, shows a notice that its change cannot be shown in place of the review, and a new file there shows the content it will create. File content and paths pass through the approval panel's terminal-safe encoding, so controls, escape sequences, invalid UTF-8, and invisible or ambiguous-width characters show as escapes.
- A second approval request that arrives while the panel shows one replaces it, and the shell answers the displaced request with a denial, so its call never waits for an answer that cannot come. Upstream's worker asks for one approval at a time.
- `ask_user_question` waits for its answers through the controller, which hands each question to the shell with the turn that asked it; a question for a turn the shell no longer shows is answered as cancelled, and one that arrives while the panel shows another replaces it and cancels the displaced one. Upstream's worker holds one pending question. A question cancelled with its turn, by Esc on an empty answer, Ctrl+C, or any other cancellation of the turn, returns upstream's `(user cancelled the question)` result, which the next request carries, where upstream discards the call's result once the turn is cancelled. The question panel replaces the composer without upstream's divider rows, which the live-region renderer does not draw around the composer either, and its trailing blank row is the gap above the hint row; a panel taller than the terminal scrolls its top rows off the screen instead of being clipped to a footer band. Arguments holding a number beyond a 64-bit float's range, or arrays and objects nested more than 128 levels deep, fail as invalid arguments and record no question in `ask --json`, where upstream reads them. The `Other` answer editor and an answered question's transcript rows show C1 controls and the line separator and bidi controls escaped, as every row draws them, and wrap and move the cursor by the escaped width, where upstream writes those characters to the terminal raw.
