# Subagents

- The subagent host runs each child work item as a task of the process's async runtime, where upstream gives it its own thread, and keeps children, their conversations, and each child's last result in memory for the life of the host until child sessions are saved, within upstream's limit of 256 children. Upstream saves each child as its own session, reads a repeated call's result back from it, and keeps the parent's registry in `subagent/children.json`, so its children outlive the process.
- A plain `message` to a named agent that is still working is refused with `child_busy`, where upstream queues it as feedback for the child's next safe boundary and answers with a `queued` receipt. Steering a running child needs the turn loop's steering boundary, which has not been ported.
- A parent turn cancelled while it waits for a child cancels the child and ends the call at once with `child_cancelled`; upstream ends the call without a result.
- A creation-time `model` override reaches the child as given. Upstream resolves it against the AI Gateway catalog for gateway connections and rejects an unknown or ambiguous name with `unknown_model` or `ambiguous_model` and candidate IDs; oh-fx has no gateway connection, and upstream passes overrides through unchanged for every other provider.
- A failed child's diagnostic names oh-fx's failure: `provider_http_error: API request failed · <status and detail>` (`API access denied` for 401 and 403) for an HTTP failure and `agent_turn_failed: <code>` with oh-fx's turn failure code otherwise, and its partial result is the text the child streamed after its last tool call. Upstream reads the partial text back from the child's saved session.
- `ask` and the interactive session offer `subagent`, after `shell`, only when they save their session, as upstream offers it only with a session store. Each child is saved as its own session beside the parent, as upstream's first session store does: its `session.json` says `subagent_child`, its user events name the work they belong to, its `subagent/owner.json` names the parent, and the parent's `subagent/children.json` holds the registry after every change. As upstream does, a new child's session starts only after the registry naming it is saved, so a registry that cannot be saved fails the call without leaving a session behind or touching an existing child. If the child's session then cannot start, the call fails and the registry is saved again without the child, where upstream keeps the child and starts its session on the next call. Work whose finished state cannot be saved returns `state_unavailable` to the parent instead of its result, as upstream's does, and a reply the child's own session cannot save fails the work with `agent_turn_failed: SessionCommitFailed`, keeping the reply as its partial result. Child sessions are left out of listings and `-c`, and resuming one directly is refused with upstream's message. A session reopened with `-c`, `resume`, or the picker takes its children back from that registry, as upstream does: work an earlier process left running is recorded as interrupted, a named agent continues from its saved conversation and settings, and a repeated operation replays the reply saved in the child's history. A child whose last work a mid-turn compaction left open, with a recovery checkpoint pending, reopens with that work committed as interrupted, as `ask` commits it before a new prompt, so its next work is saved under its own work id. While a child's approval is pending, the registry records its work as `awaiting_approval` until the work ends, as upstream does, and a restart records that work as interrupted too. A child is the parent's agent without `subagent`: the same provider, system prompt, project instructions, skills, capabilities, and MCP tools, a runtime context that is not interactive, and a permission policy at the parent's mode when the request arrived, with the same reviewer. A child advertises every tool of the connected MCP servers, as its parent does, read from the live catalog before each of its steps, and its MCP calls are admitted by its own policy, which also admits a tool the parent allowed for the session, as upstream resolves a child's MCP calls against the parent's grants. Upstream captures the MCP view its parent may use when the work is admitted and checks each call against that view and the live one; oh-fx's parent sees every connected tool, so a child sees the same set, and a tool that changed since it was advertised is refused as it is for the parent. The parent alone reports the catalog's schema and server-instruction notices, so a child never takes them from the session. The child's policy also admits what the parent's session grants admit at the time of each call, as upstream resolves a child's calls against the parent's grants, and an Always answer to a child's request is remembered by that child, not by the parent. In the interactive session a new child takes the model, reasoning effort, and Fast mode the session has at that moment, after any `/model` or `/fast` switch or model menu pick, and `/clear`, `/new`, `/reset`, and a session resumed from the picker forget the children of the session they leave, as upstream's fresh session starts with none and its resumed session takes only its own children back. A child's `web_fetch` prints no `Fetching` or `Converting` line, since `ask` shows a child's work only through the parent's `subagent` progress line.
- In `ask`, a child's call that needs approval fails the child's turn with `NonInteractivePermissionRequired`, which the parent receives as `child_failed`, as the parent's own calls fail there. Upstream registers the child's request with its approval registry, which nothing answers in `ask`, so the child waits until the run is cancelled.
- In the interactive session, a child's call that needs approval is asked on the parent's prompt during the parent's turn, with upstream's `Subagent <id> needs permission` header in place of `Permission needed · Choose one`, or of `Permission needed · Review change` and `Permission needed · Review file` on a file review, and the same body and choices as the parent's own request, so a child's `write_file` or `edit_file` shows the same file review and diff. The id is the child's session id, as upstream's is. Requests wait behind the one on screen: children's in the order they arrived, as upstream shows the first pending child request, and the parent's own ahead of any child's. Esc denies a child's request without cancelling the parent's turn, as upstream does, and a child's request raised while no parent turn runs, or still waiting when the turn ends, is denied.
- In the interactive session, a working child's row shows the child's model under it, followed by its reasoning effort when one is named, as upstream's subagent status line does with the statusline items off, and the line stays when the row settles. The effort shows without checking that the model supports it, where upstream hides an effort the model's capabilities do not list. The line is reported once, when the child starts its work, where upstream refreshes it as the child's input tokens change, which shows only with the context statusline item that oh-fx does not have yet.
