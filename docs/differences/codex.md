# Codex transport and model catalog

- The Codex transport honors `Retry-After` on HTTP errors, as custom connections do, where upstream's Codex transport ignores it.
- The Codex transport waits for the response head without a limit once it has connected, as upstream's does. It reads an error response's body for at most 30 seconds, as custom connections do, where upstream's Codex transport reads it without a limit.
- The Codex transport refreshes a due access token before each request and, after a 401, refreshes once and resends the request. Upstream makes the same decisions in its agent loop. A Codex 401 adds `Run oh-fx login codex to sign in again.` after the authentication failure line.
- A Codex reasoning item can arrive more than once in a stream: in `response.output_item.done` and again in the `response.completed` output. The live OpenAI Responses API encrypts `encrypted_content` afresh each time it emits an item, so the copies carry different ciphertexts. oh-fx accepts a later copy when every field other than `encrypted_content` matches the first completed copy, and replays the first copy that carries a non-empty ciphertext; an empty `encrypted_content` counts as none. A copy that differs in any other field fails as `ResponsesReasoningConflict`, whether or not either copy carries a ciphertext. The comparison uses a digest of the first copy's other fields, with object keys in sorted order, so it costs what the later copy costs to read and keeps 32 bytes per item. The first copy is kept because its bytes already count toward the provider-state limit, because replay then does not depend on whether the terminal event repeats the output, and because the ciphertext is opaque to oh-fx, so a later copy cannot be shown to be better. Upstream compares copies byte for byte, so a stream that re-encrypts, as the live Responses API does in every response that carries reasoning, fails there; it also accepts a copy without ciphertext whatever its other fields say. Whether chatgpt.com's Codex endpoint re-encrypts the same way could not be checked from the network these changes were tested on.
- Codex requests carry the saved session's id in the `session-id` and `x-client-request-id` headers and omit both under `--no-save`, as upstream does. A request with the same messages, tools, reasoning effort, and Fast mode matches upstream's body byte for byte.
- The Codex model catalog does not have to list `gpt-5.6-luna`. Upstream rejects a catalog without its permission reviewer and session title model as malformed, which broke its sign-in for two days when OpenAI retired the previous reviewer model. oh-fx reviews Codex calls and generates session titles with that model too, but keeps the catalog and sign-in working without it: once OpenAI retires the model, each review fails as the provider rejects it, so the call is held, or asked about in the interactive session, as when any other review fails, and each title request fails, which leaves the session untitled.
- The Codex client version that model catalog requests send is cached in `$XDG_CACHE_HOME/oh-fx/provider-versions/codex.json` instead of `~/.fx/provider-versions/codex.json`. A cache file that group or others can access is ignored and looked up again, where upstream reads it.
- `oh-fx models` prints each Codex model id through terminal-safe encoding, so control characters or bidi overrides in a catalog response cannot reach the terminal; `--json` keeps the ids as sent. Upstream prints them as received.
