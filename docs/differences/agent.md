# Agent turn loop

- The turn context reads git facts from the repository that encloses the workspace, where upstream reads only `<workspace>/.git`, and reports a tracked file as dirty only when it is missing or its size differs from the index, never from its modification time alone.
- Until `read_tool_result` lands, a tool result over 64 KiB is cut at upstream's `--no-save` truncation marker even when `ask` saves its session, where upstream shows a saved session's results over 16 KiB as a 4 KiB preview with a `read_tool_result` handle. A saved session keeps each result as the model saw it in `tool-results/`, written when the turn is saved and marked `complete`, so a resumed session sends the model the same text; upstream writes the complete output when the tool returns. Its `stored_bytes` is the length the model saw and its `output_bytes` the length the tool returned, as upstream records it. `read_file` reports image files as binary content until tool image attachments land.
- A root turn whose prompt reads as English prose, Latin script with an English authority word such as `the`, `please`, or `why`, and names no language or translation, expects an English reply, as upstream infers it. The reply's text is held until its prose, with code spans, quoted text, and bracketed text left out, shows Latin script, or until the reply is complete when the instructions or an earlier assistant or tool message read in another script. A reply clearly in another script is dropped and requested once more with upstream's correction note after the conversation, a reply that calls tools keeps its calls and loses its prose, and a second clear mismatch ends the turn with upstream's notice and `ResponseLanguageMismatch`. Steering applied during the turn that does not itself read as English prose, such as `Answer in Japanese and keep it short.`, lifts the expectation for the rest of the turn; upstream keeps the expectation its first prompt set, so it would hold, retry, and fail the Japanese answer that steering asked for. Subagent children get neither the response language instruction nor the check, as upstream. oh-fx sends the correction as its next model request, so steering waiting at that boundary joins it and the provider attempt budget is not consulted; upstream repeats the request inside its attempt loop and gives up on the correction once the step's attempts are spent.
- A tool batch that repeats malformed arguments, a shell request correction, or a shell failure ends the turn as upstream does, unless steering is waiting, which continues the turn. That batch still counts for every one of these checks, so the next batch is compared with it. Upstream moves to the steered step before its later checks record the batch (`src/core/agent/runtime/orchestrator.zig`, after `terminal_validation_retry.finishBatch()`), so a shell failure from the batch before can still end the turn after a steered batch that did not repeat it.
- A panic while selecting scoped project instructions fails every call of its batch and the turn with `ProjectContextFailed`, as upstream settles the batch as failed when that selection fails.
- A panic in tool code fails only its own call with a `tool_execution_failed` result whose message is `Tool execution panicked`, and the rest of the batch still settles. This covers preparing a call, completing its preparation, projecting the target it acts on, describing it, inspecting its file mutation or whether it refuses to run, and executing it, including the part of `execute` that runs before it returns its future. A panic while dropping a call that never ran, because its inspection panicked, it refused to run, it was held for review, or an approval or a cancellation stopped the batch first, is discarded, and so is a panic while dropping a panic's payload. A panic while writing a call back into the history keeps the arguments the model sent. The agent finds a tool by the spec it read once when it was built, so it never calls a tool's `spec` again while dispatching. Upstream is written in Zig, where a panic ends the process. A tool error there becomes `Tool execution failed` with the error's name.
- The assistant intro filter matches "oh-fx" instead of "fx".
- A prompt submitted while a turn runs steers it as upstream's does: while the model streams it ends the model step at once and the turn continues with the partial reply and the prompt, wrapped in upstream's `<user_steering>` text; while a tool or a compaction runs it waits for the next model step, or for the final answer, which then continues the turn; several prompts go together in the order typed; a prompt with skills ends the turn at the next model step and runs as its own turn; and Up in an empty composer outside a history episode pulls back the newest steering still waiting. Steering that the turn did not take before it ended, including after Esc or Ctrl+C, runs next as a continuation turn, wrapped the same way, and so does a prompt submitted during `/compact`. oh-fx shows every prompt waiting on the running work in the held banner, one line each, including steering about to end a model step and prompts queued after a cancel; upstream shows steering in the banner only while it waits for a tool or a compaction, up to two lines each, and shows steering about to end a model step as a pending prompt card at the end of the transcript.
- oh-fx ends a steered model step by cancelling a token of its own, a child of the turn's, so steering never ends a capability lookup, skill loading, or project context gathered at the start of a turn; they finish and the steering rides the first model request. Upstream sets the shared cancel flag, which also interrupts that work, retries it, and then sends the same request. The shell sends prompts to the agent over its command channel, so Up pressed before the agent has taken a just-submitted prompt finds nothing to pull back and recalls prompt history instead.
- A turn that steering with skills ends at a model step, or that such a prompt interrupts while the model streams, is saved as interrupted, as upstream saves it, and ends with the cancellation row, as a resumed session shows it, since oh-fx saves no cancellation origin. Upstream records the origin and shows no cancellation for it.
- Steering keeps the order it was typed in across a prompt that must run as its own turn: plain steering typed after a prompt with skills, or behind any prompt still waiting for its own turn, waits for that prompt and does not end the model step. Upstream's continuation turn takes plain steering queued after such a prompt ahead of it. Steering that ends the turn's last allowed model step is not taken into the turn; the turn stops at the step limit and the steering runs next as a continuation turn, where upstream adds it to the stopped turn, which no model step then answers.
- A completion that carries provider-executed calls never runs them, as upstream does: each call's provider result becomes its tool result in call order, a failure when it holds upstream's tool-failure shape, and the local calls around it run as before, apart from any parallel group, as does any call that carries a provider result. A stop whose answer follows only provider-executed calls keeps their results and ends the turn with the answer, with the provider state split between the two as upstream splits it; without an answer, the turn asks again. A provider-executed call with malformed JSON arguments, or without a provider result, fails the turn before any call runs, as `MalformedProviderToolArguments` or `MalformedProviderResultIdentity`. A provider-executed `exa_search`, `parallel_search`, or `perplexity_search` call shows upstream's search row, `Searching` and then `Searched` with its query and up to three allowed and blocked domains, and a resumed session replays the `Searched` row, or `Completed tool call` when the saved arguments are not an object; other provider-executed calls show no row, as upstream does. Upstream's duplicate call identity check, its observed search counts, and its recovery that keeps provider results confirmed before a stream failed arrive with the gateway transport.
- Provisional tool progress is opt-in through registered presentation metadata. Upstream publishes it for every registered tool except write, edit, ask and terminal operations. The port supplies read, search, skill, web fetch and subagent metadata; other registered tools without that metadata publish no provisional line until their presentation is ported.
