# Vercel AI Gateway

- The gateway route reads upstream's first two credential sources, `VERCEL_OIDC_TOKEN` and then `AI_GATEWAY_API_KEY`, each ignored when blank, and `OH_FX_AUTH_MODE=host-managed`. The fx login, the stored key and the `credential_source` choice come with `oh-fx login` and `oh-fx setup`. Until then the missing-credential message names only `AI_GATEWAY_API_KEY`, where upstream's also names `fx login` and `fx setup`, and the interactive shell stops at startup with that message, where upstream opens signed out with `/login` and `/provider` guidance.
- A saved session whose provider is the gateway resumes on the gateway only when one of those sources is present. Otherwise it continues with the selected provider and its rebind notice, as a session saved with a provider oh-fx cannot use does.
- `OH_FX_E2E_GATEWAY_CHAT_URL` and `OH_FX_GATEWAY_CHAT_URL` replace upstream's `FX_E2E_GATEWAY_CHAT_URL` and `FX_GATEWAY_CHAT_URL`, and the first outranks the second, as upstream's does. Both take only a loopback `http://` URL with a port. An end-to-end URL that is not loopback is ignored, as oh-fx's other end-to-end overrides are, where upstream fails the request with `InvalidE2EGatewayUrl`.
- The gateway's model catalog has not been ported, so the route knows no model's context window, output limit or image input. Requests carry no `maxOutputTokens`, a turn with an image stops as it does when a catalog is unavailable, and context use is not tracked. Upstream reads these from its catalog, and from `vercel_model_policy`'s context windows when the catalog is unavailable.
- Upstream's `review_model` setting and `FX_REVIEW_MODEL` choose the reviewer model for every provider. oh-fx does not read either yet, so the gateway reviews with `openai/gpt-5.6-luna`.
- `oh-fx status` lists the Vercel AI Gateway among the connected providers only when an environment source is present, since oh-fx has no Vercel login or stored key to find.
- Requests name oh-fx where upstream names fx: `User-Agent: oh-fx/<version>`, `X-Title: oh-fx`, and `HTTP-Referer: https://github.com/binbandit/oh-fx`, and a `zai/glm-5.2` request body carries `"headers":{"user-agent":"oh-fx/<version>"}`. Every other header and body byte matches upstream's agent request.
- Every tool description, including an MCP tool's, is cut to 1,024 bytes at a character boundary, as oh-fx's other transports cut them; upstream cuts only built-in descriptions, at a byte offset.
- The transport makes one attempt per request and leaves retries to the agent, as upstream's agent path does. Upstream's transport-owned callers, such as compaction summaries, also retry HTTP 429 and 5xx answers and dropped connections inside the transport, for up to three attempts; oh-fx's gateway transport does not.
- An error response's body is read up to 64 KiB and for at most 30 seconds, as for custom connections; upstream reads it whole. The response head is awaited without a limit, as upstream's agent path does, and the ten-minute stall watchdog runs once the head has arrived.
- A stream that ends before its `finish` event, at `[DONE]` or when the body ends, fails as `StreamInterrupted` and is retried as a network interruption, under `⚠ Network interrupted · StreamInterrupted`, where upstream labels the retry `Response ended early`; oh-fx's recovery has no response-interruption cause yet. A `length` finish fails as `OutputTruncated`, as on oh-fx's other transports.
- Tool calls follow upstream's reconciliation of streamed input, final calls and provider results, with these differences:
  - A tool call whose input is not valid JSON keeps the provider's text, which the agent diagnoses and saves as `{}`, where upstream replaces it in the transport. A final `input` that is a bare number, boolean or `null` reaches the agent as that value and is refused as non-object arguments, where upstream refuses it as malformed ones; a provider-executed call with such input fails as `MalformedProviderToolArguments`, as upstream's does.
  - Each streamed call announces its start once, when its input starts; upstream announces it again with a label taken from the first string in its arguments, which oh-fx's tool rows do not take.
  - A call the provider streams under one id and finalizes under another keeps its provisional row under the streamed id, since oh-fx's tool calls carry no provisional id; the replay and the next request use the final id, as upstream's do.
  - Calls with malformed or duplicate identities, provider results that name no single provider-executed call, and missing final results fail the request with upstream's error names (`MalformedProviderResultIdentity`, `MalformedAuthoritativeToolIdentity`), where upstream's agent rejects the completion; the turn fails as upstream's does.
  - A final call that reuses the streamed id another final call was reconciled from fails as a duplicate identity (`MalformedAuthoritativeToolIdentity`). Upstream admits it, folds its provider metadata into the other call's replay part, and replays it without its own.
  - Provider replay counts 96 bytes per part toward its 4 MiB limit, where upstream counts its own record size.
- The gateway's permission reviewer retries HTTP 408, 425, 429 and 5xx answers, in-stream provider errors and dropped requests once, and gives up on other statuses, content filters, refused or unreachable connections and stream errors, as upstream's does. A connection that times out while connecting is not retried, where upstream retries it once, since oh-fx's connection errors do not tell a connect timeout from a refused connection. The review's pending tool result is sent as a plain `text` result, as upstream's gateway review sends it; the other transports send the same text.
- A provider error reported in the stream is masked, with the key and anything that looks like a credential hidden, before it is cut to 600 bytes, and the cut ends at a character boundary; upstream cuts the raw detail at a byte offset. The resolved model a response names is masked the same way before it reaches the trace log.
- reqwest connects, sends the body and reads the response head in one call, so the `gateway` trace lines between `before_request_open` and `after_receive_head` are written together once the head arrives, and a failure there is written as `http_open_connect_error` when connecting failed and as `receive_head_error` otherwise, with oh-fx's error code in `err=`. reqwest pools connections itself, so `pool_borrow` and `pool_body_drain` are not written. The lines carry no turn or step ids yet, because a provider request does not carry the step's trace context.
