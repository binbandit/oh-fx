# Session store

- Saved sessions live in `$XDG_DATA_HOME/oh-fx/sessions/<id>`, and the session `-c` reopens for each workspace is named in `$XDG_DATA_HOME/oh-fx/continue/<sha256 of the workspace root>`, where upstream uses `~/.fx/sessions` and `~/.fx/continue`. File names, JSON fields, schema versions, and permissions inside them follow upstream.
- The session store reads only the layout upstream writes today: `session.json` with `schema_version` 4 and `events.jsonl` frames with `schema_version` 3. Upstream also imports sessions written by older fx releases (schema-v3 semantic event logs, which releases 0.0.1 to 0.0.7 wrote, legacy `session.json` snapshots from before its public repository, `latest/`, and `recovery+staging`), accepts frames with `schema_version` 1 and 2, clears the background `run_command` records those releases left, repairs their zero image ids, and reads the `fx-compaction-state-v1` files its earlier compactor saved; oh-fx has never written any of them, and it reads `~/.fx/sessions` only to list the sessions fx saves today, as [sessions](sessions.md) records, so it has no importers yet. These decoders come with the import of fx's sessions. A session folder without `session.json` is reported as `SessionNotFound`, one whose `session.json` is not a JSON object with a `schema_version` as `InvalidSessionFormat`, another version as `UnsupportedSessionSchema`, and older frames as `InvalidConversationFrame`.
- Until the features behind them are ported, session frames and metadata carry upstream's defaults for terminal presentations and subagent children. A frame or `session.json` that sets one of them fails as `InvalidConversationFrame` or `InvalidSessionMetadata` instead of losing the value on resume, and a `recovery.json` checkpoint that sets one, or a provider-executed call's result, fails as `InvalidRecoveryCheckpoint`.
- A tool result's command output replay (`command_replay_ref` and `command_replay_bytes`) and the cancelled command of an interrupted turn (its replay and `command_artifact_ref`) are read and validated as upstream reads them, kept in the log and in `history-cache.bin`, and written back unchanged, so sessions that ran shell commands in fx resume in oh-fx. oh-fx writes no command replays of its own and never reads the `logs/commands` files they name, because its transcript shows no command output under tool rows yet: a resumed shell row shows no output, and a resumed interrupted turn leaves out its cancelled command and keeps its cancellation line, where upstream shows the cancelled command with its output in place of that line. The aborted call's result in a resumed request does not name the cancelled command's replay, which upstream names for `read_tool_result`, a tool oh-fx does not offer yet. A `recovery.json` checkpoint whose tool result sets `command_output_replay` still fails as `InvalidRecoveryCheckpoint`.
- A `write_file` or `edit_file` result's committed file presentation (`committed_file_presentation`: the file's path, whether it was added or edited, its preview lines with their line numbers, its added and removed line counts, whether the preview was truncated, its lifecycle id, and either the previous and new contents inline or the `content_handle` of a `diff-*.json` pack in `tool-results`) is read and validated as upstream reads it, kept in the log and in `history-cache.bin`, and written back unchanged. A resumed edit row names the path the presentation saved, the one the live row showed, which for a file outside the workspace is the resolved target rather than the requested path, and shows the presentation's added and removed line counts after its action, as upstream's resumed row does. oh-fx shows no diff under tool rows, live or resumed, so a resumed edit leaves out the preview lines and the full review upstream builds from the diff pack, which oh-fx never reads, and it writes no presentations of its own, so its own edits resume without line counts. A `recovery.json` checkpoint whose tool result sets `committed_file_presentation` still fails as `InvalidRecoveryCheckpoint`.
- An `interrupted` frame's `cancellation_origin`, which upstream writes only as `compaction` for a turn cancelled while its automatic compaction ran, is read and written back as upstream does: a missing key or `turn` reads as a turn cancellation and is written without the key, and anything but those two names is refused. oh-fx saves a turn cancelled during its own automatic compaction with `compaction`, and a resumed session shows no cancellation line for such a turn, as upstream's resume does. A tool call's `provisional_id`, an identity, and its `final_identity` (`valid`, `absent`, `empty`, or `wrong_type`) are read, validated, kept, and written back in their place in the frame and in `history-cache.bin`. oh-fx's providers report neither, so oh-fx writes `null` and `valid` for its own calls, and a resumed call is sent under its final id as before. A `recovery.json` checkpoint's `user.work_id`, which upstream writes for a subagent child's turn, is read and validated as upstream does (1 to 128 bytes, no NUL), written from the child session's work, and kept when the checkpoint's turn is committed.
- A user prompt's `images` (each with its `id`, `path`, `media_type`, `snapshot_path`, `snapshot_sha256`, `inline_data`, and `source_ref`) and a tool result's `tool_image_handle` are read and validated as upstream reads them, with at most 128 images, a bounded path, a media type of 1 to 256 bytes, and an identity for the handle. They are kept in the log and in `history-cache.bin` and written back unchanged, and oh-fx leaves the `images/` snapshots and tool image artifacts they name as fx wrote them. oh-fx does not attach images to model requests yet, so a resumed session sends such a prompt as its text alone and later requests no longer show the model the images, which upstream sends again. A `recovery.json` checkpoint whose user turn or tool result carries images still fails as `InvalidRecoveryCheckpoint`.
- Turn summaries on `turn_completed` and `interrupted` frames and in a checkpoint's execution memory are read as upstream writes them: a frame's summary takes upstream's defaults for missing fields, a checkpoint's must hold every field with a start that is not negative and an end that is not before it, and committing a checkpoint keeps its summary in the `interrupted` frame. oh-fx writes `null` for its own turns until it records summaries.
- `events.jsonl` frames are read in the forms upstream writes: integers, such as `seq` or a turn summary's `turn_duration_ms`, as JSON integers, enum values as their names, and text as JSON strings. Upstream's typed frame parser also accepts an integer written as a string or as a float with an integral value, such as `"1"` or `1e3`, an enum value written as its numeric tag, except a cancellation's origin, and text written as an array of byte values. Upstream's writer emits none of these forms, so the frames it saves read the same in oh-fx; accepting them would mean porting Zig's coercions, including its 128-bit float parsing, for input that only a hand-edited file holds.
- Session frames keep a tool call's `provider_result` and `provenance` and a result's `provider_native` mark as upstream writes them, and resume restores each call with its provider result and provenance, so a session that ran provider-executed tools upstream resumes in oh-fx. oh-fx writes `provider_native` as `false`, as upstream's runtime does. A Codex request replays a provider-executed call as a function call with its arguments as recorded, unchecked, and never rewrites its call id, as upstream does; a Chat Completions request whose history holds one, or any call with a provider result, fails as `UnsupportedToolProvenance`, as upstream's does. No connection oh-fx supports produces provider-executed calls until the gateway transport arrives.
- A saved turn's file evidence, the `files` of `turn_completed` and `interrupted`, is read, validated as upstream validates it, and kept in the log, so sessions upstream saved with it resume. oh-fx records evidence for its own turns as upstream does: one entry for each `read_file`, `write_file`, `edit_file`, `grep_files`, and `glob_files` result with a usable path argument, the whole-file view of a successful read the model saw untruncated, and `stale` on a read that a later successful write or edit of the same path in the turn replaced. A tool call id that looks like a secret is written as `redacted-` and a digest, as upstream writes it; oh-fx's secret masking recognizes a few more shapes than upstream's. The agent gathers a turn's evidence when the turn ends, keeping the entries of steps a mid-turn compaction removed, and the session saves what the agent gathered. Like upstream, it sends the evidence in later requests as a `Session file evidence from previous tool execution` user message after the turn's tool steps, before any later steering and the turn's reply or closing messages, in live and resumed requests alike. Upstream's `ReadTracker` is not ported: upstream creates one only in `read_file`'s tests, and its production dispatch context leaves it unset, so its snapshots feed no decision.
- A new session holds `session.json`, `events.jsonl`, `session.lock`, and `owner.live`. Upstream also writes `permissions.json` and `usage-v2.json` when it creates a session; oh-fx adds them when session grants and usage are saved. Without a matching recovery checkpoint, a writable open closes a turn left open by a crash with `interrupted` (`failed`), as upstream does.
- An append to the conversation log may end a turn or add a compaction checkpoint only with its last event, so a crash at any byte of an append leaves nothing of it after the next writable open. Upstream's writer accepts a batch with a turn end or checkpoint before its last event, though upstream never writes one.
- A compaction checkpoint whose coverage ends between a tool call and its result fails as `InvalidCheckpointCoverage` when it is appended or read back, and replay fails as `InvalidConversationFrame` on a tool result whose call it did not restore. Upstream's writer checks only calls still pending, so it accepts such a checkpoint, though its compactor never chooses one, and every later replay of that session fails as `InvalidConversationFrame`.
- `ask` and the interactive session save each turn as upstream does: one append with the user message, each tool step, and the reply, closed by `turn_completed`, or by `interrupted` for a cancelled turn and for a failed one with partial text. A failed turn that did nothing is not saved, and a failed one that ran tool steps without partial text is saved as completed with an empty reply. An interrupted turn is saved without the tool call that was running: oh-fx drops a call that did not finish from the turn, as its history does, where upstream saves it so a resumed session shows the model the call was aborted. A tool result's `created_at_ms` is the time its turn was saved.
- A compaction during a turn saves the turn's user message and finished steps and then the checkpoint, whose `covers_through_seq` is the last event the compaction cut covers, as upstream does. The rest of the turn follows the checkpoint when the turn ends, and a resumed session replays from the checkpoint. A compaction whose checkpoint cannot be saved fails the turn and is not applied.
- A checkpoint's cut counts only the turns the conversation log holds. A turn that completed but could not be saved, while the session kept running, is summarized without being covered in the log, and a turn dropped after its checkpoint saved its prompt is covered with the saved turns before the cut, so a resumed session keeps every saved turn the summary leaves out. Upstream counts the cut against the saved turns as if every turn of the conversation had been saved, so after such a failure its checkpoint covers saved turns the summary never held, and a resume loses them.
- Session listing keeps upstream's `.resume-catalog` index in the sessions folder, in upstream's version 6 encoding: one row per session, bound to a SHA-256 fingerprint of the stats of the session folder, its `session.json`, `events.jsonl`, `authority.json`, `authority.pending.json`, and `display.json`, and its `subagent` folder and markers. A listing reuses a row whose fingerprint still matches without opening its session and reads the others on four threads, as upstream does, and a store opened for writing saves the index when a row changed, keeping earlier rows whose sessions still match; a read-only store only reads it. A row is reused only while its session folder holds `session.json` and `events.jsonl` and none of the `authority.json`, `authority.pending.json`, and `display.json` files of upstream's older schema-v3 layout, and only when it holds no preview, display metadata, managed children, or missing workspace root, which upstream writes only for the older layouts it imports; any other row is read again from its session, since oh-fx lists only what it can open, and a row whose session oh-fx cannot read stays in the index unchanged, without rewriting the index on every listing. Listing 200 sessions with 50 MB of logs took 16 ms with no index and under 1 ms once the index was saved (release build, macOS arm64, warm page cache). An entry whose folder listing reports no type is checked with `fstatat`; upstream skips such entries. A new session is titled from the first line of its first saved prompt, as upstream does, unless that prompt is a slash command, a model choice was saved before it, or the session already has a title, such as one `/rename` gave it. It has no preview, as upstream's sessions in this layout have none: upstream reads a preview only from a schema-v3 session's `display.json` or derives it from a legacy snapshot's first prompt.
- A writable resume of a session whose `events.jsonl` is not empty keeps upstream's `history-cache.bin` beside it, in upstream's encoding (cache format 3 for conversation schema 3): a binary mirror of every log line, framed with CRC-32 checksums and bound to the log by the length and CRC of the last line it covers. A resume checks the cache against the log, replays the lines it covers from it and the rest from the log, and adds those to the cache; a read-only load uses the cache but never writes it. A cache that fails its checks is read from the log instead, and the writable resume rebuilds it. The resumed transcript walks the cache too, then the turns saved after it. Resuming a 3,000-turn log with tool output (15 MB) and walking its transcript took 64 ms from the log and 17 ms from the cache, and a 100,000-turn one (266 MB) 581 ms and 221 ms (release build, macOS arm64, warm page cache). oh-fx differs in three ways:
  - It does not sync the cache to disk after writing it. A crash that loses part of it only shortens the prefix the next resume trusts, since every frame is checked against its CRC, and syncing a new cache for a 266 MB log added up to 2 s to the resume that wrote it. Upstream syncs it before the session opens.
  - When a writable open cuts an unfinished turn from the log, oh-fx cuts the cache to the same length, so a turn kept up to its compaction checkpoint keeps its cached lines. Upstream cuts the cache back to the turn's first line.
  - A cached line that no longer decodes is read from the log, and a writable resume then deletes the cache for the next one to rebuild. Upstream retries the whole open from the log and rebuilds the cache in that open.
