# The `shell` tool and its process supervisor

- A `shell` run is bound to the working directory it was admitted in. Just before admission the call opens its resolved `cwd` without following a symlink in any component and keeps that descriptor open until the command starts or the call is denied, held, cancelled, or fails, so the directory the approval prompt, the reviewer, and a remembered command name stays allocated, and no directory deleted and created again at its path can take its device and inode. When it runs, the call fails with upstream's `CommandAuthorityContextMismatch` unless the path still opens, again without following a symlink, to the held directory: the model and the reviewer judged a path, so a call whose path now names another directory runs nothing, even when the held directory still exists elsewhere. On Linux the session supervisor, whose working directory the command inherits, starts in the held directory itself through `/proc/self/fd/<n>`, so the path is not looked up again between that check and the command's start. Other systems have no such entry, so there the supervisor changes to the path and compares the device and inode of its own working directory with the held directory's before it starts the command, and a directory replaced in that moment runs nothing; the descriptor stays open until the supervisor is in its working directory, which keeps that comparison sound. Upstream compares the `cwd` its admission resolved with the one it resolves when the call runs only for terminal runs; a captured `shell.run` rebinds its admission to the `cwd` it resolves when it runs, so a directory swapped during a review or an approval runs the command in the replacement. A `cwd` that names a file fails with `NotDir` before anything starts, and on macOS every directory on the `cwd`'s path must be readable, as `read_file` requires.
- Until command output is saved with the session, `ask` offers the `shell` schema that upstream offers when it keeps no session, without `tty`, `shell`, and `chars`, so commands never get a terminal and `interact` only observes. Shell results carry `full_output_handle: null`, and output cut to its head and tail is marked `... bytes omitted ...`, where upstream's marker points at the handle.
- `tty=true` terminals are being ported; their helper processes exist, but no call starts one yet. As upstream does, oh-fx re-executes itself as a launcher that owns the terminal and runs the shell, and the shell's startup script reports back through control markers. The hidden modes are `--oh-fx-internal-terminal-launcher` and `--oh-fx-internal-terminal-control`, the startup script, command, and socket files are `/tmp/oh-fx-terminal-<hex>.bootstrap`, `.command`, and `.sock`, and the startup script keeps the command and its exit status in the shell variables `oh_fx_terminal_command` and `oh_fx_terminal_status`, where upstream names all of them after fx. Upstream can also start a terminal without a command, a shell that waits for typed input, but nothing in upstream starts one, so oh-fx does not port it. When the shell ends while the launcher waits for the owner to release its command, upstream's launcher keeps waiting until the owner closes the terminal and then reports that its control failed; oh-fx's launcher reports the same failure at once. When the shell reports that it is ready, both launchers turn the terminal's echo back on, but upstream's attempt fails with `EIO`, because by then the launcher is a background process in an orphaned process group, so a startup file that turned echo off leaves it off; oh-fx's launcher blocks `SIGTTOU` in its own thread for that one change, so echo is on when the command starts.
- Each terminal has a record in `$XDG_DATA_HOME/oh-fx/terminal/<session id>/record-<terminal id>.json`, where upstream keeps `~/.fx/terminal/<session id>/terminal/state/record-<terminal id>.json`, or the same `terminal/state` folder inside a session folder of its older layout. The record has upstream's field names for the fields oh-fx keeps: the shell, working directory, command, deadline, lifecycle, process, and exit status. Upstream's folder also holds each terminal's output journal and screen checkpoints, and authority, proof, event, and close files that let another process act on the terminal. Terminals end with the process that started them, so only that process acts on them, and oh-fx keeps none of these files, nor upstream's backend fields, since oh-fx has only the native backend. A terminal belongs to the session that started it. A record names the process that wrote it as `oh-fx-process-v1/<random instance>/<pid>`, where upstream writes `fx-process-v1/<random instance>/<pid>/<process start token>` and checks whether that process still runs before it marks the terminal lost; oh-fx does not check, because a saved session is open for writing in one process at a time, so a live terminal another process recorded is marked lost when its session's terminals are listed. oh-fx reads only its own records, so the terminals of a session imported from fx answer as unknown rather than as ended.
- A `shell` call is kept and saved in upstream's form and goes back to the model in upstream's request form. A call sent as a lone `{"request":{...}}` object is kept as that request, written compactly the way upstream's JSON writer writes it; any other call is kept exactly as the model sent it. `events.jsonl` and `recovery.json` save that form, as upstream saves its normalized calls, and a resumed or continued session reads it back. The check that stops a turn when the same shell command fails in consecutive steps compares calls in that form too, as upstream's does, so the wrapped and bare forms of one request count as the same command. Each request then wraps a kept call that is not already a lone request object in `{"request":...}`, written compactly, so a bare request gains the wrapper and numbers such as `5E3` read `5000`, in live, resumed, and continued turns alike, as upstream projects its history into every request. Upstream also rewrites the payload of a `write` action in both forms; oh-fx's shell, like the one upstream's `ask` offers, has no `write` action, so such a call is kept and sent as the model sent it, only compacted.
- On Linux a stop, a deadline, or the loss of the oh-fx process that owns a shell command stops the command's whole process tree, as upstream's process tree tracker does, including descendants that left the command's process group, such as a daemon started with `setsid`. When the command ends on its own, every process left in its session is killed and a daemon that started its own session keeps running. A daemon whose parent exits right after forking it, as a command that calls `daemon(3)` does, can still be in the session when the command's exit is seen, before the child has called `setsid`, and is then killed, as upstream's is. Before the supervisor kills tracked processes, the command included, it sends each of them SIGSTOP in the order its walk found them, walks the tree again to send SIGSTOP to any child forked in the meantime, and sends SIGKILL only once every one of them has a stop pending. Signal delivery is asynchronous, so a process may still be finishing a system call when its SIGKILL is sent, but a pending stop is acted on before it returns to its own code, so no tracked process can act on another one's death before its own SIGKILL arrives, as a background `(sleep 5; echo done)` could print `done` once its `sleep` was killed. Upstream sends SIGKILL to one process after another, newest first. A forced stop kills the command directly only after the tree, so that a command the walk cannot reach still stops. A process stopped this way that left the command's session in the meantime, during the cleanup after the command ended on its own, is continued with SIGCONT and keeps running, and one whose `/proc` entries can no longer be read is still killed. Upstream walks `/proc/<pid>/task/<tid>/children` from the command and from the supervisor, a child subreaper, every millisecond for as long as the command runs. oh-fx walks the same files only when the supervisor acts: when a stop, a deadline, or the loss of the owner arrives, or the command exits, and then every millisecond until no tracked process is left or the cleanup time runs out. A forced stop or the loss of the owner that arrives during that wait makes the supervisor kill every tracked process at once, such as a process that ignores SIGTERM after a graceful stop ended the command, or a daemon that started its own session after the command ended on its own; upstream does not look for either during the wait. The subreaper keeps every process the command starts inside the supervisor's tree until it exits, so a walk when the supervisor acts finds what upstream has tracked, and a running command costs no CPU. So that the walk sees the tree before anything in it starts to exit, a graceful stop goes to the supervisor, which walks the tree and then sends SIGTERM to the command's process group and to the tracked processes outside it; upstream's owner sends SIGTERM to the group itself while its supervisor signals the processes outside it from the tree it already holds. If the walk fails, the group still receives SIGTERM before the supervisor gives up. Sending SIGTERM from the owner as upstream does would let the group's processes exit and hand their children to the supervisor while it walks, so the walk could miss them. Because the supervisor shares the command's process group, a command that signals its own group, as `kill -TERM 0` does, also starts a graceful stop, and the group then receives SIGTERM twice, once from the command and once from the supervisor, where upstream's group receives it once. While the command runs, the supervisor reaps the orphans handed to it as they exit; upstream leaves them as zombies until the supervisor exits, as oh-fx does with orphans that exit after the command. A process counts as exited only once it is a zombie with no thread left. Upstream treats a process as exited as soon as `/proc/<pid>/stat` reports it as a zombie, which it also does when only the main thread has exited, so upstream never signals such a process and its other threads keep running after a stop; oh-fx reads the thread count from the same line and stops it. The supervisor walks `/proc` only when it belongs to the supervisor's own pid namespace, which it checks with the `NSpid` line of `/proc/self/status`. In a pid namespace whose `/proc` was not mounted again, as under `unshare --pid --fork` without `--mount-proc`, `/proc` lists another namespace's pids, so the supervisor uses the process-group fallback described below for macOS; upstream walks that `/proc` anyway and can signal unrelated processes that hold the pids it reads there. A kernel built without `CONFIG_PROC_CHILDREN` has no `/proc/<pid>/task/<tid>/children` files, so the walk finds no descendants and a stop silently reaches only the command's process group and the command itself, as upstream's does. A process whose `/proc` entries the supervisor may not read, as `/proc` mounted with `hidepid=1` reports for a process that turned off dumping or runs a setuid program, is left out of the walk with its descendants, which the walk finds again once they are handed to the supervisor; upstream fails the stop with the error instead. Any other failure to read `/proc` still fails the stop, as upstream's does; when it happens after the command exited, the supervisor still kills the command's process group before it exits.
- On macOS the supervisor still uses the process-group fallback. A stop, a deadline, or the loss of the owner reaches only the command's process group, and the command itself once the stop is forced. When a command ends on its own, oh-fx kills what is left of its process group; upstream kills what is left of its session, so a process that moved to another group of the same session survives here. Both keep a daemon that started its own session. Porting upstream's macOS tracker, which finds descendants through a witness pipe they inherit, is a follow-up.
- If the supervisor has still not exited five seconds after a stop or a deadline started to end the command, oh-fx kills its process group, reports the command as indeterminate with incomplete output at once, and reaps the supervisor in the background; upstream reports the same result but first waits for the supervisor to exit.
