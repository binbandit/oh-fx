# Hooks and Herdr reporting

- The lifecycle hooks of `core/hooks` are first-party handlers compiled into oh-fx, as upstream's are; neither reads hooks from settings nor runs a configured command. Freezing the hook runtime consumes it, so a handler cannot be registered after the freeze or the view read before it, where upstream returns `RuntimeFrozen` and `RuntimeNotFrozen`; a runtime frozen with no handler holds nothing, so dispatching it is one branch. A `PostTurnEnd` or `AttentionRequired` handler returns nothing and the runtime writes no handler start or finish lines, because oh-fx has no debug trace; upstream records a side-effect handler's error only in that trace and runs the next handler either way. The agent runs `PreToolUse` handlers on tokio's blocking thread pool and waits for their outcome, one call at a time in the batch's order, and a handler that panics blocks its call closed as a failing handler does; rewritten arguments are UTF-8 because they are Rust strings, so upstream's UTF-8 checks need no counterpart. `Stop` handlers run the same way, once per turn, and a handler that panics allows the answer as a failing handler does. The message that a continuing `Stop` handler adds reads `Continue the turn. oh-fx hook context:` followed by its context, where upstream's names fx, as the system prompt names oh-fx; neither ever saves it, and it leaves the session's history when the turn ends, as upstream's rebuilt history drops it. An invocation carries its scope kind and turn but not upstream's workspace root, session id or subagent id, and the `Stop` and `PostTurnEnd` inputs carry no provider completion disposition: no handler reads the invocation fields, and oh-fx's completions record no length-limited finish to report. The agent dispatches `PostTurnEnd` after it reports the finished turn, with paused recoveries reported as paused, and runs the handlers on tokio's blocking thread pool, where upstream runs them on its agent worker thread: the session's runtime has one thread, so a handler that blocks, as a Herdr report can for 250 ms, never holds it. The turn returns without waiting for them, so the session shows it at once, as upstream presents a turn before its handlers run, and the agent's next turn, like the session's next working report, waits until they have returned. The interactive shell dispatches `AttentionRequired` when its permission or question prompt becomes active, and a request that replaces a prompt that is still open dispatches nothing, as upstream's prompt activation does.
- Foreground Herdr reporting uses `OH_FX_HERDR` for the application opt-out while retaining the third-party `HERDR_SOCKET_PATH` and `HERDR_PANE_ID` variables and the upstream `custom:fx` source and `fx` names. Working is reported when the session starts a prompt's turn, before the provider starts; upstream reports it when the prompt enters the worker's queue, so a prompt queued behind a running turn reports working when its own turn starts instead of before the earlier turn's idle report. Startup reports the actual opened session, then idle and both names; a visible permission or question prompt reports blocked through upstream's `fx.herdr.attention_required` lifecycle hook, every interactive turn reports idle when it ends through the `fx.herdr.turn_end` `PostTurnEnd` hook, the startup, working and idle reports run on tokio's blocking thread pool, and terminal shutdown releases authority before a handled termination signal is re-raised. The release is serialized with reports and permanently closes the reporter; the last shared reporter drop provides idempotent fallback cleanup. Later session selection, manual compaction and route-recovery decision prompts still need lifecycle reporting, and sounds remain unimplemented. Socket failures are ignored and the 250 ms timeout applies only to receiving a response, as upstream specifies.
