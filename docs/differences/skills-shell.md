# Skills in the interactive shell

- The requested-skills notice that names the explicit skills a prompt loaded ends with upstream's `(ctrl+o for details)` when one fails, but the details, which upstream shows only in its full transcript, are not shown until the full transcript is ported. A skill chosen in the `/skills` menu is bound to the prompt by its location, as upstream binds it. Typing `$` in the composer opens upstream's `$` mention menu, the `/skills` menu anchored to that `$` and filtered by the token after it, and choosing a skill binds it by its location, as does a pasted `$name` that matches a skill. The menu lists the catalog as the agent last discovered it, before the latest prompt or `/skills` command, and keeps that list while it is open, where upstream's list follows its background refresh. Upstream also draws the rest of a skill name after `$prefix` as a dimmed completion that Tab or Right accepts, and lists skills among the slash completions; neither is ported yet, so a skill typed as `$name` without the menu is still matched by name.
- `/skills list`, `show`, and `remove` discover skills again before they read the catalog, since the interactive session otherwise rediscovers only when a prompt runs. Upstream reads the catalog that its background refreshes keep current.
- The `/skills` menu, its path notice, and its remove notice name oh-fx's own roots `oh-fx`, as in the `oh-fx` source tab and the `oh-fx · Workspace` and `oh-fx · Global` scopes, where upstream says `fx`.
- `/skills add` and `/skills install` install local directories into the managed root, retaining upstream's initial `Installing from <source>...` notice, metadata-name result lines, directory-name or metadata-name filter, and catalog refresh after every completion, including empty results and failures. Upstream refreshes only after a nonempty successful result; oh-fx uses one completion path to refresh the catalog before releasing queued commands regardless of the install outcome. Remote repository sources, install-command and URL normalization, and the top-level CLI installer remain unported; remote sources produce upstream's generic installation failure notice.
- A local `/skills add` or `/skills install` starts on the blocking pool as soon as its command is accepted, while upstream copies synchronously on the app thread with its turn on another worker. Completion is handled during idle work, turns and compaction; the initial and result notices are emitted together before the catalog refresh, preserving upstream’s notice ordering without blocking stream progress, cancellation or approvals. Only while an install runs, later `/skills` commands, clear commands and prompts wait in arrival order behind it. Completion drains those inputs without waiting for queued prompts to run; each prompt is then submitted as if it had just been typed, so one released while a turn runs steers that turn, a new install pauses the drain, and clear cancels active work and drops earlier waiting prompts and steering just like an immediate clear. Prompts still waiting behind a subsequent install are observed again for the fresh session’s language, alongside prompts already in the turn queue. A held prompt that names the skill being installed, such as `$new-skill check it`, was typed before the composer could bind the skill, so it is plain text: released while a turn runs, it steers that turn without loading the skill, as upstream's steering does with a prompt that carries no skill binding, since upstream checks only bindings and images for same-turn steering and loads explicit skills only from a turn's own prompt (`sameTurnSteeringEligible` in `src/core/agent/worker_runtime.zig`, `buildExplicitPromptSection` in `src/core/agent/runtime/orchestrator.zig`); run as its own turn, its `$new-skill` mention loads the skill, as upstream's prompt does. A failed blocking task emits the generic installation failure and releases its shutdown guard. Cancelling the active operation does not discard accepted installs. Accepted and executing installs hold shutdown guards until their results and cleanup finish, so normal exit drains them while unrelated worker tasks retain the existing two-second grace.
- Local skill installation opens source and managed-root components through directory handles without following symbolic links, refuses linked or non-directory destinations, and copies only regular files and directories through those handles. Upstream follows source and destination path components during copying and replacement. The stricter checks prevent a linked or swapped path from directing installation outside the held managed root.
- During local skill discovery, asset copying, and staging cleanup, an entry whose directory listing reports no type is classified with descriptor-relative metadata lookup without following symbolic links. Upstream skips such entries. oh-fx either processes the actual file type or reports the lookup failure, so filesystems without entry types cannot silently omit installed definitions or assets.
- Local skill installation rejects a source inside the managed root or a managed root inside the source before creating directories. Upstream does not reject these relationships, which can recursively copy an installation's own staging tree.
- Local installation requires the copied `SKILL.md` to be the regular file whose metadata was validated, with its size, timestamps, device, and inode unchanged during copying. Upstream reopens the pathname for copying without tying it to the metadata read. The additional checks reject a changed or removed definition instead of reporting the old metadata for a different copied skill.
- Local installation preserves ordinary file read, write, and execute permissions under the process umask, but strips set-user-ID, set-group-ID, and sticky bits from copied assets. Upstream passes the source file's full permission mode to file creation. Transaction directories are private to the current user rather than using upstream's default directory permissions, so partially copied assets and rollback backups are not exposed while installation runs.
- After acquiring an installation lock, oh-fx checks that its directory entry still names the held lock file. Upstream checks the file when opening it but does not repeat that identity check after acquiring the lock. The additional check rejects replacement while waiting; neither protocol excludes every subsequent mutation by another process with the same user identity.
- `/skills create` never replaces an existing `SKILL.md` and reports it as a failure, and it creates the managed root, the skill directory, and `SKILL.md` through directory handles that refuse symbolic links, so a linked managed root, skill directory, or `SKILL.md` cannot make it write outside the managed root. Upstream truncates an existing `SKILL.md` to the template and follows symbolic links on the way.
- `/skills` shows the skill discovery warning only when the conversation has not shown it yet, as the context notice does, and both show it again in the conversation `/clear`, `/new`, or `/reset` starts and in a resumed session, as upstream forgets the notices a conversation has shown when it resets or restores one. Upstream repeats it on every `/skills` command.
- A filesystem failure in `/skills create` is reported as `Failed to create skill '<name>': <error>` in an error notice, where upstream returns the error from its command handler. Without a configuration directory there is no managed root, so `create` and `remove` fail instead of writing relative to the working directory.
- The prompt card shows a bound skill as the `$name` text that was submitted, where upstream draws the same styled `name` chip the composer draws, because transcript entries and the held-prompt banner carry only the prompt text.
- Killing text that holds a bound skill and yanking it back restores the `$name` text without its binding, because the kill ring keeps plain text, with pasted blocks expanded. Upstream's kill ring keeps the binding.
