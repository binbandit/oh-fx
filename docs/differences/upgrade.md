# Upgrades and releases

- There is one release stream, so `oh-fx upgrade` has no `--channel` option.
- Releases come from GitHub Releases. Every push to `main` that changes more than documentation publishes `v<version>-dev.<n>`, where `<n>` is the commit count on `main`.
- `oh-fx upgrade` follows upstream's stable flow, text and JSON reports, and progress line, including the 150 ms pause on `oh-fx <current> -> <latest>` before the download percentages, which stop at 100%. It checks more along the way: a local build, which has no release version to compare, fails with `this is a local build; install a release to enable upgrades`; the running binary must be replaceable before anything is fetched; the checksum is fetched before the archive, so a release without one fails before the download; and the staged binary must report the new version through `--version` before it replaces the old one, or the upgrade fails with `downloaded binary failed to run`. Its fetch errors name GitHub where upstream's name its CDN, and it waits for the install lock that every oh-fx installer shares.
- The interactive shell checks for upgrades in-process as upstream does: 10 seconds after launch and then every five minutes instead of upstream's thirty, so each merge reaches users quickly. The footer shows upstream's `upgrading to <version>...`, `update ready: ctrl+g to reload`, and `upgrade failed`; a binary another oh-fx process installed meanwhile counts as ready without a download. `auto_upgrade: false` in the user settings, at the top level or in the workspace's entry, turns the upgrader off as upstream's does, and so does `OH_FX_AUTO_UPGRADE=0` in place of upstream's `FX_AUTO_UPGRADE`. A build without a release version never upgrades itself, where upstream skips a build that runs from `zig-out/bin`. While Ctrl+C waits for its second press, the status shows only where it fits beside the whole `press ctrl+c again to exit`, since that cue owns the row as it does over upstream's danger status; upstream clips the exit hint to make room for the status, which hides it entirely at 31 columns. Leaving the shell stops a check or download at once and waits out an install already under way, before the agent worker is joined, as upstream orders its exit. Upstream's `stop`, which gives the upgrade thread 250 ms to finish, serves only the shutdown of its embedded host, which oh-fx does not have. One-shot commands, which upstream never upgrades, schedule a detached `oh-fx upgrade --background` instead, at most once every five minutes, and every installer shares one file lock, so two never overlap. The detached run reads `auto_upgrade` for its working directory, the filesystem root, so only the top-level setting stops it.
- Ctrl+G applies a ready upgrade as upstream's does, with upstream's notices. It is refused while a question or an approval is open, while a response runs, while the session picker is open, and while the composer holds a draft. A queued prompt always waits behind a running turn in oh-fx, so it gets the response notice. oh-fx has no API key entry, subagent view, transcript view, or image attachments to check, and its input decoder never hands Ctrl+G over inside a paste or an unfinished key sequence, so upstream's refusals for those have nothing to guard. A ready upgrade then needs a saved session that is still writable, keeps that session even when it has no turns yet, and closes the shell. Once the session is saved, `<executable> resume <id> --upgrade-relaunch` replaces the process; if that fails, upstream's recovery hint names `oh-fx --resume <id>`. The relaunch repeats the launch's `--add-dir`, `--no-additional-dirs`, and `--context-limit` flags ahead of `resume`, and passes `--ultrafast` while the launch's Ultra request has not been withdrawn, because the saved session restores only the provider, model, effort, and Fast mode. Upstream's relaunch passes only `--sessions-v2`, so its reload drops those flags: saved directories come back after `--no-additional-dirs`, directories added on the command line are lost, context limits revert, and the Ultra request ends. The relaunch carries no previous revision, because oh-fx builds record none, and the new binary's `oh-fx has been updated` notice stands in for upstream's changelog range. Upstream's `relaunch could not be prepared` failure has no counterpart, because the executable path is never copied into a fixed buffer.
