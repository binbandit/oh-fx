# Terminal ownership and restore

- While the interactive session owns the terminal, no panic report is written to it. A panic on any other thread, such as one in tool code that the agent contains, becomes an error notice in the transcript with the report Rust would print, and the session goes on. A panic the agent does not contain stops the agent thread, and the shell then ends as `/exit` ends it: it restores the terminal, and oh-fx prints `oh-fx: the agent stopped unexpectedly: <report>` and exits with status 1. A panic on the thread that runs the shell is kept until the shell has dropped and the terminal is restored, then written to stderr for at most 100 ms before the panic continues, so a terminal that has stopped reading cannot hold the process with the terminal still raw. Upstream's panics abort, writing their report to stderr as they happen.
- On Ctrl+Z oh-fx clears the window title before it stops and sets it again when it continues, where upstream leaves its title in place while stopped. When it continues, oh-fx turns theme change notifications back on unless the theme is pinned, where upstream leaves them off after any suspend, so a light or dark switch later in the session is still followed. A SIGCONT after the process was stopped by something other than Ctrl+Z, such as `kill -STOP` followed by `fg`, takes the terminal back into raw mode and repaints when the shell left it cooked; upstream has no handler for it. The theme monitor, which upstream starts even for a pinned theme so that it consumes theme replies, starts only when the theme is not pinned; a reply that arrives anyway is discarded by the input decoder. A background colour that changes without changing light or dark redraws nothing, where upstream resets the screen and replays the transcript for it.
- When a panic unwinds through the terminal owner, a startup step fails after raw mode, or a SIGTERM or SIGHUP ends the interactive session, oh-fx restores termios at once with TCSANOW instead of after queued output drains, writes the abnormal restore sequence within a 100 ms deadline, and then, when it is the one leaving raw mode, discards input it has not read. The deadline covers only that write, and the next item describes where a blocking descriptor can still hold it. Rust's default panic hook writes the panic report to stderr before the unwind reaches the terminal owner, so when stderr is a terminal that has stopped reading, the panic waits in that write with termios still raw, as upstream's panic handler also writes its report first. The sequence ends synchronized output, turns off mouse tracking and focus reports, and leaves the alternate screen, in the order upstream's own alternate screen exit uses, then turns off the modes that oh-fx's inline session sets and that would break the shell: the kitty keyboard flags, which kitty keeps for each screen and so are popped only once the main screen is back, modifyOtherKeys, bracketed paste, theme notifications, the hidden cursor, and disabled autowrap. The keypad, insert, origin, and attribute resets come last. oh-fx’s retained-text viewer now enters and leaves the alternate screen, while approvals still draw in the inline live region. The viewer adds no mouse-tracking modes; focus reports, mode 1002, and the cursor key, keypad, insert, and origin modes are reset by both restores and set by neither. Each escape sequence goes out in its own write, so a terminal that reads only part of the restore before the deadline gets those modes back first and is left between two sequences, unless its kernel splits a write of a few bytes. Upstream writes its sequences in one write, with the keyboard modes last. Discarding unread input, as the TCSAFLUSH of a normal exit does, keeps the shell from running a command typed for the session. Termios is restored before the sequence is written, so a process that dies during the write never leaves the terminal without echo, but echo and signal keys are then back on while the write waits for a stalled terminal, for up to 100 ms. Keys typed in that time are echoed, in the kitty encoding until the terminal has popped the keyboard flags, and a Ctrl-C or Ctrl-Z that arrives as its control character still interrupts or stops oh-fx; the other keys are then discarded rather than run by the shell. The discard runs once the kernel has queued the restore sequence, not once the terminal has processed it, so keys and probe replies still on their way, such as over SSH within one round trip, can arrive after it and reach the shell. Upstream's panics abort without restoring the terminal, and its signal handler writes the sequence with one blocking write and leaves termios as it is, so after either the shell reads that input. A normal exit and a suspend wait for queued output before restoring termios, as upstream does. A normal exit keeps its signal handlers until its last write and the termios restore are done, so it waits for a terminal that has stopped reading, and on the nonblocking descriptor a SIGTERM or SIGHUP meanwhile ends that wait, restores termios at once, and ends the session by that signal; once a fatal signal has been taken, the exit writes only the abnormal restore. The session intercepts SIGTERM and SIGHUP before it puts the terminal in raw mode and keeps intercepting them until termios is restored, so one that arrives during startup, or while a failed startup unwinds, also leaves the terminal cooked.
- A SIGTERM or SIGHUP that ends the interactive session also stops the in-process upgrader: it ends a check or download at once and waits out an install already under way after the terminal is restored and Herdr is released, as upstream's exit releases Herdr before it stops the upgrader, and before the process exits by that signal; upstream's handler for those signals restores the terminal and exits at once, so it can end the process during an install. A second SIGTERM or SIGHUP during that wait ends the process at once, as upstream's handler does for the first, so a stuck install cannot hold the exit. That is safe because an install stages the new binary next to the old one and renames it into place: a process killed before the rename leaves the old binary working and at most a staged copy, which a later install sweeps once it is an hour old.
- The interactive terminal writes through a nonblocking descriptor of its own. oh-fx reopens the terminal's path for it, or opens `/dev/tty` when the path cannot be opened and the terminal is the session's controlling terminal, and uses neither when poll reports it invalid, as macOS can for `/dev/tty`. On that descriptor a SIGTERM or SIGHUP ends a rendering write to a terminal that has stopped reading at once, and the restore that follows waits for room before each escape sequence and gives up when the 100 ms deadline passes. When neither works, as under `su <user> -c oh-fx`, which starts a session without a controlling terminal on a terminal that belongs to another user, oh-fx writes through a blocking duplicate of stdout, as upstream always does. On that descriptor a terminal that stops reading holds every rendering write until it reads again, and a SIGTERM or SIGHUP cannot end the write, as upstream. The abnormal restore still waits up to its deadline for the terminal to report room before each escape sequence and then writes that sequence with a blocking write, so it gives up after 100 ms on a terminal that has stopped reading. If something else writes to the terminal between that check and the write and fills its queue again, the write blocks until the terminal reads, as upstream's one blocking restore write does. If poll reports stdout itself invalid, the restore writes nothing rather than risk a blocking write it cannot bound.
