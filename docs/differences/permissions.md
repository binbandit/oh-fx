# Permissions and approvals

- In the ask and auto permission modes, whether set in settings or for one request with `--auto`, a `read_file` call whose path, or a `glob_files` or `grep_files` call whose search root, resolves outside the workspace needs approval. Upstream reads and searches such paths without approval unless a configured `permission` rule asks for it. The interactive session asks for that approval with upstream's approval panel. The auto-mode reviewer does not grant it, since upstream never reviews reads, and until permission rules are ported nothing can grant that approval to `ask`, so it handles the call as upstream does when no approval prompt is available: it prints the blocked-action guidance with upstream's ask-mode or auto-mode hint (which still name `--auto` and the interactive shell), records the call as an error, and fails with `NonInteractivePermissionRequired`. Full access, from settings, `--full-access`, or `--yolo`, reads and searches external paths. A call admitted only for the workspace resolves its path again when it runs and fails with `PathOutsideWorkspace` if the path has left the workspace since admission.
- A `read_file`, `glob_files`, or `grep_files` call outside the workspace that the user approves at the prompt, once or for the rest of the session, or that a remembered session grant admits, runs confined to the directory tree the approval covers: the target itself when it is a directory, otherwise its parent. A prompted call's tree is resolved once, before the request reaches the host, and both the approved call and an `Always` grant are bound to that tree, so a symlink swapped while the prompt is open moves neither of them. The call resolves its path again when it runs and fails with `PathOutsideWorkspace` if the path no longer lies inside that tree, the same check a call admitted only for the workspace makes against the workspace root. Upstream runs such a call, whether approved at the prompt or admitted through `sessionGrantAllowed`, with ordinary authority, so the tool reads whatever its path resolves to at that moment, and a symlink swapped after the user answered lets an approval given for one directory read another one without asking. The approval is consent for its tree only, so oh-fx does not follow the path out of it. Full access is unchanged, and `write_file` and `edit_file` need no extra check, because their execution already requires the exact target and identities recorded at admission, as upstream does.
- An `ApprovalRequested` event carries what the host needs to show exactly what it approves, which upstream's permission request does not always name. Its `title` is the call's progress title where upstream shows a permission label. `tool_arguments_preview` is the call's arguments made terminal-safe and cut at 4 KiB, upstream's `max_tool_arguments_preview_bytes`, for every tool, where upstream fills it only for dynamic MCP tools, and `tool_arguments_truncated` says whether it was cut. `scope` is what the gate resolved before asking: the canonical path a `read_file`, `glob_files`, or `grep_files` call reads or searches and the tree the call stays confined to, which upstream does not show, and in `always` the session grant an `Always` answer records. `file` names a file change's target and state, and once the change is prepared `change` carries a copy of it: the path upstream's approval shows, the requested path for a workspace target and the canonical target outside it, already terminal-safe and cut from the front at 4 KiB, with the exact bytes before and after the change, the ones the commit checks and writes. Upstream's request carries a preview of at most six rows, and its approval screen reads the full review the worker built and keeps while it waits. The prepared call that owns those bytes stays with the agent, so oh-fx copies them into the request, at most the 4 MiB each side of a change may hold, and the interactive shell builds its review from the copy on the agent's thread and then drops it. A change to an existing file outside the workspace, which is not read before approval, has no `change`. For `shell`, `command` holds the full command text with its resolved `cwd`, its profile, `user` when the call names none, whether it wants a terminal, and the shell a terminal run names, or the full input `interact` would send; upstream puts the command and profile behind a `# shell.run profile=…` header, does not name the working directory, and leaves `interact` input out of its request. Command text, the named shell, input, `scope.target`, `file.target`, the bytes in `change`, and the paths and command in `scope.always` are raw, and a file name can hold terminal escapes, so a host makes all of them terminal-safe before showing them. Upstream's permission request can also carry an `explanation`, which upstream fills only for its permission rule commands, so it has no counterpart yet.
- The gate settles what an `Always` answer grants before the request reaches the host, and `scope.always` carries it, as upstream's file grant offer does; the host shows it on the `Always` choice and offers no `Always` when it is `None`. A change inside the workspace offers `WorkspaceFiles`, upstream's workspace file access: changes, reads, and searches anywhere in the workspace, `.git` included. A change outside it offers `FileChangesUnder` the nearest existing directory above the target, as upstream normalizes its target and parent grants, so a new file at `/new.txt` offers `/` and one at `~/x` offers the home directory. A `read_file`, `glob_files`, or `grep_files` call outside the workspace offers reads, name searches, or content searches under the tree it is confined to, and a `shell` run offers its exact command. `interact` and `stop` offer nothing, and neither does a call whose target no longer resolves when the request is built, which runs confined to the workspace if approved, or a `shell` run whose `cwd` is not an existing directory, which fails when it runs. Upstream fails that run before asking; here it asks first, so the absence of an external directory stays behind approval like the rest of an external path, and no grant is offered for a run that cannot start. Upstream shows its second choice on every prompt and, for every call but a file change, records a grant it works out from the call after the answer, so it also remembers `interact`, `stop`, and a call whose target vanished. oh-fx offers `Always` only when it can name the grant before asking: a grant worked out after the answer can differ from the one the user saw, and `interact` and `stop` carry no target a grant could be bound to. The agent records exactly the offer it showed, so a target that becomes a directory or a symlink swapped while the prompt is open cannot change the grant, and an `Always` answer to a request without an offer approves only that call. Upstream fails a file change whose offer it cannot represent safely, such as a tree whose path holds `*` or `?`, which its grant patterns would read as wildcards; grants here are literal paths, and every canonical file target has an existing directory above it, so neither case arises.
- A remembered command admits the same command text with the same profile, terminal mode, and named shell, so `profile: user`, which runs the login and interactive startup files, asks again after `Always` on `profile: clean`, as upstream binds a command grant to its shell environment and terminal mode. A terminal run's `shell` names an executable the call chooses, so its path is part of the request and the grant, and its `clean_start` sets the profile, as upstream's terminal identity binds it. Every other run uses the account's login shell. Upstream binds that path too; oh-fx leaves it out, because it reads the path from the account database for every call and no call argument can change it. The grant also binds the resolved `cwd` the command was approved in, as upstream keys a command grant on its resolved working directory, so the same command in any other directory asks again.
- An answer the host delivers is never dropped. If the turn is cancelled as the answer arrives, an `Always` grant is still recorded and the call does not start, and once the agent has withdrawn a cancelled request, resolving it returns `false`. `Agent::clear_history` also forgets every session grant, as upstream clears its permission engine when it resets a session; `PermissionGate::forget_approvals` has no default, so a gate that wraps another must decide what clearing does. `AgentSetup` gives every agent it builds the same `PermissionPolicy`, so session grants, and clearing them, belong to the process rather than to one agent; a process runs one agent today.
- `write_file` and `edit_file` are admitted as upstream admits them when no `permission` rule, session grant, or approval prompt applies: in ask mode every change needs approval, which the interactive session asks for and `ask` cannot get, so `ask` prints the blocked-action guidance and fails with `NonInteractivePermissionRequired`; auto mode allows changes inside the workspace and new files anywhere unless their path is sensitive; a write that would leave an existing workspace file unchanged needs no approval; full access allows everything. Configured `permission` rules are not applied yet. In auto mode, a change to an existing file outside the workspace or to a sensitive path goes to the auto-mode reviewer, as upstream sends it.
- A `write_file` or `edit_file` target outside the workspace and its active additional directories is not read before the call is admitted, in keeping with the approval external reads need. In ask and auto mode such a call therefore needs approval or is held even when it would change nothing or its `old_string` is missing, where upstream first reports `No changes to …` or the edit failure. With full access every target is read when the call runs, as upstream does: its path must still resolve to the same target, and those outcomes are reported then. In ask and auto mode workspace targets are read before admission, as upstream reads them. A permission mode switched while a batch runs applies to every call not yet admitted, as upstream reads the mode for each call: a call reads its workspace target or leaves it for the run under the mode in force when its turn comes, just before admission, and a call already admitted runs as it was admitted. oh-fx reads the mode once to stage the call and once more to admit it, where upstream uses one reading for both, so a switch that lands between the two either admits a change whose target was already read, which then fails if the file has changed since, or treats an existing workspace target as unread, which ask mode asks about and auto mode holds. The auto-mode reviewer therefore never sees a change to an existing file outside the workspace: it reports the evidence as incomplete, so `ask` holds the call with upstream's `review_evidence_incomplete` result and the interactive session asks for approval, where upstream reads the file and reviews the change. A new file outside the workspace has nothing to read, so the reviewer sees its whole content, as upstream shows it, and the call still refuses to run if its path resolves elsewhere or the file exists by then.
- `/shell reload` forgets the session's remembered command approvals, the ones its subagents inherit included, and keeps its file and search grants, as upstream's reload retires only shell command grants. Without the startup snapshot every command already runs the startup files, so it changes nothing else. Upstream retires command grants by snapshot generation, so a subagent's own command approvals from the running turn are retired too; oh-fx keeps those until the turn ends, when a subagent's approvals end anyway.
- `/permissions` and `oh-fx permissions` report `configured rules: (none)`, since the permission gate does not apply configured `permission` rules yet, and `/permissions remember` and `/permissions revoke` report that saved-session permission rules require an active saved session even when the interactive session is saved, because session grants and their rules are not saved yet; upstream confirms the rule and records it in the saved session. `/permissions` lists each session grant as upstream's `<permission> -> <pattern>` line, with trees relative to the workspace as upstream shows them, and a remembered command as `bash -> <command> (cwd=<directory>)`, with `, profile=clean`, `, tty=true`, and `, shell=…` added inside the parentheses when the grant binds them, where upstream prints the grant's raw identity, such as `@fx-terminal-env:<profile>:<length>:<shell>::<command>` for a profile-bound command. Controls in a command, path, or shell are escaped, so a line feed in a remembered command cannot add a line that reads as another grant, and a `cwd` or `shell` holding anything but letters, digits, and `/._-+,:@%` is shown in shell single quotes, as the approval panel shows it, so a directory named `x, profile=clean` cannot pass for a setting the grant does not bind; upstream prints them raw. The command takes no argument completion, which the interactive session has for no command yet.
- `/allowlist` views, adds, removes, and resets the allow rules saved under `permission` in the user settings and in this workspace's entry of them, with upstream's parsing, scopes, messages, and listing, and the settings loader reads both layers as upstream does, so a malformed `permission` object makes the profile unusable there too. The permission gate does not apply configured rules yet, so a saved rule does not change which calls need approval, and `/allowlist` does not load the rules into the running session as upstream does after each change. Its `tool` targets are the tools oh-fx can offer the model, `subagent` among them as upstream registers it even where it is not offered, and upstream's fixed `edit`, `read`, `glob`, `grep`, `skill`, and `web_search` categories. The settings reader follows a symbolic link to `settings.json`, so the listing reports `Failed to load settings: DurablePathUnsafe` when the settings file cannot be opened as a regular file, where upstream reports it for a linked profile folder.
