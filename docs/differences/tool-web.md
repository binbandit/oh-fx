# `web_fetch` and `web_search`

- `web_fetch` sends its requests through `ofx-http`, the client every other oh-fx request uses, so it honors `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`, the system proxy settings on macOS and Windows, `SSL_CERT_FILE`, and the TLS roots described in [providers.md](providers.md). Upstream dials the target itself with its own HTTP/1.1 client and CA bundle and ignores proxies. The URL policy is upstream's: `http://` is upgraded to `https://`, credentials, single-label hosts, private, loopback, link-local, and other non-public literal addresses, and names such as `localhost`, `*.local`, and `metadata.google.internal` are refused before any request, and every redirect is checked against the same policy before it is followed. Each hop resolves the name once and refuses it as `NonPublicDnsAnswer` when any answer is not public; a direct connection then dials only those answers, as upstream pins its connection to the answers it checked. When a proxy applies, the proxy resolves the name again for its own connection, so the local answer is a best-effort check: a name that fails to resolve locally is still fetched through the proxy, and a name whose answer changes between the two lookups, or that the proxy resolves differently, reaches whatever address the proxy chose. A host listed in `NO_PROXY` takes the direct, pinned path. The hop deadline also bounds connecting, where `ofx-http` otherwise stops a connection attempt after 30 seconds.
- `web_fetch` asks for `Accept-Encoding: gzip, deflate` and decodes both with the inflater the self-upgrade already links. Upstream also asks for and decodes `zstd`; oh-fx leaves it out because a zstd decoder would add a C library to the binary for one rarely chosen coding, and a server that sends zstd anyway gets upstream's unsupported content encoding failure. The request names `oh-fx (web_fetch; +https://github.com/binbandit/oh-fx)` as its user agent.
- `web_fetch` sends the request target as the WHATWG URL parser normalizes it, so characters such as `"`, `<`, `>`, and non-ASCII bytes in the path are percent-encoded, `\` reads as `/`, and `%2e` dot segments are resolved; upstream sends the path bytes it validated. HTTP framing is hyper's rather than upstream's own parser, whose framing tests have no counterpart here, the body of a redirect is not read, and a transport failure is named after its cause, such as `ConnectionRefused`, `UnknownHostName`, `CertificateHostMismatch`, `Timeout`, or `BodyTooLarge`, where some of upstream's Zig error names have no exact equivalent. An IPv6 literal is read with Rust's address parser after upstream's rule that an embedded IPv4 address may only follow `::ffff:`, so a literal whose `::` stands for no groups, such as `[::2606:4700:4700:0:0:0:0:1111]`, is refused as malformed where upstream's parser accepts it.
- `web_fetch` returns a binary response, such as a PDF or an image, as upstream does when no session artifact store is configured: the result names its MIME type and `<artifact_bytes>` and nothing is cached. Upstream also writes the bytes to `artifacts/web-fetch` in a saved session and names the file with `<artifact_handle>`, `<artifact_retention>`, and `<artifact_path>`; the artifact store follows in its own change, since `ask` opens its saved session only after the tools are built and the interactive session saves none yet.
- `oh-fx ask` prints upstream's `Fetching <url>` and `Converting <url>` lines for `web_fetch` in the raw, quiet, and JSON modes, with the URL's credentials and sensitive query values redacted and the URL clipped to 96 columns, and leaves out the call's progress title there, as upstream does. Redaction reads each query field up to its own `&` and `=`, here and in the result's `<url>` and failure details; upstream's search runs past the field, so it shows a bare key followed by another field, such as `?flag&b=1`, as `?flag&b&b=1`. Upstream also cuts a clipped URL at 192 bytes, which only a URL dense with non-ASCII characters reaches. Terminal mode and the interactive session show the call's progress title, `Fetching <url>`, until upstream's tool rows are ported. That title names the normalized URL with the same redaction; upstream's title repeats the URL argument as the model wrote it, so a signed URL's query secrets reach its terminal output and scrollback. The `ask --json` tool call record does not yet carry upstream's `web_fetch` summary of the URL, bytes, status, duration, cache hit, and artifact state, and no network diagnostics are recorded, since oh-fx has no trace log yet.
- `web_fetch` runs without approval in every permission mode, as upstream does when no configured `permission` rule names it; upstream's `web_fetch` `domain:<host>` rules arrive with configured permission rules.
- `web_search` is registered as upstream registers it, as a tool the provider runs rather than oh-fx: it is never sent as a function, and its description follows the system prompt, ahead of the skills catalog, as custom tool guidance for every provider, as upstream does. Upstream runs the search only on the Vercel AI Gateway, through the gateway's search service, so it arrives with oh-fx's gateway transport; until then no connection oh-fx supports can run it. As upstream, a Chat Completions stream that calls it fails as `InvalidToolName`, since it was not offered as a function, and a Codex call to it gets upstream's argument errors or `web_search is unavailable: no local runtime with a configured Gateway transport policy is installed`, and `ask --json` records it with status `error`, as upstream does. Such a call prints no progress line: upstream shows only its provisional `● Searching` label there, which arrives with provisional tool rows. Upstream's search progress, result rendering, and the `web_search` search count and duration in the `ask --json` record arrive with the gateway transport too, and upstream's rule that an `ask` or `deny` `permission` rule hides the tool arrives with configured permission rules.
