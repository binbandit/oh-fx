# Provider connections, HTTP, and TLS

- Custom provider connections accept `headers` with `${VAR}` interpolation, `tls.ca_file`, `proxy`, a `models` list, `max_tokens_parameter` (`max_completion_tokens` for reasoning models and Azure OpenAI), plain `http://` base URLs on any host, and host names with `_`, so self-hosted gateways such as Portkey work. Settings files may start with a UTF-8 byte order mark.
- The chat-completions stream parser tolerates gateway dialects that upstream rejects: empty-choices chunks, a stream that ends after its finish chunk without `[DONE]`, repeated finish chunks, mismatched usage totals, provider-native finish reasons, `stop` after tool calls, tool call deltas without an `index` or with empty ids or repeated names, and finish chunks without a `delta`. A repeated name that could also extend to another advertised tool fails as `InvalidToolName`, where upstream appends it. `{"object": "error"}` chunks and a `finish_reason` of `error` fail as provider errors, and a response that is not `text/event-stream` fails with its JSON error or `UnexpectedContentType` instead of a parse error.
- Provider connections never follow redirects. A 3xx answer names the redirect target's host and explains that `base_url` must point at the gateway API, so a sign-in page never receives the request or its headers.
- An HTTP 404 keeps its real status in the error line, and protocol, transport, and stream failures print a second `oh-fx ask:` line with a masked, terminal-safe detail; a 401 adds the gateway's own explanation. Upstream prints only the error name.
- Stream and response body failure details carry structural facts, never the provider's raw bytes: a rejected stream event is named by its position and size (and, for Codex, a validated event type), an incomplete stream by its event and byte counts, a response that is not `text/event-stream` by its media type and size, and an error body whose read fails partway, which fails as `ReadFailed` as upstream does, by its status, read error, and bytes received. Provider error objects are parsed, re-serialized, and masked before they are shown.
- An HTTP error body without an `error` object but with a non-blank top-level `message` or `detail` string, such as chatgpt.com's `{"detail":"The 'gpt-5.4' model is not supported when using Codex with a ChatGPT account."}`, is shown as `API request failed · HTTP 400 · <text>`, masked and made terminal-safe like an error object's message. Upstream shows such bodies raw, as `HTTP 400: {"detail":...}`. Bodies whose `detail` is not a string, such as validation error lists, still print raw after masking.
- An error response whose body read fails partway or times out keeps its `Retry-After` on the `ReadFailed` or `Timeout` error, so the retry waits as long as the gateway asked. Upstream drops the delay with the body and retries on its default backoff.
- Configured secrets are masked in every provider detail, including forms hidden behind JSON string escapes (`\uXXXX` and surrogate pairs too) or percent-encoding, alone, mixed, or layered, such as `%5Cu0070`: the bearer token, proxy credentials, every substituted value of a header whose name looks sensitive, and other substituted values of at least 8 bytes. A secret that itself contains escapes is also matched in each decoded form of at least 8 bytes. Decoding repeats until a round changes nothing, for at most sixteen rounds over at most 64 KiB, enough for any backslash run that fits; text that would still decode after that, or that is longer and contains any escape, is shown as `content withheld (N bytes)` instead. A bearer token longer than 16 KiB or with non-visible characters fails as `InvalidConfiguredProviderCredential` before any request. Whitespace-only header variables count as missing, and nested defaults are rejected.
- A model failure diagnostic, the text in retry notices and in Codex `response.failed` details, masks anything that looks like a credential across its whole text before it is cut to 256 bytes. Upstream cuts first, so a credential that crossed the cut could leave a prefix too short to be recognized and masked.
- Codex details follow the same rules. A rejected Codex stream event is reported as `stream event N (TYPE, B bytes) was rejected`, such as `stream event 35 (response.completed, 15517 bytes) was rejected`, where upstream reports only the error name. TYPE is the `type` the reducer read while parsing an event whose content it then rejected, shown only when it is 1 to 64 bytes of lowercase ASCII letters, digits, `.`, and `_` that secret masking and terminal-safe encoding leave unchanged. An event rejected by the event-count or byte limits is never parsed, so it, an event that is not valid JSON, and any other type are reported as `stream event N (B bytes) was rejected`. Failure codes and messages from `response.failed` and `error` events are masked with every token the request sent as well as the current one, and Codex HTTP error bodies take the same parse-then-redact path as custom connections.
- A Codex `error` event without a top-level `code` or `message` takes both from its nested `error` object, using the object's `type` when it has no `code`, so `{"type":"error","error":{"type":"server_error","code":null,"message":"..."}}` is retried as a server error and shows its message. Upstream reads only the top-level fields and reports such an event as a non-retryable `provider_error: Provider response failed`.
- On Linux, TLS roots come from one CA bundle that is read when the first TLS handshake needs it, as upstream reads them with `std.crypto.Certificate.Bundle.rescan`, with these differences. `SSL_CERT_FILE` and `SSL_CERT_DIR` replace the bundle with the files and directories they name, as in rustls-native-certs and OpenSSL; upstream ignores both. The search tries Entware's `/opt/etc/ssl/certs/ca-certificates.crt` and OpenHarmony's `/etc/ssl/certs/cacert.pem` after upstream's six bundles, and the certificate directories are the ones rustls-native-certs read before, `/etc/ssl/certs`, `/etc/pki/tls/certs`, and `/etc/security/certificates`, where upstream reads Android's `/system/etc/security/cacerts` in place of the last, so no directory is trusted that oh-fx did not trust before. When a certificate fails verification against the bundle for any reason other than a name mismatch, oh-fx reads the certificate directories once and verifies again against the bundle and the directories together, the roots it trusted before, so a CA added to `/etc/ssl/certs` without regenerating the bundle is trusted, even when it replaces a bundled CA with the same name; upstream reads only the bundle. A connection's `tls.ca_file` adds to these roots. A failed load is kept for the rest of the run, fails each TLS request as `CertificateBundleLoadFailure`, upstream's name, with a second line naming the file, and is not retried. On macOS and Windows, oh-fx keeps rustls-platform-verifier and the system trust store.
- `oh-fx ask` reads the TLS roots on a background thread once its arguments and settings are valid and the connection, custom or Codex, uses `https://`, so the parsing overlaps name resolution, the TCP connection, and the start of the TLS handshake. Upstream reads them when its first request starts and opens a whole connection ahead of time only for the Vercel AI Gateway; oh-fx never connects early, so the HTTP client's proxy, `CONNECT`, and `NO_PROXY` handling always applies.
