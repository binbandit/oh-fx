# MCP

- Profile MCP servers live in `$XDG_CONFIG_HOME/oh-fx/mcp.json`, written with the `mcp.lock` advisory lock beside it, where upstream uses `~/.fx/mcp.json`. A workspace keeps its servers in `.mcp.json` at its root, the name other MCP clients read, and the project trust choices (`enabledMcpjsonServers`, `disabledMcpjsonServers`, and `enableAllProjectMcpServers`) live under the workspace's entry in the profile `settings.json`, as upstream keeps them.
- Adding or removing a profile MCP server fails with `StreamTooLong` and leaves `mcp.json` untouched when the canonical file it would write exceeds 1 MiB, the limit a profile is read with. Upstream writes the larger file, which its next read then refuses with the same error.
- MCP connections always start with the initialize handshake that upstream uses by default, and the opt-in 2026-07-28 protocol behind upstream's `FX_MCP_PROTOCOL_VERSION` is not ported: `OH_FX_MCP_PROTOCOL_VERSION`, in the environment or a server's `env`, accepts only `2025-11-25`, and any other value fails the server with `McpUnsupportedProtocolVersion`.
- A remote server that answers 401, or 403 with a `WWW-Authenticate` challenge, fails with `Authentication required. Run /mcp auth NAME --open, or configure bearer_token_env.` and is listed as needing authentication, as upstream does. `/mcp auth NAME --open` authorizes such a server and reconnects it. `capability_search` answers a query that names such a server with `Run /mcp auth NAME --open in an interactive oh-fx session.`, and one that names a failed server whose `bearer_token_env` variable is not set with `Set this environment variable before starting oh-fx.`, where upstream's messages name fx. Static `headers`, `header_env`, and `bearer_token_env` work as upstream sends them. Because every connection keeps one fixed authentication until authentication partitions land, a resource read cached under a `private` `cacheScope` is served like a `public` one, where upstream keys private reads by the authenticated identity. The interactive shell and `oh-fx ask` advertise form and URL elicitation and ask for a server's form, or for consent before opening its URL in the browser, as upstream does, the shell in its question panel and `ask` on the terminal. The URL questions say that oh-fx will not fetch the URL, or could not open the browser, where upstream's name fx, and a launcher still running after two seconds counts as an opened browser, where upstream waits for `open` or `xdg-open` to exit. With `OH_FX_NO_OPEN_BROWSER` set, the browser counts as not opened, so the question offers to continue manually, retry, or cancel. Without the capability, a stdio server's `elicitation/create` request during a tool call is answered `Method not found`, and a remote server's fails the call with `UnsupportedServerRequest`, as upstream answers them when it cannot ask. `mcp_features` asks for a server's form or URL elicitation while it reads a resource or gets a prompt, as upstream does, and `/mcp resource read`, `/mcp prompt get` and argument completion answer as if oh-fx could not ask, as upstream's do. Requests that overlap, within one tool call or across servers, are asked one at a time in the order they arrive. A request waiting its turn does not time out, each gets its 30 minutes from when it is asked, and a tool call's deadline stays paused until the last of its requests is answered. Upstream asks overlapping requests at once, each with 30 minutes from its arrival, so on the terminal the next line can answer either, and it resumes the deadline as soon as one of them ends.
- MCP OAuth credentials are kept in `credentials.json` under `$XDG_DATA_HOME/oh-fx/mcp-credentials/`, in upstream's format and with upstream's private permissions (`0700` for the directory, `0600` for the file) behind its `credentials.lock`, where upstream keeps them under `~/.fx/mcp-credentials/` and, on macOS, in the login keychain. As upstream does, a profile server uses its stored grant when it connects and refreshes it before any request made within a minute of its expiry, and a failed refresh during startup reports `MCP credential refresh failed. Run /mcp auth NAME --open.` or, without a refresh token, `MCP credentials expired. Run /mcp auth NAME --open.`. A refresh that fails after the server connected marks the server failed with that message when a tool call or a tool listing meets it, as upstream does, while a resource, prompt, or completion request or the notification stream fails with the refresh's error and leaves the server connected, listed as needing authentication when the authorization server rejected the grant, where upstream marks it failed too. The notification stream stops at such a rejection. Closing a Streamable HTTP session sends its `DELETE` with the last bearer oh-fx installed, without waiting for a refresh in flight, where upstream sends the headers it resolved when the session started.
- `oh-fx mcp auth NAME` authorizes a profile or approved project server as upstream's `fx mcp auth` does: protected resource and authorization server discovery, a configured client, a client metadata document or dynamic registration, PKCE S256 and the issuer checks, prints the authorization URL, opens the browser unless `OH_FX_NO_OPEN_BROWSER` is set, and waits up to five minutes for the loopback callback. It registers its dynamic client as `oh-fx` where upstream registers `fx`. A configured `callback_port` listens on `127.0.0.1` only, where upstream also listens on `::1` when it can, so a browser that resolves `localhost` to IPv6 alone cannot reach it. The callback listener is the one oh-fx's provider logins use: it keeps waiting through a connection that sends nothing, a request that is not a `GET`, a malformed request line, or a head over 16 KiB, answering the last three with a not-found page, and answers a `GET` outside `/callback?` with its failure page before it fails with `InvalidAuthorizationCallback`. Upstream accepts a single connection when no port is configured and fails on any of these, with `InvalidAuthorizationCallback` or `AuthorizationCallbackTooLarge` and no page. A listener that cannot bind reports `McpCallbackPortUnavailable` even for an automatic port, and one that fails while waiting reports `InvalidAuthorizationCallback`, where upstream reports the socket error. `oh-fx mcp auth NAME` refuses a project server with `McpStoredCredentialsNotAllowed` before any request, because project servers never read stored grants, as upstream's do not; upstream saves the grant and reports success, and the next session connects without it. A stored grant is found for a server whose configured `oauth.resource` lies within the grant's protected resource, or whose `oauth.issuer` differs from the grant's only by a trailing slash, the identities discovery accepts; upstream looks grants up by exact equality, so after such a discovery its next connection omits the grant `fx mcp auth` saved. An authorization saves its grant in place of every grant of that server and endpoint that the server's lookup would find, so it leaves exactly one, where upstream replaces only a grant with the same resource and issuer and keeps the others, which can make its lookup ambiguous and find none. A refresh updates only the grant it refreshed, and only while that grant is still stored; when an authorization has replaced it, the refreshed grant stays with the session that refreshed it, where upstream saves it again beside its replacement. `oh-fx mcp logout NAME` signs a server out as described below. The other `oh-fx mcp` operations stay unavailable.
- `/mcp auth NAME --open` in the shell runs upstream's authorization in the background, one at a time, and reconnects the server with the new grant, which it saves and also keeps for its server for the rest of the session, as upstream does, so an approved project server uses it for that session. It counts a launched `open` or `xdg-open` as an opened browser, where upstream waits for the launcher and fails with `McpAuthorizationBrowserOpenFailed` when it exits with an error, and with `OH_FX_NO_OPEN_BROWSER` set it fails with `McpAuthorizationBrowserOpenFailed` when it would open the browser, after discovery, a switch upstream lacks. The grant is withheld with `McpAuthorityChanged` when a challenge, or a reconnection that loads the server's credentials, arrives during the browser flow, where upstream's credential load does not withhold it and its refresh does. A 401 during the reconnection that follows the authorization marks the server as needing authentication again, where upstream drops the challenge of that temporary connection. Its notices name oh-fx where upstream names fx (`You can continue using oh-fx while the browser flow completes.`, `... while oh-fx stays open`, `oh-fx stopped before token exchange.`), and the issuer hint names the profile `mcp.json` path where upstream names `~/.fx/mcp.json`.
- A failed MCP transport reports its error name, such as `ConnectionRefused`, `Timeout`, or `FileNotFound` for a missing stdio command, never the underlying message, which for HTTP names the request URL and anything in its query.
- Numbers in MCP results, such as a list's `ttlMs` or a resource link's `size`, and the `minimum`, `maximum`, `multipleOf`, `minLength` and `default` of an elicitation form, are read through serde_json, which holds integers exactly and other numbers as the nearest double, so `1.0000000000000001` counts as the integer 1 where upstream reads the exact decimal and refuses it. serde_json also refuses a whole frame that holds a number beyond the double range or nests deeper than 128 levels, as `InvalidEnvelope`, where upstream parses it and then names the value's own error. A JSON-RPC error `code` written `-0`, which serde_json reads as a fraction, fails as `InvalidEnvelope`, an elicitation form length or item count written `-0` makes the form invalid, and an elicitation request id written `-0` is refused as `Invalid request id`, where upstream reads them as 0. The `input_required` result that repeats a URL request's parameters writes their numbers as serde_json holds them, where upstream repeats the server's text. The prompt messages that `/mcp prompt get` shows and `mcp_features` returns, and the `annotations` and `_meta` of the resource contents `mcp_features` reads, write each number back as serde_json holds it, such as `1000.0` for `1e3` or `0.5` for `0.50`, where upstream repeats the number as the server wrote it. `mcp_features` arguments that hold a number beyond the double range or nest deeper than 128 levels fail as `Invalid mcp_features arguments.`, where upstream reads them.
- A stdio MCP server whose restart fails stays failed until the next reload. Later tool calls and feature requests then fail with `McpConnectionClosed`, or are answered from its last catalogs and resource reads. Upstream instead tries to restart it again on each request until `restart_limit` restarts are spent. With the default limit of one restart, both stop after the first.
- Stopping a stdio MCP server also kills what is left in its process group after the server itself exited, so a background process it started does not outlive it. Upstream signals the group only while the server is still running.
- A Streamable HTTP event stream that breaks partway, answering a request or carrying notifications, is resumed with a GET whose `Last-Event-ID` is the last complete event's id, as the MCP resumability rules allow for network failures, and the notification stream keeps that id and the server's retry delay across its reconnection attempts. The request itself is never posted again. Upstream fails such a request with `ReadFailed` and restarts its notification stream without `Last-Event-ID`.
- A connection cancelled after a Streamable HTTP server answered `initialize` with a session, such as an `ask` start on demand that the turn's cancellation drops while tools are listed, sends that session's `DELETE` in the background, bounded by the 250 ms close timeout, so the server can release it at once. Upstream leaves a cancelled connection's session for the server to expire.
- An MCP tool is advertised to the model under upstream's name, `mcp_<server>_<tool>`, with upstream's selected schema (the tool description, the server instructions cut at `mcp_server_instructions_bytes`, and the input schema, refused with a `[context]` notice when it exceeds `mcp_selected_schema_bytes`), from the step after `capability_search` loads it or `mcp_select_tool` selects it until the turn ends, as upstream advertises the tools a turn selects. The `<mcp_servers>` section marks no server `loaded="true"`, since upstream marks only the always-loaded servers an ACP client supplies, and its guidance and availability change notice name `capability_search` and `mcp_select_tool` as upstream writes them.
- A `tools/list_changed` notification makes oh-fx list the server's tools again at once, or as soon as a listing already in flight ends, and a selected tool of that server stays advertised meanwhile with its last listed definition; upstream leaves it out of the step while a change is pending and lists the tools again when they are next searched, selected, or used. A call made while that listing is in flight waits for it, and fails with `McpRequestTimedOut` without reaching the server if its deadline passes first, where upstream refuses a call that finds another caller's listing in flight with `McpToolCatalogChanged`, as both refuse a call while a change stays unfetched after a failed listing. A list whose `ttlMs` has expired is listed again by the next search, selection, or call to one of its tools, or by a reload, as upstream's do. When that listing fails before a selection, `mcp_select_tool` answers from the last list, where upstream fails the selection with the listing's error.
- Outside a terminal, `oh-fx ask` connects required profile servers and approved project servers before the turn and starts the optional profile servers when a search, a selection, or `mcp_features` needs them, as upstream does, but a call to an unadvertised tool of such a server stays an unsupported tool, where upstream starts the server and answers that the tool is not selected. A subagent child starts them when its own search, selection, or `mcp_features` call needs them, where upstream starts all of them when it creates the child. The interactive shell connects them in the background at startup, as upstream starts discovery; until a server's startup has begun, the `<mcp_servers>` section shows it `unavailable`, and a project server waiting for approval `disabled`, where upstream shows both `discovering` while discovery runs.
- Until upstream's project trust prompt lands with the MCP menu, the interactive shell reports unapproved project MCP servers in a warning notice that points to `/mcp trust approve <name>`, where upstream asks for project trust in the shell. Server names in that notice and in `oh-fx ask`'s list of skipped project servers are made terminal-safe, which upstream does only in its summaries. Servers that fail to start are summarized in upstream's startup notice.
- `/mcp` and `/mcp list` open the MCP menu as upstream's shell does. Its Servers tab's list, details, help, reload, sign-in, add form, removal, project trust and logout, and the Tools, Resources and Prompts tabs with their catalogs and filter, work as upstream's do. Until previews, the argument form and insertion land, enter does nothing on a catalog item, and the catalog hint and the help screen name only the keys that work. The Tools tab lists every ready server's tools without upstream's permission-rule filter, which oh-fx does not apply. A catalog's tab and header show at once and its loading row after upstream's 200 ms grace, where upstream keeps the previous frame until the catalog arrives or the grace ends. Returning to the Servers tab cancels a catalog still loading, and a selected server that leaves also clears the filter, where upstream keeps both. The Slack preset's `s` key and hint are left out with the preset. On a confirmation, the arrows and Ctrl+J and Ctrl+K do nothing, and enter acts on the server the confirmation was opened for, where upstream moves the hidden selection and removes, logs out or rejects the server it lands on. `/mcp trust reject` and `/mcp trust reset`, and the menu's reject and reset, retire live authority even when settings.json already held that choice, so a choice written to settings.json while oh-fx runs takes effect, where upstream leaves an unchanged choice alone. In the add form, Ctrl+D and the other control keys edit the field as they edit the composer or do nothing, and `$` types a plain `$`, where upstream passes control keys to the field as typed text; enter and tab wait while a change is being saved, where upstream sends the form again. A logout from the menu signs out the server it names, and the Resources and Prompts tabs list the server they name, even when a reload replaced the runtime after the menu's last snapshot, where upstream fails them with `McpMenuSelectionChanged`. The menu's Source row and help name the oh-fx profile configuration path, and its configuration error row points to `oh-fx mcp list`, where upstream names `~/.fx/mcp.json` and `fx mcp list`. The shell asks for a fresh server snapshot every tenth of a second while the menu is open, as upstream refreshes it on its frame tick. Super+R does nothing while the menu is open, as it does over the settings, help and skills menus, where upstream opens the sessions picker hidden behind the MCP menu, whose keys it never receives. The menu's action generations continue across openings, so a result from a closed menu never settles a reopened one, where upstream starts each opening at generation 1. A server refresh that drops the selected server returns the menu to the server list and cancels a pending sign-in for that server, but keeps a pending reload, whose result still appears, because oh-fx publishes a reload's server set before the reload settles; upstream cancels whatever is pending. The text summary that upstream's `/mcp` prints in hosts without the menu is not ported, since every oh-fx host that runs `/mcp` opens the menu.
- `/mcp logout NAME` and `oh-fx mcp logout NAME` sign a server out as upstream's do: they delete every stored grant of that server and endpoint, whatever its resource or issuer, close its connection, sending a Streamable HTTP session's `DELETE` with the old bearer, and leave it disconnected until `/mcp auth NAME --open` or `/mcp reload`; then they revoke the grant's refresh token and access token at its revocation endpoint and report `Logged out of MCP server 'NAME' locally; remote revocation failed.` when either request fails. A project server that is not approved only has its stored grants deleted, without any request. A grant that a refresh renewed while the logout ran is revoked as well once the logout has deleted the stored grants, refresh token then access token, and kept unrevoked when the logout rolls back, where upstream discards it unrevoked, and a request that waited for that refresh fails with `McpAuthorityChanged` instead of sending it. In the shell the logout runs in the background and its result appears when it is done, so the shell keeps taking input while the revocation requests run, where upstream's shell waits for them; a `/mcp auth NAME --open` sent before that logout finishes closing the connection fails with `McpAuthorityChanged`, after its browser flow when it started before the logout's fence, and leaving the shell before the logout finishes can skip its revocation requests, both of which upstream's waiting shell cannot reach. A logout waits for a `/mcp reload` already in progress and then signs out the server that reload published, and a `/mcp reload` sent during a logout waits until the logout has deleted the grant and closed the connection, so no connection a reload starts carries the deleted grant; upstream's logout does not wait for a reload in progress, whose replacement connection can keep the grant after the logout succeeds. Each revocation request is bounded by 30 seconds as a whole, where upstream bounds each socket read and write by 30 seconds, and a request already sent on the closed connection may still finish, where upstream waits for it before closing.
- `/mcp add slack` prints the add usage without the Slack form, as `oh-fx mcp add slack` does.
- `/mcp resource list`, `templates`, `read`, and `complete`, and `/mcp prompt list`, `get`, and `complete` ask the server in the background, and their listing or failure appears in the transcript when it arrives, so the shell keeps taking input meanwhile. Upstream's shell waits for the answer, up to the server's operation timeout, before it takes more input. They wait for a server that is starting, but a server whose startup has not begun yet counts as offering no resources, prompts, or completions, so a completion fails with `McpCompletionUnsupported`, where upstream also waits for it while startup discovery runs. In the shell, `mcp_features` waits the same way, so for such a server it answers with its `unsupported` envelope or fails a completion with `McpCompletionUnsupported`; `oh-fx ask` starts the server first, as upstream does.
- A tool call that a server on a 2025-11-25 connection refuses with the URL-required error `-32042` asks for consent to open each of its URLs, opens the browser, waits for the server's `notifications/elicitation/complete` for each one or for the user to say the flow is complete, and calls the tool again, up to 8 rounds, as upstream does. Without a way to ask, as in `oh-fx ask` without a terminal, the tool result carries the URL requests as upstream's `input_required` result and ends the turn as `McpInputRequired`, as upstream's does: no further model request is made, the batch's later calls do not run, and `ask` exits with status 1 and reports `McpInputRequired`. A completion the server sends before its error arrives counts for that flow if it came within ten minutes on the same connection, where upstream counts only one that arrives while the call runs, and the limits of 32 waiting flows and 64 early completions apply to each connection, where upstream's apply to all servers together. When the connection ends, or the server is stopped, logged out, or replaced, while a flow's questions are open, they are withdrawn and the call ends as cancelled; upstream withdraws the consent question only when the server stops, so it can still open the browser for a lost connection before it ends the flow. A flow whose server's tools change, or are announced as changed, before the retry ends as cancelled, as upstream's does. A URL-required error `-32042` that carries `data` on a 2025-11-25 connection is handled for resource reads and prompt gets as upstream handles it: `mcp_features` asks for the URL consent and the completion and reads or gets again, up to 8 rounds, and answers `{"error":"McpInputRequired"}` and ends the turn when the flow is declined or cancelled or it cannot ask, while `/mcp resource read` and `/mcp prompt get` report `MCP resource read failed: McpInputRequired.` or `MCP prompt invocation failed: McpInputRequired.`, or `McpProtocolError` when the data is malformed. Every other JSON-RPC error that `resources/read` or `prompts/get` returns shows as the server's masked protocol error, as upstream's does.
- When an expired resource read fails over HTTP, the last contents are served if the connection was reset, timed out at the socket, broke its pipe, or ended early outside the response body. Those are the transient failures upstream accepts. A server that closes the connection cleanly before it sends the response head gets no fallback, because the HTTP client reports that case without a connection error oh-fx can tell apart, where upstream counts it as transient (`HttpConnectionClosing`).
- A resource read, prompt get, or completion checks that its resource, template, or prompt is still listed just before the request is sent. Upstream holds that check under a lock across an HTTP send, so a catalog refresh that lands between the check and the send refuses the request upstream (`McpFeatureCatalogChanged`) and lets it through in oh-fx. A read's contents are cached only if the catalog is still unchanged afterwards. The check compares the descriptors oh-fx keeps, so a refresh that changes only a field it does not keep, such as a resource's icons, annotations, size, or `_meta`, or a prompt's icons or `_meta`, leaves the request current, where upstream refuses it.
- `/mcp path`, `reload`, `trust`, `add`, `remove`, `auth`, and `logout` say `HOME is not available.` when oh-fx has no profile directory, which it takes from `XDG_CONFIG_HOME` or `HOME`, where upstream checks `HOME` alone.
- For a connected server, its `cache` field and the `retry_attempt` and `retry_in_ms` it reports follow upstream for tool, resource, template, and prompt catalogs. The change subscription reads `active`, `stopped`, or `unavailable`, as upstream's does on the connections oh-fx makes; its `starting` and `unsupported` states come from the 2026-07-28 protocol's `subscriptions/listen`, which is not ported. A server that failed after it was connected, such as one past its restart limit, one that answered 401, or one whose stored grant could no longer be refreshed, is disconnected and shows none of its negotiated details, counts, or cache state, where upstream keeps those of its last connection. A pending or rejected project server shows `state=disabled` as soon as the configuration is loaded, where upstream shows it disconnected until startup discovery has run.
- A reload refreshes the tool lists of the servers it keeps running; upstream also lists the tools of the servers it has just connected a second time.
