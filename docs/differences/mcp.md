# MCP

- Profile MCP servers live in `$XDG_CONFIG_HOME/oh-fx/mcp.json`, written with the `mcp.lock` advisory lock beside it, where upstream uses `~/.fx/mcp.json`. A workspace keeps its servers in `.mcp.json` at its root, the name other MCP clients read, and the project trust choices (`enabledMcpjsonServers`, `disabledMcpjsonServers`, and `enableAllProjectMcpServers`) live under the workspace's entry in the profile `settings.json`, as upstream keeps them.
- Adding or removing a profile MCP server fails with `StreamTooLong` and leaves `mcp.json` untouched when the canonical file it would write exceeds 1 MiB, the limit a profile is read with. Upstream writes the larger file, which its next read then refuses with the same error.
- MCP connections always start with the initialize handshake that upstream uses by default, and the opt-in 2026-07-28 protocol behind upstream's `FX_MCP_PROTOCOL_VERSION` is not ported: `OH_FX_MCP_PROTOCOL_VERSION`, in the environment or a server's `env`, accepts only `2025-11-25`, and any other value fails the server with `McpUnsupportedProtocolVersion`.
- Until MCP OAuth lands, a remote server that answers 401 fails with `McpAuthenticationRequired`, and `mcp auth` and `mcp logout` are not available. Static `headers`, `header_env`, and `bearer_token_env` work as upstream sends them. oh-fx advertises no elicitation capability, so a server's `elicitation/create` request is refused, where upstream asks the user.
- A failed MCP transport reports its error name, such as `ConnectionRefused`, `Timeout`, or `FileNotFound` for a missing stdio command, never the underlying message, which for HTTP names the request URL and anything in its query.
- Numbers in MCP results, such as a list's `ttlMs` or a resource link's `size`, are read through serde_json, which holds integers exactly and other numbers as the nearest double, so `1.0000000000000001` counts as the integer 1 where upstream reads the exact decimal and refuses it. serde_json also refuses a whole frame that holds a number beyond the double range or nests deeper than 128 levels, as `InvalidEnvelope`, where upstream parses it and then names the value's own error.
- Stopping a stdio MCP server also kills what is left in its process group after the server itself exited, so a background process it started does not outlive it. Upstream signals the group only while the server is still running.
- A Streamable HTTP event stream that breaks partway, answering a request or carrying notifications, is resumed with a GET whose `Last-Event-ID` is the last complete event's id, as the MCP resumability rules allow for network failures, and the notification stream keeps that id and the server's retry delay across its reconnection attempts. The request itself is never posted again. Upstream fails such a request with `ReadFailed` and restarts its notification stream without `Last-Event-ID`.
- Until `capability_search` finds MCP tools and `mcp_select_tool` and `mcp_features` land, every tool of a connected MCP server is advertised to the model on every step under upstream's name, `mcp_<server>_<tool>`, with upstream's selected schema (the tool description, the server instructions cut at `mcp_server_instructions_bytes`, and the input schema, left out with a `[context]` notice when it exceeds `mcp_selected_schema_bytes`). The notices keep upstream's wording, including its `--context-limit mcp_selected_schema_bytes=BYTES|off` and `mcp_server_instructions_bytes` override hints, although `--context-limit` refuses MCP limits until its full port adds those keys; `context_limits` in `settings.json` sets both meanwhile. Upstream advertises a server's tools this way only when the host marks it always loaded, and otherwise lists configured servers in an `<mcp_servers>` section and advertises a tool once `capability_search` or `mcp_select_tool` selects it. The section is left out until those tools exist.
- `oh-fx ask` connects every enabled MCP server it may start before the turn, in every output mode, so their tools can be advertised; upstream connects only required servers for `--json` and other non-terminal output and starts the rest on demand. The interactive shell connects them in the background at startup, as upstream starts discovery.
- An image or audio item in an MCP tool result is described as unsupported media, and a binary embedded resource as unsent, until tool results can carry images; upstream sends supported images to the model.
- Until upstream's project trust prompt lands with the MCP menu, the interactive shell reports unapproved project MCP servers in a warning notice that points to `/mcp trust approve <name>`, where upstream asks for project trust in the shell. Server names in that notice and in `oh-fx ask`'s list of skipped project servers are made terminal-safe, which upstream does only in its summaries. Servers that fail to start are summarized in upstream's startup notice.
- Until the interactive MCP menu lands, `/mcp` and `/mcp list` print upstream's summary and health listing in the transcript, as upstream does in hosts without the menu, where upstream's shell opens the menu.
- Until MCP resource reads, prompt invocation, completion, and OAuth land, `/mcp resource read`, `/mcp resource complete`, `/mcp prompt get`, `/mcp prompt complete`, `/mcp auth`, and `/mcp logout` check their arguments as upstream does and then say the feature is not available yet, such as `MCP resource reads are not available yet.`, where upstream runs them. `/mcp add slack` prints the add usage without the Slack form, as `oh-fx mcp add slack` does.
- `/mcp resource list`, `/mcp resource templates`, and `/mcp prompt list` ask the server in the background, and their listing or failure appears in the transcript when it arrives, so the shell keeps taking input meanwhile. Upstream's shell waits for the answer, up to the server's operation timeout, before it takes more input. They wait for a server that is starting, but a server whose startup has not begun yet counts as offering no resources or prompts, where upstream also waits for it while startup discovery runs.
- `/mcp path`, `reload`, `trust`, `add`, `remove`, `auth`, and `logout` say `HOME is not available.` when oh-fx has no profile directory, which it takes from `XDG_CONFIG_HOME` or `HOME`, where upstream checks `HOME` alone.
- The MCP health listing reports `auth=none` or `auth=configured` and no `needs auth` count until OAuth lands. For a connected server, its `cache` field and the `retry_attempt` and `retry_in_ms` it reports follow upstream for resource, template, and prompt catalogs, but the tool catalog counts as `fresh`, or `stale` once the server announced a tool list change that is not yet fetched, without upstream's expiry, refreshing, and failed-refresh states for tools. The change subscription reads `active`, `stopped`, or `unavailable`. A server that failed after it was connected, such as one past its restart limit, shows none of its negotiated details, counts, or cache state, where upstream keeps those of its last connection. A pending or rejected project server shows `state=disabled` as soon as the configuration is loaded, where upstream shows it disconnected until startup discovery has run.
- A reload refreshes the tool lists of the servers it keeps running; upstream also lists the tools of the servers it has just connected a second time.
