# `oh-fx ask`

- `oh-fx ask ""` fails with `InvalidConversationEvent` before any request is sent.
- A streamed write to a closed or failing stdout cancels the request and ends `ask` with the failed write's name, such as `BrokenPipe` or `NoSpaceLeft`.
- Until upstream's ask presenter is ported, terminal-mode `ask` writes the turn to stdout as plain lines: assistant text as it streams, operational lines such as `Done.`, `[notice]` recovery and system notice lines, and tool progress lines. Consecutive lines of each of the last three kinds stay together, and exactly one blank line separates each such run from assistant text and from runs of another kind. Whitespace the model streams is written only once visible text follows it, so blank lines at either edge of a stretch of text merge into that separator, and the output ends with a single newline; whitespace at the very start of the output is kept. Upstream paints the same events on stdout as a styled transcript with a banner, the prompt, indented Markdown, and grouped tool rows. A streamed start for a registered tool with provisional presentation metadata prints its generic progress line immediately, before its arguments are complete, as upstream does. The plain terminal transcript keeps that line and appends the admitted call's full title, where upstream replaces its provisional row. A rejected provisional call counts no executed step, including in JSON output. Blocked-action guidance and failure lines stay on stderr and start on a new line. Progress lines and blocked-action labels escape their control characters with terminal-safe encoding. The raw, quiet, and JSON modes print progress, operational lines, and notices on stderr, as upstream does.
- `ask --json` lists the tool calls of a parallel group in call order. Upstream lists the calls that ran in the order their threads finish, then the calls that failed before running, such as on invalid arguments or a missing path.
- On a Codex connection, upstream's `ask` prints each streamed call's provisional label, such as `● Reading` followed by a raw `ESC [0m`, on stderr in every output mode, and leaves a call rejected before it runs, such as on invalid arguments, out of `steps`. oh-fx publishes provisional progress in `ask` for registered tools with presentation metadata and leaves their rejected provisional calls out of `steps`. Terminal mode prints its plain progress line on stdout; raw, quiet and JSON modes print the upstream progress bytes on stderr. Interactive provisional rows remain deferred.
- `oh-fx ask` asks for an approval on stderr when stdin is a terminal, as upstream does: in the raw and terminal output modes always, and in the JSON and quiet modes only with `--prompt-permissions`. It writes `oh-fx wants to run:`, the call's permission label, and `Approve? [y/N] `, rings the terminal bell when stderr is a terminal, and reads one line: a single `y` or `Y` approves the call once, and anything else, an empty line, end of input, or a line of 256 bytes or more denies it, so the model receives upstream's `tool_permission_denied` result and the turn goes on. A line that long is read through to its end and dropped, so no part of it answers a later prompt; upstream stops at its 256-byte buffer and leaves the rest of the line on stdin, where its next prompt reads it as an answer to a call the user has not seen yet. The label is upstream's: `shell.run` with the command and its risk and safer-alternative notes, `file_mutation` for a file change, or the tool name and its target. A call's progress line comes before its prompt, except a file change's and `web_fetch`'s, which follow the decision, as upstream orders them. A review that reaches no decision still holds the call, as upstream holds it, where the interactive session asks instead. Upstream's terminal transcript replaces a denied call's row with `⊘ Denied: <action>`, and its attention notification can also play a sound; oh-fx's plain terminal lines show no denied row, and it rings only the bell. Every label escapes control characters, in the tool name and its target as well as in a command, and redacts `web_fetch` URLs, as oh-fx's progress lines and blocked-action labels do, so a path, pattern, or tool name the model supplies cannot rewrite the approval prompt the user answers. Upstream escapes only a `shell.run` command and writes the other labels' arguments raw. As upstream does, the agent decides every call of a group that may run together, asking about each in turn, before any of them starts, so a prompt never overlaps a running tool, in `ask` and in the interactive session alike; a cancellation while the group is decided starts none of it.
- `oh-fx ask` honors `--model`, `--effort`, `--fast`, `--no-fast`, `--auto`, `--full-access`, `--yolo`, `--system`, `--timeout`, `--json`, `--quiet`, `--no-color`, `--resume`, `--resume-id`, `--continue-recovery`, `--prompt-permissions`, and `--no-save`. It fails as not available yet on `--image`, because image attachments do not exist yet. It also fails as not available yet when `--sessions-v2`, given before or after `ask`, or `OH_FX_SESSIONS_V2` set to `1` or to `true` in any letter case selects the v2 session store, unless `--no-save` is given: the flag and the variable explicitly ask for the v2 store, whose sessions upstream resumes only with the flag, so oh-fx reports that it cannot honor the request instead of saving to the default store. Upstream's `--no-save` writes nothing to either store, so with it the request runs. It validates `--provider-order`, `--provider-strict`, and `--no-provider-strict` as upstream does and then ignores them, as upstream does for custom provider connections, which never advertise gateway routing. Custom connections never advertise reasoning or Fast mode either, so `--effort` and `--fast` leave their requests unchanged, as upstream. `--verbose` is accepted and ignored, as upstream does.
- `ask --system` must be valid UTF-8 and otherwise fails with `InvalidAskArgs` before any request. Upstream sends the invalid bytes as a JSON byte array, which OpenAI-compatible gateways reject.
- `ask` starts its session once the connection is ready, so a run that fails while selecting the provider, reading credentials, or refreshing a Codex login leaves no session, where upstream has created one by then. As upstream, a first request rejected as unauthorized discards the new session, a store that cannot be opened prints `oh-fx ask: warning: session persistence unavailable; error=<code>; continuing without saving` and runs without saving, a session that cannot be started in an open store fails the run with the store's error, and a session `--resume` or `--resume-id` cannot open fails the run with the store's error before any request.
- `ask` rejects a `--model` that is not valid UTF-8 with `InvalidModel` before it reads or refreshes the Codex login, so such a model never triggers a refresh. Upstream has no such error and loads and refreshes the login at startup, before it looks at the model. Other models the Codex request rejects, such as an empty name, still fail when the request is built, as upstream's do.
- `ask` looks up the model's capabilities, the Codex model catalog included, at the start of a run only when a reasoning effort other than `auto` or Fast mode is requested, or when the skill catalog has skills or warnings to render under its compiled default budget, which scales with the context window. Otherwise it looks them up once the conversation holds something compaction could replace, an earlier turn or a finished tool step, since the context window matters only then. Upstream looks them up at the start of every run. A run that ends with its first reply therefore makes no catalog or Codex release lookup, and a first request is measured against the context window only when the capabilities are already known, so a first prompt too large for the model fails with the provider's own error where upstream fails with `ContextCapacityExceeded` before sending it.
